# 面试链路设计文档

## 概述

面试链路是系统的核心功能，负责将一份简历转化为一场结构化的模拟面试，并在结束后给出评估报告。

整条链路由三个阶段组成：**出题（bootstrap）**、**对话（reply）**、**评估（evaluate）**。每个阶段背后都有一个独立的 AI 工作流在驱动，这个工作流由 LangGraph 编排。在深入每个阶段之前，我们先理解 LangGraph 在这里扮演的角色。

---

## LangGraph：面试流程的"剧本引擎"

### 它是什么

LangGraph 是一个用来编排 AI 工作流的框架。你可以把它想象成一个**剧本引擎**：你提前写好剧本（定义节点和流转规则），每次执行时它按剧本推进，每一幕（节点）做完一件事，然后把结果交给下一幕。

LangGraph 的核心概念只有三个：

- **State（状态）**：贯穿整个流程的数据容器，类似演员手里的剧本，记录着"现在演到哪了、说过什么"。
- **Node（节点）**：每一步要做的事，是一个纯函数——接收当前 State，返回对 State 的局部更新。节点不直接读写数据库，只操作内存中的 State。
- **Edge（边）**：节点之间的连接，决定执行顺序。可以是固定顺序，也可以根据条件分支。

### 为什么用它

面试对话天然是有状态的：当前在第几题、这道题有没有追问过、每道题说了什么——这些信息需要在用户的每次回答之间保持一致。如果不用框架，这些状态会散落在各处的字典里，很难维护。

LangGraph 的 `TypedDict` State 给了这些字段明确的类型定义，让状态结构一目了然。同时，出题、对话、评估三个子任务各自有不同的逻辑，LangGraph 允许为每个子任务定义独立的图，互不干扰，对外统一由 `CvInterviewWorkflow` 暴露。

### 图执行是"无副作用"的

这是理解整个系统的关键点：**LangGraph 的节点函数不直接读写数据库**，它只在内存里操作 State。数据库的读写全部由外层的服务层（`InterviewService`）在图执行前后完成。

可以把它理解成一个计算器：你把数字（State）递进去，它算完把结果还给你，它自己不存任何东西。存不存、存在哪，是调用方的事。

```
服务层从数据库读取 workflow_state
    │
    ▼
传入 LangGraph 图执行（纯内存计算）
    │
    ▼
服务层将更新后的 workflow_state 写回数据库
```

这个设计让工作流逻辑可以独立测试，也让服务层完全掌控持久化的时机。

## 整体流程

理解了 LangGraph 之后，再看整体流程就清晰很多。三个阶段各对应一个 LangGraph 图，由服务层串联起来：

```
用户携带简历信息发起面试
         │
         ▼
   [出题阶段] plan_graph
   根据简历生成 4 道题目
   创建会话，状态: preparing
   返回第一道题（SSE 流式）
         │
         ▼
   [激活] activate
   用户确认开始，状态: preparing → active
         │
         ▼
   [对话阶段] interview_graph（每次回答执行一次）
   用户回答 → 生成追问 or 切到下一题
   最后一题追问完成后自动触发评估
   状态: active → completed
         │
         ▼
   [评估阶段] evaluation_graph
   分析全部对话，生成结构化评估报告
         │
         ▼
   [强制结束] finish（可选）
   用户主动结束，跳过剩余题目，直接触发评估
```

---

## 会话状态机

每个面试会话有三个状态，只能单向流转，不可逆：

```
preparing ──► active ──► completed
```

- **preparing**：出题完成、会话已创建，但用户尚未正式开始。此状态下不接受回答。
- **active**：用户已确认开始，正在进行对话。
- **completed**：面试结束，评估报告已生成，不再接受任何操作。

`preparing` 状态的存在是为了给用户一个"预览题目、确认开始"的窗口。出题需要调用 LLM，有几秒延迟，先完成出题再让用户确认，比"点击开始后干等"的体验更好。同时它也给了前端一个明确的信号：会话已创建但尚未开始，可以安全地展示题目预览。

## 三个阶段的设计

### 阶段一：出题（bootstrap）

**触发**：`POST /api/interviews/stream`

**对应 LangGraph 图**：`plan_graph`

```
START → draft_plan → pick_opening_question → END
```

`plan_graph` 是一个线性图，只在发起面试时执行一次。两个节点分工明确：`draft_plan` 负责生成全部 4 道题，`pick_opening_question` 负责取出第一题、准备开场白。

**题目是怎么生成的**

题目生成有两条路径，取决于是否配置了真实的 LLM：

- **LLM 路径**：将简历全文、亮点标签、工作/项目经历、技术技能一并发给 LLM，要求返回 4 道题，每道题包含题干、考察焦点、追问方向提示。
- **规则路径（mock fallback）**：从简历中匹配预定义技能关键词，提取最多 4 个考察焦点，再用固定模板生成 4 道题（项目背景、技术决策、问题排查、业务与成长）。

无论哪条路径，最终都产出结构相同的 4 道题：

| 字段 | 说明 |
|---|---|
| id | 题目编号（q1~q4） |
| title | 题目标题 |
| prompt | 题干，直接展示给用户 |
| focus | 考察焦点，用于生成追问，不展示给用户 |
| follow_up_hint | 追问方向提示，仅供 LLM 参考，不展示给用户 |

`focus` 和 `follow_up_hint` 是"幕后信息"——用户看不到，但它们在后续每次追问时都会传给 LLM，帮助 LLM 知道这道题要往哪个方向深挖。

难度等级也在这一步生效：LLM 路径会在 prompt 里说明难度，规则路径则在题干前加前缀（"请结合最熟悉的场景"、"请把问题放到高压场景里"等）。

**出题完成后发生了什么**

`plan_graph` 执行完成后，服务层接管：
- 创建 `interview_sessions` 记录，状态为 `preparing`，将完整的工作流状态（含 4 道题）存入 `workflow_state_json`
- 将第一道题作为第一条消息写入 `messages` 表
- 通过 SSE 流式返回给前端：先推送会话元数据（含题目列表和剩余配额），再逐字符流式输出第一道题的题干

**配额扣减的时机**

配额在调用 LLM 出题之前就扣减。这意味着即使出题失败，配额也已消耗。这是有意为之——防止用户通过反复触发失败来规避配额限制。代价是偶发的 LLM 故障会让用户损失一次机会，这个取舍在教学版场景下是可以接受的。

### 阶段二：对话（reply）

**触发**：`POST /api/interviews/{session_id}/reply/stream`

**对应 LangGraph 图**：`interview_graph`

```
START → record_answer → compose_response → END
```

与 `plan_graph` 不同，`interview_graph` 会被反复执行——用户每回答一次，图就跑一遍。每次执行时，服务层从数据库读取最新的 `workflow_state` 传入，图执行完成后再把更新后的状态写回去。图本身没有记忆，所有上下文都来自传入的 State。

**两个节点的分工**

- `record_answer`：把用户的回答追加到当前题目的对话线程（`QuestionThread`）里。每道题都有自己的线程，记录这道题从出题到追问的完整对话历史。
- `compose_response`：这是核心决策节点，根据当前状态决定下一步做什么：

```
当前题目尚未追问？
    └── 是 → 生成追问，标记该题 follow_up_done = true
    └── 否 → 还有下一题？
                └── 是 → 生成过渡话术 + 下一题题干，current_index + 1
                └── 否 → 输出结束语，触发评估，status → completed
```

每道题只追问一次。追问完成后，用户的下一次回答会直接切到下一题。这个设计控制了对话总轮次，保证整场面试在可预期的长度内结束，不会无限延伸。

**追问和过渡话术怎么生成**

- **LLM 路径**：把当前题目的考察焦点（`focus`）、追问提示（`follow_up_hint`）和用户的回答一起发给 LLM，生成自然的追问。追问控制在 40-90 字，过渡话术控制在 28-60 字，要求先接住用户的回答再自然转场，不能生硬切换。
- **规则路径（mock fallback）**：根据回答长度和关键词（指标类词汇如"QPS"、"延迟"，协作类词汇如"团队"、"上线"等）匹配固定模板，生成预设的追问语。

**消息持久化的顺序**

用户的回答在调用 LLM 之前就写入数据库。这样即使 LLM 调用失败，用户的回答也不会丢失，前端可以安全重试。LLM 生成的回复在调用成功后才写入，同时更新 `workflow_state_json`。

**SSE 流式输出**

LLM 调用是同步阻塞的，完成后再按固定块大小（默认 10 字符）加延迟（默认 25ms）分块推送，模拟流式打字效果。这是"伪流式"——追问和过渡话术都是短文本（40-90 字），真正的 token 级流式收益有限，伪流式实现更简单，也更容易控制节奏。如果本轮触发了评估，评估结果也通过 SSE 一并推送。

---

### 阶段三：评估（evaluate）

**触发时机**：
1. 对话阶段最后一题追问完成后自动触发
2. 用户主动调用 `POST /api/interviews/{session_id}/finish`

**对应 LangGraph 图**：`evaluation_graph`

```
START → evaluate → END
```

最简单的线性图，只有一个节点。输入是全部 `question_threads`（每道题的完整对话历史），输出是结构化的评估报告。

- **LLM 路径**：将所有题目和对话记录格式化后发给 LLM，要求返回包含综合评分（0-100）、评级（稳健/良好/待加强）、总结、优势列表、改进建议列表的 JSON。
- **规则路径（mock fallback）**：基于回答题数、总字数、覆盖的考察焦点数量，用公式计算基础分，再生成固定模板的优势和建议。

评估结果写入 `interview_sessions.evaluation_json`，会话状态更新为 `completed`。

**`finish` 接口**

`finish` 允许用户在任意时刻强制结束面试，不要求已经回答完所有题目。它跳过剩余的对话轮次，直接触发评估。评估基于已有的对话记录，未回答的题目不影响评估流程，只影响最终评分。

---

## workflow_state：贯穿全程的"记忆"

面试是一个跨越多次 HTTP 请求的有状态过程，但 HTTP 本身是无状态的。`workflow_state` 就是解决这个矛盾的关键——它是面试进度的完整快照，存储在数据库的 `workflow_state_json` 字段里，每次 reply 后更新。

它的字段结构直接对应 LangGraph 的 `InterviewState` TypedDict：

| 字段 | 说明 |
|---|---|
| questions | 4 道题目的完整信息 |
| question_threads | 每道题的对话线程，含所有消息历史 |
| current_index | 当前正在回答的题目索引（0-3） |
| status | 面试状态 |
| target_role / language / difficulty_level | 面试配置，用于生成追问时传给 LLM |
| model_provider / model_name | 使用的模型，贯穿整个面试 |
| trace_id | 链路追踪 ID，贯穿整个面试 |

每次用户回答时，服务层从数据库取出这份快照，传给 LangGraph 图执行，图执行完成后把更新后的快照写回数据库。工作流本身不持有任何内存状态——服务重启、进程崩溃都不会丢失进度，下次请求照样能从上次停下的地方继续。

值得注意的是，`question_threads`（工作流视图）和 `messages` 表（展示视图）存在一定的数据冗余。前者是 LangGraph 生成追问时需要的上下文，后者是前端渲染对话界面需要的数据。两者分开维护，互不依赖，各自服务于不同的消费方。

## 分层结构

整个面试链路分为五层，每层职责清晰：

```
路由层（routes/interviews.py）
    │  参数校验、鉴权、SSE 响应封装
    ▼
服务层（interview_service.py）
    │  业务规则（配额、状态校验）、消息持久化、SSE 生成
    │  负责在 LangGraph 图执行前后读写数据库
    ▼
工作流层（workflow.py / CvInterviewWorkflow）
    │  LangGraph 图定义与执行、LLM 调用、规则 fallback
    │  不感知 HTTP，不直接读写数据库
    ▼
LLM 层（llm/factory.py）
    │  provider 路由（OpenAI / Anthropic / 火山引擎 / mock）
    │  JSON 提取、错误处理
    ▼
存储层（db/store.py）
    │  SQLite CRUD，不感知业务逻辑
```

工作流层不感知 HTTP，服务层不感知 LangGraph 内部结构，存储层不感知业务逻辑。这种分层让每一层都可以独立修改和测试。

## 关键设计决策

**为什么每道题只追问一次？**
控制对话总轮次，保证面试在可预期的时间内结束。无限追问会让用户感到压迫，也增加 LLM 调用成本。一次追问足以验证候选人是否能在压力下补充细节。

**为什么 workflow_state 整体存储而不拆列？**
工作流状态的内部结构会随功能迭代演化（新增字段、调整 thread 结构等），整体存储让数据库 schema 保持稳定，变更只影响应用代码。

**为什么用户消息在 LLM 调用前就持久化？**
防止 LLM 调用失败导致用户回答丢失。用户的输入是最重要的数据，应该最先保存。

**为什么流式输出是"伪流式"？**
追问和过渡话术都是短文本（40-90 字），真正的 token 级流式收益有限，而伪流式实现更简单，也更容易控制推送节奏。

**为什么 LangGraph 节点不直接操作数据库？**
保持节点函数的纯粹性，让工作流逻辑可以脱离数据库独立测试。持久化的时机和方式由服务层统一掌控，工作流只负责"算"，不负责"存"。
