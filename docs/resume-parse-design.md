# 简历解析链路设计文档

## 概述

简历解析是面试流程的入口。用户上传简历文件后，系统将非结构化的文本转换为结构化的候选人画像，供后续出题和追问环节使用。整条链路的核心设计目标是：**在 LLM 可用时尽量利用语义理解，在 LLM 不可用时保证基础功能不中断**。

---

## 链路全景

```
用户上传文件
     │
     ▼
[格式校验] ── 不支持的格式 ──► 400 Bad Request
     │
     ▼
[文本提取] ── 提取失败 ──► 400 Bad Request
     │
     ▼
[内容校验] ── 文本过短 ──► 400 Bad Request
     │
     ▼
[结构化解析] ── LLM 可用 ──► LLM 语义解析
     │         └── mock 模式 ──► 规则解析（fallback）
     │
     ▼
[归一化处理]
     │
     ▼
[持久化存储]
     │
     ▼
返回 ResumeExtractResponse
```

---

## 各阶段设计

### 1. 格式校验

接受 `.pdf`、`.txt`、`.md`、`.docx` 四种格式，在路由层通过 `UploadFile` 拿到文件名后缀即可判断，不需要读取文件内容。拒绝时直接返回 400，不消耗任何计算资源。

这里没有做 MIME type 校验，只依赖后缀名。对于教学版场景，这个精度足够，避免引入额外依赖。

### 2. 文本提取

不同格式走不同的提取路径：

| 格式 | 提取方式 |
|---|---|
| `.txt` / `.md` | UTF-8 解码，`errors="ignore"` 容错 |
| `.pdf` | `pypdf.PdfReader`，逐页提取，换行拼接 |
| `.docx` | `python-docx`，逐段落提取，换行拼接 |

提取结果是纯文本字符串，后续所有处理都基于这个字符串。PDF 和 DOCX 的提取质量依赖原始文件的排版，扫描件 PDF 会得到空文本，这是已知限制。

提取完成后做一次长度校验（`< 20` 字符视为无效），防止空文件或纯图片 PDF 进入后续流程。

### 3. 结构化解析

这是链路中最核心的一步，也是设计上最需要权衡的地方。

#### 设计原则：LLM 优先，规则兜底

系统不强依赖 LLM。当 `llm_provider` 配置为 `mock`（默认值）或 LLM 客户端初始化失败时，自动降级到基于规则的本地解析器。两条路径产出相同的数据结构，对下游透明。

```
_parse_resume_text()
    └── _parse_with_llm()
            ├── MockLLMClient → _parse_with_rules()   # 规则路径
            └── LangChainLLMClient → LLM prompt       # 语义路径
```

#### LLM 解析路径

向 LLM 发送包含简历全文的 prompt，要求返回固定 JSON 结构：

```json
{
  "personal_info": "一句话个人信息摘要",
  "highlights": ["亮点标签"],
  "technical_skills": ["技能1", "技能2"],
  "work_experience": [{"name": "公司/经历名", "detail": "内容"}],
  "project_experience": [{"name": "项目名", "detail": "内容"}]
}
```

`highlights` 和 `technical_skills` 限制最多 8 个，避免 LLM 过度发散。

LLM 返回的文本经过 `_extract_json()` 处理，该函数先尝试直接 `json.loads`，失败后用正则从文本中提取 `{...}` 或 `[...]` 块再解析，兼容 LLM 在 JSON 前后附加说明文字的情况。

#### 规则解析路径（fallback）

规则解析器不依赖任何外部服务，完全本地运行：

- **个人信息**：取简历前 3 行拼接，截断到 240 字符
- **工作/项目经历**：按关键词（"工作经历"、"项目经历"、"experience" 等）切分段落，再按列表符号（`-`、`•`、数字序号）切分条目
- **技术技能**：对预定义的 20 个技术关键词做全文匹配（大小写不敏感）
- **亮点标签**：直接复用技术技能的前 4 项

规则解析的质量明显低于 LLM，但对于格式规范的简历能提取出基本可用的信息，足以支撑后续出题流程。

### 4. 归一化处理

两条路径的归一化行为略有差异：

**LLM 路径**（`_normalize_entries`）：
- 字符串字段 `.strip()`，空值转为空字符串
- 列表字段去重、截断到上限（highlights / technical_skills 最多 8 个）
- `work_experience` / `project_experience` 过滤掉 `detail` 为空的条目，最多保留 6 条
- `detail` 字段不做长度截断，原样保留 LLM 输出

**规则路径**（`_make_entries`）：
- 工作/项目经历最多保留 4 条（而非 6 条）
- 每条经历的 `detail` 截断到 1200 字符，防止后续 prompt 过长
- 当技术技能关键词全部未命中时，亮点标签 fallback 到固定值 `["项目表达", "技术取舍", "问题排查"]`

归一化的核心目的是：LLM 输出不可控，但数据库写入和出题 prompt 的构造需要稳定的结构。

### 5. 持久化存储

解析结果以 JSON 整体存入 `resumes` 表的 `payload_json` 字段，同时记录原始 `resume_text`、使用的 `model_provider` 和 `model_name`。

存储时额外记录 provider 和 model 信息，主要用于调试和审计：当解析质量出现问题时，可以快速定位是哪个模型在哪次解析中产生的结果。

读取时 `_serialize_resume()` 将 JSON 展开为扁平结构返回，`resume_text` 也一并返回，供前端在发起面试时直接复用，不需要重新上传文件。

---

## 数据流向

简历解析的产出物在后续流程中有两个用途：

1. **出题阶段**：`resume_text`、`highlights`、`work_experience`、`project_experience`、`technical_skills` 全部传入 `build_questions_with_llm()`，LLM 据此生成针对性的面试题
2. **前端展示**：`personal_info`、`highlights`、`technical_skills` 直接展示在面试配置页，用户可以在发起面试前确认解析结果是否准确

---

## 关键设计决策

**为什么不在上传时做流式响应？**
简历解析是一次性操作，用户等待几秒是可接受的。流式输出对结构化 JSON 没有意义，同步返回更简单。

**为什么 resume_text 要原样存储？**
LLM 解析可能丢失细节，保留原文让用户在发起面试时可以选择直接传原文给出题 LLM，而不是只传结构化摘要。这在简历内容复杂时能提升出题质量。

**为什么规则解析不做更复杂的 NLP？**
规则解析只是 mock 模式下的开发辅助，不是生产路径。保持简单降低维护成本，真实场景下应配置 LLM provider。

**provider 和 model 为什么在请求时传入而不只用配置？**
前端可以在上传简历时指定使用哪个模型解析，与后端全局配置解耦。这样同一套后端可以支持用户选择不同的解析质量/成本组合。
