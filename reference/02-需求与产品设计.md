# 02 需求与产品设计：把想法变成可验收行为

## 1. 用户真正要完成的任务

用户不是来观看一个模型聊天，而是希望在有限时间内练习与目标岗位相关的表达，知道自己哪里讲清了、哪里仍缺依据，并据此安排下一次练习。

以库存项目为例，“多问几道 Redis 题”只是功能描述。“帮助用户发现自己能讲原子扣减，却解释不清订单写入失败后的处理”才是可观察的练习价值。因此产品需要同时覆盖面试前的方向选择、面试中的适应性追问，以及结束后的可操作反馈。

当前实现支持校招／社招、岗位、技术语言、难度、可选 JD 与重点方向。它们提供生成上下文，不构成真实招聘结论，也不能保证每个 JD 要点都被充分验证。

## 2. 第一版为什么应该控制范围

开发推演中，最小版本应先保证登录、简历、创建会话、回答、结束和查看结果能够连通。若同时实现自动出题、复杂追问、长期档案和高级检索，出现错误时很难判断是哪一环出了问题。

历史旧版本的固定追问是合理的起点：简单、容易观察、便于跑通存储和页面。它的限制是策略粗糙。动态追问应在基础链路稳定后加入，而不是把第一版写成什么都没有考虑的错误设计。

## 3. 计划预览解决什么

用户可能想练系统设计，系统却偏向基础知识。直接进入对话会让用户在开始后才发现方向不匹配。预览使考察范围在消耗正式面试机会前可见。

当前预览提供主题名称、是否必考、预计时间等信息；完整开场题和评估标准留在内部计划中。候选人需要知道方向，但过早看到全部题干会改变模拟效果。因此“预览计划”不等于“公开完整计划 JSON”。

生成后可以策略化重新生成，最多额外两次。生成调用内部最多三次尝试是另一件事：前者是用户调整版本的额度，后者是单次生成对异常输出的重试预算。

## 4. 关键需求怎样验收

| 需求 | 正常行为 | 必须考虑的反例 |
|---|---|---|
| 简历属于当前用户 | 自己的简历可用于创建 | 他人的简历 ID 不可引用 |
| 计划开始前可调整 | 新版本有有效差异并保留历史 | 仅改无关文字不应算有效新计划 |
| 确认后固定版本 | 后续使用 confirmed_plan_id | 重复确认返回冲突；并发需另验 |
| 面试有边界 | 时间／轮数／追问限制由代码判断 | 模型请求继续追问不能越过硬边界 |
| 评估可追溯 | 结论关联主题和回答依据 | 没有证据的方向不能假装充分验证 |
| 可恢复查看 | 刷新后从服务端读取记录 | 请求断开不能被当成业务必然失败 |

这些是验收语义，不是宣称每项均已通过本次运行验证。测试映射见第 10 章。

## 5. 产品上的冲突与取舍

**深度与覆盖冲突。** 库存问题可以追问很久，但本场还要覆盖其他方向。当前通过总轮数、单主题轮数与收尾区控制投入。代价是有价值的追问也可能被截断，不能保证每个主题都达到同样深度。

**反馈与谨慎冲突。** 用户希望拿到明确分数，但未充分考察时给一个确定低分容易误导。三态验证和空分保留不确定性。界面还必须说明总分只覆盖已评分方向，否则少量高分主题可能被误读为整体能力很高。

**连贯与成本冲突。** 多次模型调用可以把证据、判断和表达分开，却增加等待。分块展示改善阅读节奏，不能替代降低首个有效响应时间。

**长期学习与可比性冲突。** 两场计划难度和覆盖不同，分数变化不一定代表能力变化。学习档案需要隔离用户、简历、岗位和面试类型，并过滤无效场次，仍需谨慎解释趋势。

## 6. 不应写进当前成果的内容

不能把真实并发容量、专家评分一致率、用户留存增长、正式生产运行时间写成现有成绩，除非另有测量。当前目标是练习闭环；生产级招聘决策、公平性验证和完整商业运营并无充分依据。

## 7. 差异化诉求与免费额度策略

**为什么做差异化**：市场上多数 AI 面试工具只提供"问问题 + 给分数"，用户难判断分数是否可靠。Offer Agent 在登录页和简历页 hero 区插入 3 张卖点卡片（数据库/工作流/盾形图标）：

- 卖点 1：基于近 3 年 3000+ 真实面试数据训练 prompt 模板
- 卖点 2：计划→执行→证据三段式，每轮追问可追溯到计划主题
- 卖点 3：评分规则可追溯到候选人原话

**免费额度策略**：每个新用户 `quota_remaining=1`（一次性免费面试），降低首次试用门槛。充值档位 `¥20/5 次` 适合短期密集练习，`¥200/月卡` 适合长期持续练习。月卡激活后 `tier='subscription'` + `subscription_expires_at`；激活面试时若订阅有效，**跳过 quota 拦截**且不扣 quota 字段。`membership_status`（`active_subscription` / `expired_subscription` / `paid` / `free`）由 `apply_payment_to_user` 与 `sync_subscription_status` 统一维护，是订阅状态的单一权威。

**算法回合**：让候选人获得代码级练习反馈，与主对话流独立；UI 体现为 live page 右侧滑出 side panel。模型质量对算法的要求比对话低（不需要角色扮演），但仍要 LLM 跑完整调用，**不**走规则本地判题。算法评分不写 `messages` 表，避免污染面试对话流。

**面试配置补齐**：在原基础上扩展：
- `target_role` 枚举从 4 个扩到 9 个（+ `data_ml` / `mobile` / `qa` / `sre` / `embedded` / `__custom__`），`__custom__` 时 `custom_target_role` 必填
- `INTERVIEW_TYPES` 加 `intern`（实习）
- `duration_minutes` 枚举 `[15, 30, 45, 60]`，替代写死的 45 分钟
- `include_algorithm` 开关 + `focus_topics` 上限 8
- `language` 字段保留在 schema 以兼容老数据，但前端 UI 已移除
