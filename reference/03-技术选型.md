# 03 技术选型：说明适用条件与真实代价

## 1. 选型应该从约束出发

这个仓库的规模与形态是前后端分离、Python 模型调用、单机 SQLite、可选本地向量索引。现有代码能证明用了什么，无法证明当时团队熟悉度、采购预算或评审过程。下面的比较是基于当前需求的设计解释，不冒充历史会议记录。

## 2. FastAPI 与 React

FastAPI 承担请求校验、鉴权依赖、业务路由和 StreamingResponse，适合把 Python 中的模型工作流暴露为接口。它不会自动把同步 SDK 调用变成异步。当前回复路由用 `asyncio.to_thread` 承载同步业务处理，避免该段同步执行直接占住事件循环，但线程、模型连接与数据库写入依然是有限资源。

React 承担页面交互；React Router 对应不同业务阶段；TanStack Query 管理服务端查询与 mutation；TypeScript 提供开发期类型约束。前后端分开便于独立迭代，也带来接口结构同步、跨域和部署路由回退的工作。

替代方案可以是服务端模板或一体化框架。若页面简单且交互少，它们可减少两端协作成本；当前面试工作台包含异步状态、流式展示和多阶段页面，独立前端有现实收益。不能由此推出所有项目都应该前后端分离。

## 3. 为什么使用 LangGraph

本项目的一轮回答有明确节点、条件分支和共享状态：接收回答、组装上下文、边界检查、抽取、合并、决策、话术或切题。图结构把这些步骤及分支集中表达，便于观察流程。

普通函数配合条件分支同样可以实现。选择图的收益在于流程可读性与节点边界；代价是框架概念、状态字段约定和调试复杂度。框架不是动态决策的来源，模型与规则才负责判断。

当前图通过 `compile()` 构造，每次回复执行 `invoke`。服务层负责加载并保存运行态。不能声称已经使用 checkpointer、分布式任务调度或节点级自动恢复。LangChain 与 LangGraph 也不是必须二选一：当前模型接入与图编排承担不同职责。

## 4. 为什么先用 SQLite

SQLite 无需单独维护数据库进程，数据文件方便本地运行，适合当前单机原型。Store 集中读写，让服务层不必到处拼 SQL。

代价在写竞争、部署存储和演进管理。SQLite 可以有事务，但当前多个 Store 方法各自提交，不会因为底层是数据库就自动成为一个跨方法事务。迁移 PostgreSQL 也不只是改连接字符串：需要处理驱动、SQL、事务、约束、并发控制、迁移脚本与数据回填。

判断是否迁移应看写入等待、锁冲突、多实例部署需要和维护成本；没有实测前，不给出“支持多少并发”的数字。

## 5. 为什么选择可选 RAG

岗位知识可帮助规划阶段补充通用考察框架，但不应成为基础面试闭环的强依赖。当前 RAG 默认关闭，仅规划阶段调用；检索失败可以继续规划。

Milvus Lite 是当前本地索引载体，不代表系统部署了分布式向量集群。默认 local embedding 是确定性哈希向量，适合无外部依赖地运行检索链路，但语义泛化弱，不能把它宣传为经过训练的高质量语义模型。改为语义 embedding 后要重建索引并验证维度一致与召回质量。

若语料很少，可以比较关键词检索、直接提供精选岗位材料与向量检索。是否增加 RAG 应由固定样本上的检索相关性和计划质量决定。

## 6. 为什么模型能力要包在适配层

`backend/app/llm/factory.py` 提供统一创建与调用入口，让业务不用直接依赖每个 Provider 的请求格式。收益是更换服务商时减少业务层改动，统一日志与结构化输出处理。

适配并不保证语义等价。相同提示词换模型后，字段遵循、中文表达、延迟和证据抽取质量都可能改变，需要回归。当前不应宣称自动切换服务商或具有多 Provider 故障转移，除非代码和测试明确提供这条路径。

## 7. SSE 的选择

回答请求使用 POST 并携带鉴权与答案，再通过 fetch 读取响应流。单向推送展示结果不需要 WebSocket 的双向连接管理。代价是客户端必须自己解析事件与处理断流。

当前模型生成完成后才开始 SSE，因此选择 SSE 的理由是展示协议与事件表达，不是已实现 token 级实时生成。真正接入 token 流时，还要解决部分输出是否可展示、完整结果校验、取消和落库一致性。
