# 09 前端架构：展示、缓存与服务端事实

## 1. 页面如何对应面试过程

App 使用 React Router 组织简历、配置、计划、正式面试、评估和记录页面。每个页面有对应 services、types 与 hooks。不要沿用旧笔记中“所有页面仍堆在一个 App.tsx”的当前架构描述。

页面负责渲染和交互；services 负责 HTTP；hooks 管理查询、mutation 和缓存；types 描述接口结构；utils 处理打字、评分展示和练习卡片等转换。

这种拆分让页面不必直接处理每个请求细节，但类型定义不会在运行时自动验证服务端数据。API 契约变化仍需联调。

## 2. 服务端数据与临时交互分开

会话详情、计划版本、报告属于服务端事实，放在查询缓存中；输入框、弹窗和当前打字片段属于本地交互。若把两者混在一个大对象里，刷新、重试与流事件很容易互相覆盖。

useInterviewLive 的查询键包含 sessionId，避免不同会话共用同一个缓存条目。查询在处理回复时约每 2 秒刷新，active 常态约每 15 秒刷新，并在窗口重新聚焦时重新读取。轮询是状态对齐手段，不代表模型每两秒产生一个结果。

## 3. 一次发送怎样呈现

用户提交回答后，页面应显示处理中、限制重复操作；services 通过 fetch POST 发送答案与 Bearer token；解析 SSE 事件，将 delta 交给展示逻辑；完整消息结束或重新查询后，以服务端持久消息对齐最终结果。

当前接口在完整计算后才开始发送流，因此“处理中”的反馈很重要。不能把尚未收到 delta 当成连接必然失效，也不能把 message_start 当成模型刚开始思考。

## 4. SSE 解析为何需要缓冲

网络读取的一块字节不对应一个业务事件。一个事件可能被拆成多次读取，多个事件也可能合在一次读取。client.ts 使用 TextDecoder 流式解码并保留 buffer，再按空行切分事件，避免中文 UTF-8 字节分割与半包直接解析。

当前解析器针对后端约定的 event 与单行 data 格式，不是完整通用 SSE 实现。多行 data、不同换行方式、尾部未终止事件等情况，若协议扩展需要增加针对性验证。不能因为使用了 TextDecoder 就宣称所有边界都覆盖。

## 5. 请求失败后怎样判断

HTTP 失败发生在流建立前，使用普通错误响应；流过程中还可能收到 error 事件；连接直接中断则未必有业务错误事件。前端必须避免把三者都呈现成“回答没有保存，请重发”。

教学情境：后端已落库但浏览器断网，用户重连后应该先读会话。如果助手消息已经存在，就恢复展示；若显示处理中，继续观察；若只存了用户消息且处理失败，应根据明确重试语义处理。当前缺少请求幂等键，因此不能承诺自动重试一定不重复。

## 6. 倒计时与评分展示

后端维护截止时间与结束时剩余时间快照。浏览器倒计时是展示，用户修改系统时间或刷新不应成为业务结束的唯一依据。面试结束后还在持续减少的倒计时会让报告像仍在进行，冻结快照用于避免这种误导。

评分展示要区分 null 与零分、部分评分覆盖与完整考察、验证状态与表现高低。练习卡片来自不同报告结构，统一转换应避免重复或矛盾文案，而不是在页面里随意拼接。

## 7. 验证重点

至少演练刷新计划页、重复点击开始、提交后切换页面、流中断、报告空分、学习对比没有历史场次、失效登录和窄屏长文本。前端 build 验证类型和打包，不能代替交互验证。
