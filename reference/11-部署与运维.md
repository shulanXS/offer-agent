# 11 部署与运维：从本地可运行到可交付

## 1. 当前到底具备什么

仓库提供前后端源码、依赖清单、启动脚本、环境示例、数据库初始化和健康接口。当前未找到 Dockerfile 或编排配置，因此删除旧笔记中可直接使用的 docker build／run 示例。也没有据此确认正式生产部署、域名、自动发布、监控告警或备份恢复演练已经完成。

本章把本地复现与上线建议分开。启动成功证明进程在运行，不能证明真实模型、持久化和整个面试闭环都可用。

## 2. 本地复现顺序

在 WSL 项目目录中，先为 backend 建立虚拟环境并安装 requirements.txt，再由 `.env.example` 准备 backend/.env，配置实际 Provider、模型与对应 Key，然后运行 backend/start.sh。前端安装 package-lock 对应依赖后运行 npm run dev。

默认前端 5173、后端 8000，开发时 Vite 代理 `/api`。`/healthz` 返回应用状态；随后还需要实际登录、上传脱敏简历、生成计划、回答、结束、评估，才能验证业务依赖。

不要沿用旧笔记给出的统一 Node 18 下限。当前锁文件中 Vite 的 engines.node 为 `^20.19.0 || >=22.12.0`；选择满足这一范围及其他依赖要求的 Node 环境。后续升级依赖时重新核对锁文件与安装输出。

## 3. 配置为什么可能“设了却没生效”

Settings 自定义来源，当前读取显式初始化、backend/.env 和 secrets，省略普通 env_settings。因此不能假设 shell 中 export 或容器 `-e` 的业务配置一定覆盖 `.env`。部署时必须按实际加载规则验证。

关键字段包括 LLM_PROVIDER、LLM_MODEL、Provider 对应密钥、DATABASE_PATH、JWT_SECRET、CORS_ORIGINS。数据库默认位于 backend/data/offer_agent.db。DATA_DIR 是代码中的路径常量，不是旧文档所称的通用环境覆盖入口；JWT_SECRET_KEY 也不是当前 jwt_secret 的正确命名。

不在笔记中复制真实 Key、令牌、用户原文或默认签名密钥值。启动日志可检查 Provider、模型、base URL 和 has_key，不需要打印密钥。

## 4. 单机上线的一套可审查方案（建议，未交付）

前端构建静态文件并由 Web 服务器提供；同域 `/api` 代理到后端，`/healthz` 单独配置探测；前端路由需要回退到入口页面。后端使用稳定进程管理，关闭开发 reload，确认运行用户、工作目录和依赖版本。

SQLite、Milvus Lite 索引和必要日志放在持久目录，不能随着替换应用目录消失。配置明确的数据库路径；密钥通过受控配置提供，同时核对当前 Settings 加载行为。开放服务前替换默认 JWT_SECRET，并限定 CORS 到实际前端来源。

这些步骤是部署设计，不表示仓库已有对应配置文件。若需要 Docker，需要另行编写、构建和验证镜像及持久卷。

## 5. SSE 代理的两个时间段

回复有“模型处理但流尚未开始”和“结果分块发送”两个阶段。代理超时应覆盖前者的长等待；禁用响应缓冲影响后者的分块展示。仅添加 X-Accel-Buffering 不保证代理所有配置都正确。

客户端断开也不一定取消 `to_thread` 中的同步计算。应重新查询状态确认结果，不能把连接生命周期当作任务生命周期。

## 6. 日志怎样用于排查

按 trace_id、session_id、operation_name 定位规划、抽取、决策、话术和评估。先查哪个阶段失败或变慢，再看降级原因与最终持久状态。当前 trace_id 是应用日志关联字段，不是完整分布式 trace。

日志调用包含简历文本与业务载荷，生产前需要检查脱敏、截断、访问权限和保留策略。配置中的 payload 长度限制也应核对实际行为。避免为了方便调试把候选人原文长期暴露在普通日志中。

## 7. 备份与回滚要恢复什么

仅回滚代码可能无法读取已经升级的 JSON 或表结构。上线前应记录应用版本、schema 变更与数据兼容策略；备份 SQLite 要使用一致性方法，不能假设在写入过程中随手复制就一定完整。索引可重建时仍需保留知识文件和 embedding 配置。

恢复演练应在独立路径还原备份，验证用户、简历、会话、消息、计划引用和报告。没有实际做过恢复，就只能说“设计了备份方案”，不能说“验证过可恢复”。

## 8. 发布验收与容量

推荐验收一份脱敏简历的完整闭环，检查刷新、断流恢复、额度、报告和日志，再做代表性并发测试。观察各阶段耗时分布、模型失败与降级比例、数据库锁等待、线程占用和内存。

当前没有可靠容量或 SLA 数据。先测量再谈扩容：若瓶颈是模型串行耗时，换数据库作用有限；若问题是任务可靠性，可能需要后台任务与幂等；若多实例写入冲突明显，再评估数据库与存储架构。
