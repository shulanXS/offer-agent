# 16 完整案例推演：从一段简历到一份报告

本章全部输入、主题和回答均为教学构造，用于把前面章节串起来。模型真实输出不保证相同；本章不冒充运行日志。为控制篇幅，深入展开一个主题，其余主题只说明它们在全场中的位置。

## 1. 原始需求如何进入系统

候选人上传简历：“开发一个订单练习系统，负责库存扣减接口，使用 Redis 和 Lua 检查并减少库存，订单信息保存到关系数据库。”目标为后端岗位，技术语言选择 Java，JD 关注并发控制、数据一致性和故障排查。

解析阶段应保留原始文本，再提取项目、技能和亮点。这里出现的 Redis 与 Lua 是待验证的简历说法，不能直接形成评估中的正向证据。JD 同样只是考察参考，不是候选人已经符合要求的证明。

用户还选择“加强项目实践”。服务校验简历存在且属于本人、配置枚举合法、文本达到最低要求，再创建 planning 会话。创建流程随即调用生成，不是把任务丢进一个当前不存在的后台队列。

## 2. 计划生成怎样把材料变成考察目标

若启用岗位 RAG，规划上下文会补充后端岗位知识。即使命中库存相关材料，它也只辅助“应该问什么”，不会替候选人证明“已经做对”。RAG 失败时规划仍可继续。

内部计划可以包含项目实践、技术基础、系统设计、故障排查等四至五个主题，实际维度必须满足所选面试类型的校验要求。教学中重点展开一个“库存方案实践”主题：目标是辨别个人贡献、Redis 内原子性与跨存储一致性；开场题要求说明场景、职责与关键实现；追问策略围绕缺失信号展开。

为便于阅读，本章用“个人贡献”“原子扣减”“跨系统一致性”作为信号简称。真实字段须以实际计划为准，不能在已有会话中随意改名，否则旧证据与信号对不上。

计划校验关注结构和约束：主题数、必考数、唯一 ID、维度、时间、字段以及摘要安全。通过校验表示计划可执行，不表示每一道题都是最优选择。

## 3. 为什么要把内部计划与用户预览分开

预览告诉候选人本场侧重项目实践和一致性，列出主题与预计时间，不把完整开场题和所有评价标准直接展开。用户可以判断方向是否符合练习目标，同时保留正式问答的即时性。

如果用户要求更贴合 JD，重生成会引用上一版摘要与明确策略，产生新版本并检查有效差异。若只改变措辞，没有实质调整，不应视为成功满足要求。

确认后，会话记录引用确定的 plan_id。下一次回答和最终报告都读取该版本。不能在面试过程中为了让报告看起来完整，事后给计划补上候选人恰好说过的考点。

## 4. 开始正式面试

激活检查确认状态与额度，初始化当前主题、计数和空工作记忆，写开场消息并进入 active。实际倒计时在进入正式详情或首次回答等启动时钟的路径上开始，避免只在计划页激活后空耗时间。

教学开场：“请介绍库存扣减这一部分，你负责什么，为什么使用 Redis 与 Lua？”这只是示意，不是固定模板原文。

此时有三件不同的事：计划存在，助手已经提问，候选人还没有提供证据。不要提前给任何主题一个高分。

## 5. 第一轮：有实现，但信息不完整

候选人回答：“扣减接口是我写的。我把检查库存和扣减放在 Lua 脚本里，避免多个请求分别检查后都认为库存足够。”

服务先保存用户消息，meta 关联当前主题。ingest 将总轮数与主题轮数从 0 增至 1。边界允许继续，抽取器尝试提取两类信息：个人工作与 Redis 内原子性。假设两项都提供了来自本轮的合法引语、正确匹配信号，且强度达到覆盖阈值，它们会进入工作记忆。

| 数据位置 | 本轮后应怎样理解 |
|---|---|
| messages | 保留候选人完整回答与主题归属 |
| working_memory.evidence | 可能存在两条经过校验的原话证据 |
| missing_information | 跨系统一致性等尚未获得依据的信号 |
| current_topic_round | 已回答一次 |
| current_topic_probe_count | 在生成追问后增加 |

Decide 可以选择追问风险，期望了解 Redis 成功、数据库失败时怎么办。Act 生成自然语言：“如果 Redis 已扣减，但订单没有写入数据库，你会怎么处理？”系统不应因为第一轮说得流畅就自动标记全部目标已验证。

## 6. 第二轮：发现设计边界

候选人回答：“这版只验证了 Redis 内扣减，数据库失败时还没有补偿机制。我目前只记录失败日志，准备增加订单状态和补偿任务。”

这段回答同时包含一个明确不足和一个未来方案。抽取时要区分：已实现的是日志；未实现的是补偿。不能把“准备增加”抽成已经落地的工程成果。

如果模型与校验得到有效证据，跨系统一致性这一信号可能被视为已经考察，但极性可以是负向或中性。这说明 covered 与 positive 不同。Decide 可能继续问如何设计补偿，也可能认为本主题信息足够而切题；是否继续仍受追问次数、轮数与时间约束。

报告合理的表达应类似“能解释 Redis 内原子性，但当前实现尚未闭合跨存储失败恢复”。不能写成“已实现最终一致性”，也不应直接泛化为“完全不懂一致性”。

## 7. 第三轮：边界与证据发生冲突

假设系统第二轮继续追问，候选人第三次回答提出幂等补偿与对账方案。ingest 先把主题回答轮数增加到 3，然后边界判断触发单主题上限，直接进入推进路径。

当前代码下，这一轮可能没有进入 extract_evidence。原话已经保存在 messages，主题摘要也可能包含相关信息，但工作记忆不自动得到同等的结构化新证据。

这就是一个可由执行顺序推导出的业务缺口：报告可能知道这轮对话存在，却仍以旧证据评分。排查不能只看“消息是否保存”，还要看“本轮是否经过抽取和合并”。改进时可以让停止提问与提取最后回答分开处理，或补偿抽取；同时考虑到期场景下的耗时预算与任务可靠性。

本章没有假装这个缺口已经修复，也不把第三轮的未来方案当成候选人真实做过的系统。

## 8. 切题之后，全场上下文如何延续

完成当前主题后，系统保存主题摘要、记录 completed_topic_ids，切到下一主题，清零本主题轮数与追问次数，继续保留工作记忆和持久消息。

之后的题目仍围绕确认计划推进。前面库存主题的信息可通过摘要提供背景，但不应让下一主题的回答被错误归到库存主题。topic_id 是后续证据与引用正确连接的重要条件。

用户刷新页面后，前端从服务端查询当前状态和消息，不靠浏览器中还没消失的半句文本判断进度。若刷新发生在回复处理中，还需要等待或按服务端结果恢复展示。

## 9. 报告怎样生成，不强行填出具体分数

结束进入 evaluating 后，评估服务读取确认计划、运行态与主题消息，投影各主题证据。规则为每个主题生成验证状态与分数，再聚合总分与覆盖。

本案例没有给出完整 evidence 的 strength、polarity 与全部主题输入，所以不能凭几段自然语言编造一个精确报告分数。应先确定输入，再按公式计算。第 06 章的 3 分、4 分换算 70 是独立的算术示例，不是本案例实际结果。

合理报告必须保留以下边界：某些能力有证据，某些仍不足；正向实现与已承认的不足并存；计划未充分考察的方向不给假分；第三轮证据遗漏会影响完整性；模型叙事不能把未来设想改成已实现成绩。

## 10. 从报告回到下一次练习

如果这场满足有效学习条件，outcome 写入并参与同用户、同简历、同岗位和同面试类型的档案汇总。一次不足不一定已经构成“重复薄弱信号”；需要按实际聚合规则和场次数据判断。

下一次练习可以优先补充失败恢复、幂等与对账的表达，但是否由用户选择重点，或由系统自动影响生成，需要核对当前调用链。不能仅因页面展示建议，就声称自动自适应规划已经完整实现。

## 11. 你应该能够独立还原什么

合上本章，自己重画八个对象的关系：用户、简历、配置、计划版本、会话状态、消息、工作记忆、报告与档案。解释为什么第二轮的负向证据可以覆盖信号，为什么第三轮原话存在仍可能没有影响评分，以及为什么断流后应先查询结果。

能够完成这些推演，就开始具备围绕同一项目连续回答需求、设计、实现、故障、测试与改进的能力。之后用第 15 章的真实演练记录，替换本章教学输入，形成属于自己的可核查项目材料。
