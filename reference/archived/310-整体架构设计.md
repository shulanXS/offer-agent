# 整体架构设计

目录路径：实战项目 / AI面试智能体 / 项目全景 / 整体架构设计

[原页面](https://acn2lw4rwc26.feishu.cn/wiki/TsJ8wirVNiwQEBkqKefcXgvpnHh)

整个系统分为前端和后端两部分。前端是你在浏览器里看到的界面，后端负责处理所有的逻辑——解析简历、调用 AI、存储数据。两者通过网络接口通信，互相独立，这种方式叫前后端分离，是目前主流的 Web 应用架构。

#### 整体架构图：

![页面图片](../assets/310-d0f3d7814603c8df.png)

整体数据流转逻辑清晰：

1. 用户在浏览器执行操作，前端发起 HTTP 请求。

2. 请求抵达 FastAPI 路由层，完成参数校验后调用服务层。

3. 服务层统筹处理业务逻辑，按需调用 LangGraph 工作流与数据库。

4. 处理结果逐层回传，最终由前端完成页面渲染。

5. 流式输出场景：服务层通过 SSE 协议，将大模型输出内容逐段实时推送给前端。

#### 前端是怎么工作的

前端是一个单页应用（SPA）。所谓单页，就是整个网站只有一个 HTML 文件，页面的切换不是跳转到新页面，而是 JavaScript 在原地替换内容。这样用户体验更流畅，不会有白屏闪烁。

你在界面上看到的内容，本质上是五个视图在切换：

#### 后端五层架构的职责分工

后端用 FastAPI 框架写成，按职责分成五层，每层只做自己该做的事，互不越界。这种分层方式是后端开发的常见实践，好处是改一层不会影响其他层。

1. 路由层（api/routes）

只处理 HTTP 协议相关的事情。解析请求参数，调用对应的 service 函数，把结果序列化成 HTTP 响应。路由层不包含任何业务判断逻辑。

2. 服务层（services）

业务逻辑的主场。协调简历解析、面试状态流转、配额扣减等模块，决定"下一步做什么"。服务层通过 db/store 读写数据，通过 agent/workflow 调用 LangGraph，但不直接操作数据库 SQL，也不知道 HTTP 层的存在。

3. AI 工作流层（agent/workflow）

专注 LangGraph 图的定义和执行。三个 graph 分别处理三类任务：

- plan_graph 解析简历生成题目

- interview_graph 处理每轮对话和追问判断

- evaluation_graph 生成评分报告

这一层不知道它的结果会怎么被使用，只负责执行 AI 工作流并返回结果。

4. 模型层（llm/factory）

多 provider 的适配层。工厂函数根据 LLM_PROVIDER 配置返回对应的 LLM 实例，上层代码用统一接口调用，不感知具体是 OpenAI 还是 Claude。这一层还提供了 JSON 提取工具函数，处理 LLM 输出不稳定的问题。

5. 存储层（db/store）：

系统用两个本地文件存储所有数据，不依赖任何外部数据库服务：

#### 目录结构

````
offer-agent/
├── backend/
│   ├── knowledge/
│   │   └── roles/
│   │       ├── backend_engineer.md  # 后端工程师岗位知识（JD/技能/常见题/考察维度）
│   │       ├── frontend_engineer.md # 前端工程师岗位知识
│   │       └── product_manager.md   # 产品经理岗位知识
│   ├── scripts/
│   │   └── index_role_knowledge.py  # 离线构建Milvus Lite向量索引
│   ├── app/
│   │   ├── api/
│   │   │   └── routes/
│   │   │       ├── auth.py          # 认证路由：注册、登录、获取当前用户
│   │   │       ├── resumes.py       # 简历路由：上传、列表、删除
│   │   │       └── interviews.py    # 面试路由：创建、激活、回答、评分
│   │   ├── services/
│   │   │   ├── auth_service.py      # 用户注册登录、JWT签发与验证
│   │   │   ├── resume_service.py    # 文件解析、LLM结构化提取
│   │   │   └── interview_service.py # 面试全流程编排、SSE流式输出
│   │   ├── agent/
│   │   │   └── workflow.py          # 三个LangGraph graph定义 + CvInterviewWorkflow类
│   │   ├── llm/
│   │   │   └── factory.py           # LLM provider工厂、JSON提取工具函数
│   │   ├── rag/
│   │   │   ├── embeddings.py        # EmbeddingService：本地hash或OpenAI两种实现
│   │   │   ├── indexer.py           # Markdown解析、离线建索引逻辑
│   │   │   ├── milvus_store.py      # MilvusLiteStore：向量写入与检索
│   │   │   ├── schemas.py           # RoleProfile、KnowledgeChunk等数据模型
│   │   │   └── service.py           # PlanningRAGService：检索入口
│   │   ├── db/
│   │   │   └── store.py             # SQLite建表、增删改查操作
│   │   └── core/
│   │       ├── config.py            # pydantic-settings配置管理
│   │       ├── security.py          # JWT编解码
│   │       ├── streaming.py         # SSE格式化、stream_text生成器
│   │       ├── errors.py            # ErrorCode枚举、AppError异常类
│   │       └── logging_utils.py     # trace_id日志工具
│   ├── main.py                      # FastAPI应用入口、路由注册、异常处理器注册
│   └── .env.example                 # 环境变量模板
│   └── LLM_README.md                 # 大模型配置说明
│   └── RAG_README.md                 # RAG 配置说明
└── frontend/
    ├── src/
    │   ├── App.tsx                  # 主应用，包含全部状态机逻辑和视图切换
    │   ├── api.ts                   # 所有API调用、SSE消费函数
    │   └── main.tsx                 # React挂载入口
    ├── index.html
    └── vite.config.ts               # 开发代理配置（/api → localhost:8000）
````

前端的文件结构相当简洁：3 个核心文件承担了全部工作。App.tsx 包含所有状态和视图切换逻辑，api.ts 封装所有 API 调用，main.tsx 是 React 的挂载入口。没有复杂的目录层级，逻辑集中，方便整体阅读。
