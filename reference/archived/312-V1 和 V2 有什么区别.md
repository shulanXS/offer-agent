# V1 和 V2 有什么区别

[原页面](https://acn2lw4rwc26.feishu.cn/wiki/UJoJwd5FbiGUoekkGrkcRrPhnEZ)

V1 系列把 offer-agent 从零跑通了。登录、简历上传、生成 4 道题、追问一次、最后出评分报告——整条链路是通的，代码也不复杂。

但如果你真的用它练过面试，就会发现一些问题。严格来说，这是问题不是 bug，而是设计上的天花板。

#### V1 到底哪里不够用

第一个问题：题目和简历的关联是浅的。

V1 的出题逻辑是：提取简历关键词，匹配岗位方向，生成 4 道题。这个过程不了解候选人有哪些薄弱点，也不区分你是校招应届生还是有五年经验的社招候选人。结果就是每次面试出的题型差不多，练几次之后感觉在反复刷同样的题。

第二个问题：面试官不像面试官，像脚本。

每道题固定追问一次，追问完就切下一题。不管候选人回答得好不好、说到没说到考察点、有没有值得深挖的地方，都是这个节奏。真实面试里，面试官会根据你的回答决定是继续追问、换个角度、还是直接切题。V1 的设计把这个动态过程变成了走固定流程。

第三个问题：候选人对这场面试考什么没有感知。

用户点"创建面试"，系统开始出题，直接进入对话。候选人不知道这场面试会考哪些方向，是否有自己特别想练的点，完全被动。V1 在第 1 篇讨论过 preparing 状态，让用户能看到题目标题再确认开始。V2 要做的是更进一步：在面试开始前，让候选人看到完整的考察计划，并且有机会调整。

第四个问题：评分说不清依据。

V1 的评分是拿全部对话记录一次性喂给 LLM，让它打分。LLM 返回一个总分和几行评语。这个过程缺乏结构性——评分的依据是什么、候选人哪句话被作为证据、哪个考察点完全没有覆盖，都不清楚。候选人看完报告不知道具体要改哪里。

这四个问题加在一起，指向同一个根本局限：V1 是一个走流程的系统，不是一个会思考的面试官。

#### V2 的四个产品决策

针对这四个问题，V2 做了对应的产品决策。

决策一：先生成计划，候选人确认后才开始。

面试开始前，系统根据简历、目标岗位、校招或社招类型、可选 JD，生成一份 45 分钟的考察计划。计划包含 4 到 5 个考察方向、是否必考、每个方向的参考摘要。候选人可以预览这份计划，选择调整方向重新生成，确认后锁定，然后才正式开始面试。

这个设计解决了两个问题：候选人知道这场考什么，系统也有了一份明确的执行依据。

决策二：面试官动态决策，但有明确边界。

面试 Agent 每收到一个回答，都要先判断：当前主题还缺哪些关键信息？候选人这轮回答有没有值得深挖的点？是继续追问，还是换下一个主题？

这个判断过程不是写死的规则，而是 Agent 根据计划和上下文做的结构化决策。但有一点是硬约束：面试总时长 45 分钟、单主题最多追问 2 次、整场最多回答 12 轮，这些边界由代码强制执行，不交给 LLM 判断。

决策三：面试过程持续记录候选人说了什么。

每轮回答之后，系统会提取候选人说了什么、验证了哪些信息、哪些信号还缺失。这些信息以结构化的方式累积在工作记忆里，而不是仅仅堆在消息列表里。切换主题时，前一个主题的关键信息被压缩成摘要保留，不会随着对话窗口的滑动丢失。

决策四：评分必须有证据，没有证据不给确定分数。

Evaluation Agent 不直接重读全部聊天记录打分，而是消费面试过程中提取的结构化证据。每项能力的得分必须引用候选人的原话，每个引用必须在对话记录里能找到。如果某个考察方向根本没有充分讨论，状态是"未验证"，不会直接给低分。

#### V2 的核心原则：LLM-first

V1 有一个实用的设计：双路径架构。配置了 API Key 就走真实 LLM，没有 Key 就走本地规则，系统照样能运行。这个设计对开发和演示很有帮助。

V2 移除了这个 mock 模式。

原因是双路径在 V2 行不通了。规划 Agent 要根据简历和 JD 生成个性化的考察方向，面试 Agent 要根据回答动态决策，这些能力本质上依赖 LLM，无法用本地规则等价替代。如果要给这些 Agent 写规则路径，实际上是在用规则模拟 LLM 的专业判断，代价很高，意义也不大。

V2 的原则是 LLM-first：真实 LLM 是产品的主路径，也是能力验收的标准。LLM 失败时，系统走规则降级或模板降级，保证流程不中断，但降级路径只负责"结构合法，流程可继续"，不要求复现 LLM 的专业能力。

这个转变意味着 V2 必须配置有效的 API Key 才能跑主路径。它不再是一个"什么都能跑"的演示工具，而是一个以真实 LLM 为核心的面试练习系统。
