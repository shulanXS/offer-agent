# 为什么是 SQLite、LangGraph、Milvus Lite？

目录路径：实战项目 / AI面试智能体 / 技术选型决策 / 为什么是 SQLite、LangGraph、Milvus Lite？

[原页面](https://acn2lw4rwc26.feishu.cn/wiki/R2SfwaAl7iLgDvkbYQjcNCy1nzg)

为了支撑 AI 面试场景下的数据存储、流程编排与知识检索能力，本项目引入了三项技术：SQLite、LangGraph 与 Milvus Lite。接下来我们逐一分析各项技术的选型原因、适用场景、优势与局限。

#### 为什么选 SQLite

在 offer-agent 项目中，我们需要持久化存储大量业务数据，包括用户账号信息、简历解析内容以及最终的评分报告等。面对常见的数据库选型，比如 MySQL、PostgreSQL 等，我们最终选择了更轻量的 SQLite，核心原因非常直接：快速启动，零配置门槛。

![页面图片](../assets/315-44e5c3d9035a3f01.png)

SQLite 是嵌入式数据库，整个数据库就是一个文件。不需要安装 MySQL 或者 PostgreSQL，不需要启动数据库服务，只要 Python 环境里有标准库就能用。

对于一个学习项目来说，这个选择降低了门槛。clone 代码下来，配一个 .env 文件就能跑，不需要先装 Docker、跑数据库容器、配置连接参数这些前置步骤。 数据存在 ./data/offer_agent.db，开发时可以直接用 SQLite 命令行打开查看：

````
sqlite3 ./data/offer_agent.db "SELECT * FROM users;"
````

##### 适合什么场景

SQLite 适合单进程、数据量小的应用。offer-agent 正好符合这个定位：一个进程处理请求，预期用户量不大，没有复杂的联表查询需求。

它的局限也很清楚：不支持高并发写入，多个进程同时写同一个数据库会锁死。如果以后用户量涨到需要多实例部署，就得换成 MySQL 这类支持并发的数据库。

##### 迁移成本低

即便后续从 SQLite 迁移至 MySQL，改动也仅集中在数据访问层。项目业务代码均基于抽象的增删改查接口开发，迁移时只需重新实现数据层逻辑，上层业务代码基本无需调整。

整体迁移成本可控，这也是常用的项目落地思路：MVP 阶段借助 SQLite 快速完成功能验证，业务规模扩大后再平滑切换至 MySQL。

#### 为什么选 LangGraph

本项目是典型的多轮有状态 AI 面试对话场景。完整面试流程包含出题、实时追问、进度更新、最终评估等多个环节，每一步执行逻辑都高度依赖上一轮的对话状态。系统需要根据用户回答动态判断下一步行为：继续追问、跳转下一题或结束面试。

如果采用硬编码的方式维护流程状态，会导致逻辑混乱、分支臃肿、难以迭代。因此，项目必须引入专业的 AI 工作流编排框架，统一管理状态流转与分支逻辑。

##### 主流 AI 工作流方案对比

目前 LLM 应用开发主要分为两大类编排方案：线性链式框架和图状态机框架。

###### 1.
线性链式方案（代表：LangChain）

这类框架以直线执行链路为核心，典型流程是固定的：输入 → 大模型处理 → 输出。优点是开发简单、上手快，适合一次性、流程确定、分支较少的通用问答或文本转换场景。缺点在于：不擅长表达循环与复杂条件分支，跨步骤的状态管理也需要额外设计。

###### 2.
图状态机方案（代表：LangGraph）

这类框架基于状态机 + 图节点流转设计，面向复杂 LLM 业务流程。它通过 State 统一管理流程上下文，通过 Node 拆分独立业务步骤，通过 Edge（含条件边）描述分支与循环流转。因此更适合多轮对话、动态决策、步骤复杂、强依赖历史上下文的场景。

![页面图片](../assets/315-9752be741da2d7e6.png)

##### 最终选型：LangGraph

结合本项目 AI 面试的复杂交互特性，线性链式方案无法满足需求，因此我们最终选用 LangGraph 作为核心编排框架。

它通过三大核心概念完美适配面试业务：

- State（全局状态）：统一存储面试进度、题目信息、历史对话、评分数据，保证每轮交互状态连贯一致；

- Node（执行节点）：将出题、作答判断、追问、评分等逻辑拆分为独立节点，代码解耦、清晰可控；

- Edge（流转边）：支持根据用户回答动态分支决策，实现追问、换题、结束面试的智能流转。

整体来看，LangGraph 完美解决了传统线性框架无法处理的多步骤、有状态、可分支、可循环的面试工作流，是本项目最适配的技术方案。

#### 为什么选 Milvus Lite

为了让 AI 出的面试题不空洞、贴合真实岗位，本项目加入了 RAG 知识库检索能力。

简单来说：系统会先根据用户选择的面试岗位，从知识库中捞出该岗位对应的技能要点、考察重点、高频面试题，再把这些专业信息交给大模型参考。这样 AI 就不会只会出通用的“模板题”，而是针对性出题。

而 RAG 功能的核心，就是向量检索。

普通文本无法直接做相似度匹配，所以需要把知识库内容全部转为向量格式并存入向量数据库。用户开启面试时，系统会把当前岗位需求也转为向量，通过算法算出相似度，精准匹配出最贴合的知识点。

##### 主流向量数据库选型

目前常用的向量数据库有很多，比如 Milvus、Qdrant、Chroma、FAISS 等。结合本项目轻量化、易部署、方便后续扩容的需求，我们最终选择了 Milvus 官方的轻量版：Milvus Lite。

选择它主要有两大原因：

第一，部署极其简单。和 SQLite 一样，它不需要单独搭建服务、不用开启后台进程，所有数据都存在一个文件里。仅需一条 pip 命令即可安装使用，零额外环境配置，非常适合本地开发和项目快速启动。

第二，可以无缝升级扩容。Milvus Lite 和企业正式版 Milvus 使用完全一样的代码接口。未来如果项目知识库越来越大、访问量变高，只需要改一行连接地址，就能升级成完整版 Milvus，所有业务代码完全不用改动，迁移成本极低。

##### 双模式 Embedding 向量生成方案

为了让项目既能离线运行，又能支持高精度生产使用，我们配置了两套向量生成方案，随时可以切换：

- 本地哈希向量：纯本地算法实现，不需要联网、不需要密钥，全程离线可用，足够满足日常开发调试；配置示例：

- OpenAI 向量模型：依托官方 text-embedding-3-small 模型，语义匹配更精准、效果更好，适合正式上线使用。

这种双方案设计，保证了项目有无外部网络、有无密钥都能正常跑通核心功能，整体容错性和适配性更强。

#### 小结

三个特有技术各自解决一个问题：

- SQLite 解决了快速启动、零配置的需求，代价是未来可能需要迁移

- LangGraph 解决了有状态、多步骤、需要分支决策的面试对话流程，代价是需要理解图状态机的编程模型

- Milvus Lite 解决了 RAG 知识检索的向量存储需求，代价是需要额外的依赖和索引构建流程
