#### 需求梳理

设计的起点是一个粗糙的想法：做一个 AI 面试官，能根据用户简历出题，能追问，最后给评分。

这个想法有几个核心模糊点：用户的完整操作路径是什么？每一步系统要做什么？用户在哪个环节最可能放弃？

把这些问题直接抛给 AI，提示词大概是这样的：

````
我想做一个 AI 面试练习工具。用户上传简历，
AI 根据简历出4道面试题，用户逐题回答，
AI 可以追问，最后生成评分报告。
请帮我梳理用户的完整操作路径，
找出每个阶段用户需要什么、系统要做什么，
并指出用户最可能在哪个环节流失。
````

AI 将整个使用流程拆分为上传简历、生成题目、确认开始、对话面试、查看报告五大阶段。同时指出了一个关键问题：如果生成题目后直接进入面试，用户发现考察方向不符合预期时，往往会直接退出页面。这类无声流失不仅影响体验，还会白白消耗使用次数，这也成为后续状态机设计的核心出发点。

#### 设计会话状态机

最初的状态设计较简单，只有「进行中」和「已结束」两种状态：用户创建面试、系统出题后直接进入答题。用户无法在正式开答前确认题目方向，和产品里「先对齐预期、再开始模拟」的体验不够贴合。

为此我们新增了一个中间状态 preparing（准备中），最终确定三类会话状态，且状态只能单向流转、无法回退：

1. preparing（准备中）：用户创建面试后，系统先生成题目，页面仅展示题目大致方向与考察重点，不展示完整试题。用户可以选择正式开始面试，也能返回调整，然后重新生成题目；

2. active（进行中）：用户确认开始后，进入正式答题、AI 追问的交互环节；

3. completed（已结束）：面试正常完成，或是用户主动结束，会话都会进入该状态。

完整流转路径：创建面试 → preparing → active → completed；

![页面图片](../assets/318-2452bf63a5ffac32.png)

这一设计把「出题完成」和「正式开答」拆成两步，相当于给用户预留了预览题单、确认方向再开始的环节，更贴近真实面试里「先了解考察范围、再进入问答」的节奏。

#### 功能拆解和权限设计

用户旅程确定之后，下一步是把旅程里的每个环节翻译成具体功能点。

把用户旅程描述给 AI，让它帮忙拆功能清单：

````
以下是用户操作路径：[贴入旅程描述]
请帮我列出每个阶段需要哪些功能，
指出每个功能对应的操作角色（游客/注册用户）。
注意系统里有未登录用户、有配额的用户、配额耗尽的用户三种状态。
````

功能清单里有一个设计决策需要单独说：配额系统。

系统给每个用户初始5次面试机会。为什么是5次？5次足够走完完整流程，也足够测试各种边界情况，数字本身不是关键，关键是要有一个上限。更重要的设计在扣减时机：配额在创建面试阶段扣减，而不是在面试完成时扣减。

原因是：如果等完成再扣，用户可以创建大量面试但不完成，系统资源被消耗但配额不减。在创建时扣减，保证了每次资源消耗都对应一次配额损耗，逻辑更清晰。

扣减使用 SQLite 的两步操作实现逻辑：

````
-- 步骤1：先检查配额是否充足
SELECT quota_remaining FROM users WHERE id = ?;
-- 步骤2：仅当配额 > 0 时扣减
UPDATE users SET quota_remaining = quota_remaining - 1 WHERE quota_remaining > 0;
````

如果查询结果显示 quota_remaining 已经是0，则不执行扣减操作，上层据此判断配额耗尽，返回 INTERVIEW_QUOTA_EXHAUSTED 错误。

权限矩阵根据三种用户状态设计：

| 功能 | 游客 | 注册用户（有配额） | 注册用户（配额耗尽） |
| --- | --- | --- | --- |
| 上传简历 | 否 | 是 | 是 |
| 查看历史记录 | 否 | 是 | 是 |
| 发起新面试 | 否 | 是 | 否 |
| 查看已完成面试 | 否 | 是 | 是 |

配额耗尽的用户仍然保留简历管理和历史查看权限。这个决定来自一个原则：不能因为配额用完就让用户什么都看不了，过去的面试记录是用户的资产，应该永久可查。

这个阶段的产出是功能清单文档，列出了四个模块（简历管理、面试管理、评分报告、用户认证）下的全部功能点和对应角色。

#### 数据建模

功能清单定了，数据模型就可以从功能里推导出来。

把功能清单直接给 AI，让它设计表结构：

````
以下是功能清单：[贴入功能清单]
请帮我设计数据库表结构。
要求说明每个字段的类型、是否必填、含义，
并指出有哪些设计权衡需要注意。
````

通过跟 AI 的沟通，会得到四张核心数据表：users用户表、resumes简历表、interview_sessions面试会话表、messages对话记录表。

#### 接口设计

整体接口围绕用户操作流程设计，一个操作对应一个接口，各司其职且逻辑清晰：

1. 创建面试（POST /api/interviews/stream）

对应「生成题目」。依次扣减配额、调用 workflow 生成题单、创建 preparing 会话，并通过 SSE 返回会话摘要、题目预览和首题流式内容。配额不足时直接报错终止。

2. 开启面试（POST /api/interviews/{id}/activate）

对应「正式开始面试」。将会话从 preparing 切到 active；已结束会话报错，已是 active 则幂等返回。

3. 提交回答（POST /api/interviews/{id}/reply/stream）

接收用户作答，由 AI workflow 决定追问、切换下一题或结束面试；回复内容 SSE 流式输出。流结束后通过 SSE 事件（如 done、evaluation）和消息 kind 告知前端当前状态，不使用 HTTP 响应头传递下一步动作。

4. 结束并评分（POST /api/interviews/{id}/finish）

对应用户主动「结束面试」。系统在服务端生成评分、保存结果，将会话标记为 completed，以 JSON 同步返回（非 SSE）。若用户正常答完所有题目，评分也会在最后一次 reply/stream 中自动触发，无需单独调用 finish。
