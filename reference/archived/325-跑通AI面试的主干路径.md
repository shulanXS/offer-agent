#### 第一步：用 AI 搭建后端骨架

先不要着急写业务逻辑，把目录结构和基础设施交给 AI 来生成。给 AI 的提示词要说清楚技术栈和分层方式，让它生成一个可以直接跑起来的骨架，而不是一堆互不相干的代码片段。

我们使用的核心技术栈：FastAPI + SQLite + LangGraph，并明确要求 AI 按照规范的分层结构生成代码。

给 AI 的参考提示词：

````
帮我用 FastAPI + SQLite + LangGraph 搭建一个 offer-agent 后端骨架。

目录结构如下：
backend/
  app/
    main.py           # FastAPI app 入口，注册路由和 startup 事件
    core/
      config.py       # 配置管理（pydantic-settings，读 .env）
    db/
      store.py        # SQLite 连接和初始化，所有 SQL 操作
    api/
      routes/
        auth.py       # 注册、登录
        resumes.py    # 简历上传、解析
        interviews.py # 面试生命周期
    services/
      resume_service.py
      interview_service.py
    agent/
      workflow.py     # CvInterviewWorkflow 类

要求：
- Python 3.11+
- pydantic-settings 从 .env 读取 API Key、DATABASE_PATH 等配置
````

骨架生成后，我们重点关注配置文件。项目通过 pydantic-settings 管理配置，支持从 .env 文件读取密钥、数据库路径等信息，其中 llm_provider = "mock" 是本篇关键，代表所有大模型调用都使用模拟数据，保证流程能独立跑通。

核心配置代码：

````

````

llm_provider = "mock" 是这篇的关键。后面所有需要调用 LLM 的地方，都先走 mock 分支，等主流程跑通后再换成真实调用。

#### 第二步：实现简历解析 pipeline

简历解析是项目的基础功能，我们将其拆分为文件格式校验、文本内容提取、结构化解析三个环节，让 AI 生成完整的服务逻辑 resume_service.py。

给 AI 的参考提示词：

````
实现 resume_service.py，支持 PDF/DOCX/TXT/MD 四种格式的简历上传和解析。

流程：
1. 检测文件类型（通过扩展名，支持 .pdf/.docx/.txt/.md）
2. 文本提取：PDF 用 pypdf 逐页提取，DOCX 用 python-docx 逐段落拼接
3. 结构化解析：mock 模式用关键词规则提取，真实模式调用 LLM

结构化解析的输出格式（存入 resumes.payload_json）：
{
  "personal_info": "一句话个人信息摘要",
  "highlights": ["亮点标签"],
  "technical_skills": ["技能1", "技能2"],
  "work_experience": [{"name": "公司/经历名", "detail": "内容"}],
  "project_experience": [{"name": "项目名", "detail": "内容"}],
  "resume_text": "提取后的全文"
}
````

##### 关键代码说明

1. 文本提取 PDF 和 DOCX 是最常用的简历格式，我们使用专用库提取纯文本，保证内容完整性：

````
# app/services/resume_service.py（文本提取片段）
from io import BytesIO
from pypdf import PdfReader
from docx import Document

def extract_text_from_pdf(file_bytes: bytes) -> str:
    reader = PdfReader(BytesIO(file_bytes))
    pages = []
    for page in reader.pages:
        text = page.extract_text()
        if text:
            pages.append(text.strip())
    return "\n\n".join(pages)

def extract_text_from_docx(file_bytes: bytes) -> str:
    doc = Document(BytesIO(file_bytes))
    paragraphs = [p.text for p in doc.paragraphs if p.text.strip()]
    return "\n".join(paragraphs)
````

#### 第三步：搭建 LangGraph 工作流骨架

LangGraph 是管理 AI 面试流程的核心，为了避免代码混乱，我们分两步实现：先生成工作流骨架，再填充节点逻辑。

给 AI 的提示词：

````
实现 app/agent/workflow.py，包含以下内容：

1. CvInterviewWorkflow 类，有 4 个方法：
   - bootstrap(payload) -> dict           # 生成 4 道题，返回 opening_message 和 workflow_state
   - reply(workflow_state, user_answer) -> dict  # 生成面试官回复，含 status
   - evaluate(workflow_state) -> dict     # 生成评分报告
   - finish(workflow_state) -> dict       # 收尾并评分

2. 三个 LangGraph：
   - plan_graph：draft_plan 节点 -> pick_opening_question 节点
   - interview_graph：record_answer 节点 -> compose_response 节点
   - evaluation_graph：evaluate 节点

3. mock 模式下各节点返回固定数据，不调用 LLM
````

骨架生成后，我们再单独实现 plan_graph 的完整节点逻辑，直接给 AI 以下提示词：

````
基于已经定义好的 PlanState 类型，实现 plan_graph 的两个节点逻辑：draft_plan 和 pick_opening_question。

要求：
1. draft_plan 节点：
   - 固定返回 4 道模拟面试题，不需要调用 LLM
   - 题目包含 id、title、prompt 三个字段
   - 同时返回 session_title

2. pick_opening_question 节点：
   - 从 questions 中取出第一题
   - 设置 current_question 和 initial_message
   - 用第一道题的 prompt 作为开场消息

3. 最后把两个节点按顺序连成 StateGraph，编译成 plan_graph。
````

按照同样的方式，我们可以继续填充 interview_graph 和 evaluation_graph 的节点逻辑。 至此，LangGraph 工作流骨架 + 节点逻辑全部完成，mock 模式可独立运行，为后续接入真实 LLM 能力打下完整基础。

#### 第四步：实现面试服务，串联全流程

interview_service.py 是连接接口层与工作流的核心胶水层，主要负责三件事：

1. 调用 LangGraph 工作流

LangGraph 的状态是字典格式，需要序列化为 JSON 字符串，存入数据库 workflow_state_json 字段。

````
# app/services/interview_service.py（核心片段）
class InterviewService:
    def start_interview(self, user_id: int, payload: dict) -> dict:
        user = self.store.decrement_quota(user_id)
        if not user:
            raise_app_error(429, ErrorCode.INTERVIEW_QUOTA_EXHAUSTED, "面试额度不足")

        bootstrap = self.workflow.bootstrap(payload)
        session = self.store.create_session(
            user_id=user_id,
            title=bootstrap["title"],
            target_role=payload.get("target_role", ""),
            status=InterviewSessionStatus.PREPARING.value,
            profile=payload,
            workflow_state=bootstrap["workflow_state"],
        )
        assistant_message = self.store.create_message(
            session_id=session["id"],
            role="assistant",
            kind="question",
            content=bootstrap["opening_message"],
        )
        return {"session": session, "assistant_message": assistant_message, "user": user}

    def reply_to_interview(self, user_id: int, session_id: str, answer: str) -> dict:
        session = self.store.get_session(user_id, session_id)
        result = self.workflow.reply(session["workflow_state"], answer)
        self.store.update_session(
            session_id,
            status=result["status"],
            workflow_state=result["workflow_state"],
            evaluation=result.get("evaluation"),
        )
        # ... 写入 user/assistant 消息
````

2. 创建面试时扣减用户配额

在创建面试前优先扣减配额，当前基于 SQLite 单进程部署，采用「先查询、再扣减」的逻辑：

````
def decrement_quota(self, user_id: int) -> dict | None:
    row = conn.execute("SELECT quota_remaining FROM users WHERE id = ?", (user_id,)).fetchone()
    if not row or row["quota_remaining"] <= 0:
        return None
    conn.execute(
        "UPDATE users SET quota_remaining = quota_remaining - 1, updated_at = ? WHERE id = ?",
        (_now(), user_id),)
    conn.commit()
    return self.get_user_by_id(user_id)
````

该逻辑在单进程场景下可以正常使用，但不支持多实例、高并发部署。若后续切换至 MySQL、PostgreSQL 或集群部署，需改为单条条件更新语句，保证并发安全，避免配额被扣成负数。

3. 流式响应

面试相关接口采用 SSE 流式输出，提升用户体验。

````
# app/api/routes/interviews.py（创建面试路由片段）
@router.post("/stream")
async def start_interview_stream(request: StartInterviewRequest, current_user=Depends(get_current_user)):
    result = service.start_interview(current_user["id"], request.model_dump())
    return StreamingResponse(service.stream_created_session(result), media_type="text/event-stream")
````

stream_created_session 会依次推送 session、message_start、delta、message_end、done 事件。

#### 第五步：验证主流程

骨架搭完后，逐步验证每个环节。普通 JSON 接口用 FastAPI 自带的 Swagger UI（/docs）点选即可；两个 SSE 流式接口 Swagger 表现不好，改用 curl。每步确认通过后再进行下一步，出问题时容易定位。

##### 启动服务

在 backend 目录执行：

````
cd backend
./start.sh
````

start.sh 会依次做这些事：

1. 检查虚拟环境：默认使用 backend/.venv，不存在则报错退出（需先 python -m venv .venv 并 pip install -r requirements.txt）。

2. 激活虚拟环境：source .venv/bin/activate。

3. 检查配置文件：默认读取 backend/.env，不存在则提示从 .env.example 复制。

4. 检查 uvicorn：确认依赖已安装。

5. 可选：预热 RAG 索引：若 .env 里 RAG_ENABLED=true，且 Milvus 库文件尚不存在（或设置了 AUTO_INDEX_RAG=true），会先执行 scripts/index_role_knowledge.py 建索引。

6. 启动 API 服务：默认 http://127.0.0.1:8000，开发模式带 --reload（可通过环境变量 HOST、PORT、RELOAD 覆盖）。

##### 接口功能验证

整体分为账号与简历初始化、面试全流程测试两大阶段，操作依次执行，步骤连贯可直接复现。

访问地址：[http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs)

点击页面右上角 Authorize，在 HTTPBearer 输入框中粘贴上一步复制的 token（无需添加 Bearer 前缀），依次点击 Authorize → Close 完成授权。

###### 终端执行：面试全流程测试

Docs 对 SSE 流式响应兼容性较差，统一使用 curl 命令在终端测试；所有流式请求需添加 --no-buffer 参数，保证事件逐条实时输出。

1. 配置身份令牌环境变量

将登录接口获取的 access_token 赋值给环境变量：

````
TOKEN="<此处粘贴登录返回的 access_token>"
````

2. 创建面试会话

````
curl --no-buffer -N -X POST http://127.0.0.1:8000/api/interviews/stream \-H "Authorization: Bearer $TOKEN" \-H "Content-Type: application/json" \-d '{
    "resume_text": "张三\nJava开发工程师\n3年经验\n熟悉Spring Boot",
    "target_role": "后端开发工程师",
    "job_title": "Java开发工程师",
    "language": "Java",
    "difficulty_level": "进阶",
    "technical_skills": ["Java", "Spring Boot", "MySQL"],
    "highlights": ["负责过电商后端系统开发"]
  }'
````

预期结果：终端逐条输出 SSE 事件；event: session 数据中包含会话 id、planned_questions、quota_remaining，后续依次出现 message_start、连续 delta、message_end、done 事件。记录 session.id。

4. 激活面试会话（前置必要操作）

未执行此步骤会导致答题接口返回 409 错误，替换命令中 <session_id> 为上一步记录的会话 ID：

````
curl -X POST "http://127.0.0.1:8000/api/interviews/<session_id>/activate" \-H "Authorization: Bearer $TOKEN"
````

预期结果：返回状态码 200，会话状态为 active，同时返回面试题目、对话消息等数据。

5. 提交答题内容

替换 <session_id>，执行流式答题命令：

````
curl --no-buffer -N -X POST "http://127.0.0.1:8000/api/interviews/<session_id>/reply/stream" \-H "Authorization: Bearer $TOKEN" \-H "Content-Type: application/json" \-d '{"content": "我叫张三，有3年Java开发经验，主要做后端服务。"}'
````

预期结果：终端依次输出 message_start、连续 delta、message_end、done 事件；若为最后一道题目，额外返回 evaluation 事件，done 中状态为 completed。

6. 主动结束面试（可选操作）

正常答完全部题目后，接口会自动评分并结束会话，无需手动调用；如需中途终止面试，替换 <session_id> 执行以下命令：

````
curl -X POST "http://127.0.0.1:8000/api/interviews/<session_id>/finish" \-H "Authorization: Bearer $TOKEN"
````

预期结果：返回状态码 200，包含面试评分、综合评价、优缺点等 evaluation 数据，会话状态为 completed。
