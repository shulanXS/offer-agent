# 整体测试思路

目录路径：实战项目 / AI面试智能体 / V1 版本开发 / 开发主流程 / 整体测试思路

[原页面](https://acn2lw4rwc26.feishu.cn/wiki/VnLgwbxEtiyU23kijZwcFs4EnNb)

Agent 类项目的测试难度远高于常规 Web 项目。一方面大模型（LLM）输出存在不确定性，另一方面系统分层复杂，涵盖接口层、业务逻辑层、LangGraph 状态机、LLM 调用等多个模块，任意一层都可能出现问题。

由于 LLM 无法保证输出内容完全固定，比如同一套提示词，本次返回 4 道面试题、下次可能只返回 3 道，因此测试重点不在于校验文本内容，而是验证业务流程、输出格式、异常处理是否符合设计要求。

多层架构还会带来一个问题：如果等到全部功能开发完毕再统一测试，出现问题后很难定位故障所在层级。下文将介绍循序渐进的测试思路、针对性测试方案、配套使用技巧以及核心校验要点。

#### 推荐分阶段测试流程

切忌等整体开发完成后再集中测试。正确方式是开发一个模块，就验证一个模块，由底向上逐步排查问题。

推荐的测试顺序如下：

![页面图片](../assets/327-de8eb7776da13aad.png)

1. 简历解析模块

上传 PDF、TXT 等格式文件，校验解析后的结构化数据，确认姓名、工作经历、技能等核心字段提取完整、内容准确。

2. 面试计划流程（plan_graph）

传入已解析完成的简历数据，校验生成的面试计划：必须包含 4 道题目，且每道题都完整拥有 title、prompt、focus、follow_up_hint 字段。

3. 单轮追问流程（interview_graph）

传入单道面试题和用户作答内容，检查是否正常触发追问，同时校验追问内容的格式是否规范。

4. 多轮完整答题流程（interview_graph）

走完单题的全部追问环节，验证追问结束后能否自动切换至下一题，以及会话状态标识是否正常更新。

5. 面试评估流程（evaluation_graph）

评估动作会在最后一轮作答 / 流式响应后自动触发，也可以手动结束会话并生成评估。

6. 全链路联调

从创建面试会话开始，依次完成答题、结束会话、生成评估报告，走完整套业务流程，验证端到端运行正常。

全程优先使用 Mock 模式校验业务逻辑，流程跑通后，再切换为真实 LLM 验证输出效果。

#### 针对 LLM 不稳定性的专项测试

LLM 输出常见四类问题，也是测试的核心关注点，对应有明确的测试与优化方案：

![页面图片](../assets/327-fd33946d362939aa.png)

1. 输出夹带多余内容（格式漂移）

现象：要求接口仅返回标准 JSON，但大模型常会额外增加引导话术，或是用 Markdown 代码块包裹内容，甚至将 JSON 穿插在普通文本里。

测试方式：

构造各类非常规格式的文本，检验 _extract_json 函数能否精准提取有效 JSON；遇到空内容、纯文本等无 JSON 场景，需正常返回 None。

````
test_cases = [
    '{"questions": [...]}',                              # 标准格式 → 应解析成功
    '```json\n{"questions": [...]}\n```',              # Markdown 代码块 → 应解析成功
    '以下是面试题：\n{"questions": [...]}',             # 前有说明 → 应解析成功
    '我为你生成了{"questions": [...]}请参考',           # 嵌在段落中 → 应解析成功
    '',                                                  # 空响应 → None
    '抱歉，我无法生成面试题',                             # 无 JSON → None
]
````

如果 _extract_json 执行结果为 None，上层代码捕获异常后，自动切换为本地规则生成逻辑，避免强行解析异常文本导致报错。

2. 原样返回提示词占位内容（echo-back）

现象：返回的 JSON 格式看似正常，但内容全是提示词里的示例占位文本，比如 “最多 4 个考察焦点”“题目标题” 等，并非真实业务数据。

测试方式：

模拟包含占位符的数据包，校验 _looks_like_prompt_template 函数可以准确识别这类异常内容。

````
from app.llm.factory import _looks_like_prompt_template

payload = {
    "focus_points": ["最多4个考察焦点"],
    "questions": [{"title": "题目标题", "prompt": "题目内容"}],
}
assert _looks_like_prompt_template(payload) is True
````

解析出 JSON 后，一旦判定为占位内容，直接视作无效输出，和 JSON 解析失败走同一套降级逻辑，启用规则化生成方案。

3. 字段缺失、题目数量不符（结构不完整）

现象：JSON 能够正常解析，但存在字段缺失问题，例如缺少 follow_up_hint；同时题目数量不稳定，要求固定 4 道题，实际偶尔返回 3 道或 5 道。

测试方式：

第一步：编写结构校验函数，对解析后的内容做完整性检查，可结合真实大模型调用或 Mock 数据测试；

第二步：连续调用 plan_graph 接口 5 至 10 次，统计每次返回的题目数量，复现数量异常问题。

````
def validate_plan(plan: dict):
    assert "questions" in plan
    assert len(plan["questions"]) == 4

    for q in plan["questions"]:
        assert "title" in q
        assert "prompt" in q
        assert "focus" in q
        assert "follow_up_hint" in q
        assert len(q["prompt"]) > 10
````

一旦检测到题目数量异常或关键字段缺失，系统会立刻触发降级，启用本地规则生成逻辑，保障面试流程正常运行。

仅靠优化提示词很难彻底规避这类问题，建议组合多种方案持续优化：

- 在提示词中明确要求：必须生成 4 道题目，questions 数组固定包含 4 个元素；

- 保留代码层校验，作为永久兜底；

- 结合 AI 优化提示词写法，比如改用数字编号罗列题目，同时补充接口重试机制。

4. 数组 / 字段顺序随机变化

现象：同一批内容多次返回时，JSON 对象的字段顺序、题目数组的元素顺序会随机改变。

测试方式：

利用 Mock 构造内容相同、但字段或数组顺序打乱的返回数据，完整执行面试流程，检验业务逻辑能否正常运转。

编码时需要通过字段名和题目唯一 ID读取数据，不要依赖数组下标或固定字段顺序。要明确一点：返回内容顺序随机本身并非问题，因编码不当强依赖顺序才会导致程序出错。

#### 重点校验清单

现阶段项目暂未搭建自动化测试框架，可使用 curl、Postman 手动测试，重点关注以下场景：

1. 会话状态流转

新建会话状态为 preparing；调用激活接口后变为 active；答题完成或手动结束会话后变为 completed。 额外校验：向已结束的会话发起答题，需返回 SESSION_ALREADY_COMPLETED；向未激活的会话发起答题，需返回 SESSION_NOT_ACTIVE。

2. 追问边界逻辑

每道题目仅支持一轮追问，追问完成后标记状态并自动切换下一题，不允许二次追问。

3. 面试配额流程

创建会话前先查询剩余配额；创建成功后配额数值正常减一；配额为 0 时发起创建请求，直接返回 INTERVIEW_QUOTA_EXHAUSTED，禁止创建会话。

4. 错误响应格式

针对 Token 失效、配额不足、会话状态异常等场景测试，确保响应统一包含 code、message、trace_id 字段，且错误码与预期枚举值一致。

5. 简历解析兼容性

使用单页 PDF、多页 PDF、TXT 等不同格式文件测试，保证姓名、工作经历、技能等核心字段稳定提取。

后续项目功能稳定后，可再基于 pytest 搭建自动化测试用例，实现常态化回归校验。
