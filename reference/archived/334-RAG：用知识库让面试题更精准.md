面试智能体的核心在于出题质量。早期仅靠大模型根据简历出题，不接入外部数据，虽能正常使用，但问题突出：模型对各岗位的考察重点把握不稳。

哪怕同为 5 年后端岗位简历，出题方向也飘忽不定，时而偏重算法、时而偏向业务，完全依赖模型原有训练内容。

接入 RAG 后情况明显改善。比如简历提到 “熟悉 Redis”，纯模型只会出数据结构这类基础题；结合知识库后，会结合后端岗位要求，侧重系统设计与高并发场景，例如让设计秒杀库存扣减方案并说明 Redis 的应用环节。前者只是考知识点，后者更贴合真实面试。

#### RAG 在本项目里干什么

RAG（检索增强生成）在本项目的核心作用很简单：先从岗位知识库精准查找专业知识，再把这些知识传给大模型，辅助生成更贴合真实岗位的面试题。

RAG 负责「找专业知识」，大模型负责「结合知识写题目」，两者配置完全独立。

##### 精准介入：只在出题阶段生效

RAG 只在出题这个最需要岗位专业知识的环节工作，既能提升题目质量，又不会让项目架构变复杂。

另外，RAG 默认关闭（RAG_ENABLED=false）。关闭或检索失败时，系统会自动回退到「简历 + 大模型」的原有出题方式 ——RAG 是功能增强，不是必需依赖。

##### 两条数据流：先建立地图

可以把 RAG 理解成两条链路：离线建库和在线检索。

1. 离线建库（启动前做一次）

读取知识库 → 按章节拆分知识块 → 给每个知识块加标签 → 生成向量（二选一：本地哈希/OpenAI） → 写入 Milvus 向量库

![页面图片](../assets/334-7c1abcd259c45a3c.png)

2. 在线检索（用户点击「生成题目」时）

功能开关校验 → 岗位名称统一转换 → 组装检索语句 → 向量检索 → 内容封装并注入出题流程

![页面图片](../assets/334-c4de9a258f3ae6c1.png)

##### 为什么不直接读知识库目录

上面的两条数据流并不简单，除了离线建索引，在线检索时还需要走一遍 Embedding、Milvus、建索引、拼 query 的流程，有人会疑惑：目前知识库只有三个 Markdown 文件，直接让大模型读取目录、加载对应内容出题，不是更简单吗？

这种方式在数据量小的时候确实可行，内容全部放入提示词也不会超限。但项目仍然选择向量检索，不是因为「炫技」，而是把检索和生成拆开，主要出于精准度、成本、运维三方面考量：

1. 出题匹配更精准稳定

向量检索会结合岗位信息、候选人简历技能做匹配，只选取关联性最高的内容出题。如果让模型自行读取整份文件，不仅会浪费令牌，还容易随机选取内容，导致考题风格飘忽。向量检索的结果可控、可复现。

2. 降低开销，规避扩容风险

知识库提前向量化存入 Milvus，线上检索仅毫秒级完成，不消耗大模型算力。一旦后续岗位、文档增多，纯靠模型读文件会出现上下文溢出、随机抽样等问题，稳定性大幅下降。

3. 故障隔离，方便排查与降级

检索独立为单独环节，即便检索失败，也能自动走兜底逻辑，面试流程不受影响。同时检索日志会记录命中片段与匹配分数，考题异常时能快速定位问题；若检索和出题耦合，很难区分故障环节。
