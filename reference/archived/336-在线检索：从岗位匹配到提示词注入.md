#### 检索流程

##### 第一步：功能开关校验

先读取配置 RAG_ENABLED，若为 false，直接返回空内容，RAG 全程不介入，原有出题流程正常运行。

##### 第二步：岗位名称统一转换

Milvus 检索时要用岗位标识 role_slug == 'backend_engineer' 这类固定 ID 过滤，不能直接用用户输入的字符串。问题是用户填的岗位名写法不统一。「后端工程师」「服务端开发工程师」「Java 后端」可能都是后端岗，但字面上完全不同。

这一步的任务，就是把各种写法翻译成系统认得的岗位标识 role_slug。

1. 岗位对照表 ROLE_PROFILES

所有岗位规则统一写在 app/rag/schemas.py 的 ROLE_PROFILES 中，每条配置包含唯一标识、展示名称、别名清单和默认考察方向，别名用于匹配用户输入，且与知识库内 Markdown 文件一一对应。

````
# app/rag/schemas.py（节选）
ROLE_PROFILES = {
    "backend_engineer": RoleProfile(
        slug="backend_engineer",
        display_name="后端开发工程师",
        aliases=("后端开发工程师", "后端工程师", "java后端", "后端研发工程师", "服务端开发工程师"),
        default_focus_points=("系统设计", "数据一致性", "性能优化", "故障排查"),
    ),
    "frontend_engineer": RoleProfile(...),
    "product_manager": RoleProfile(...),
}
````

2. 名称匹配逻辑

系统会拼接前端传入的 target_role 和 job_title 字段，统一转为小写后，和配置里的别名逐一比对。代码示例：

````
def normalize_role(target_role: str = "", job_title: str = "") -> RoleProfile | None:
    raw = f"{target_role} {job_title}".strip().lower()
    if not raw:
        return None
    for profile in ROLE_PROFILES.values():
        if any(alias.lower() in raw for alias in profile.aliases):
            return profile
    return None
````

最终得到匹配结果：

- 匹配成功：使用对应的 role_slug 进入向量库检索；

- 匹配失败：流程不会中断，直接返回空检索内容，后续出题会启用兜底文案，仅依靠岗位名和简历生成题目。

````
# app/agent/workflow.py（节选）
岗位知识库摘要:
{planning_rag_context or '暂无岗位知识库命中，请仅结合岗位名和简历生成题目。'}
````

##### 第三步：组装检索语句

在第二步岗位匹配成功后，我们就能拿到标准化的岗位标识（role_slug）和对应的正式岗位名称（display_name），例如「后端开发工程师」。 接着，系统会结合创建面试时前端传入的各项信息，拼接成用于检索的 query 语句。代码示例：

````
# app/rag/service.py
@staticmethod
def _build_query(
    *,
    role_name: str,
    language: str,
    difficulty_level: str,
    technical_skills: list[str],
    highlights: list[str],
    resume_text: str,
) -> str:
    resume_excerpt = " ".join((resume_text or "").split())[:240]
    return "\n".join(
        [
            f"岗位: {role_name}",
            f"技术语言: {language or '不限'}",
            f"面试难度: {difficulty_level or '入门'}",
            f"简历亮点: {', '.join(highlights[:6]) or '暂无'}",
            f"技术技能: {', '.join(technical_skills[:8]) or '暂无'}",
            f"简历摘要: {resume_excerpt or '暂无'}",
            "检索目标: 岗位JD、必备技能、常见面试题、重点考察维度",
        ]
    )
````

语句最后一行的检索目标是明确的指令提示，告诉 Milvus 优先匹配岗位 JD、必备技能、面试样题和重点考察维度这四类知识块，忽略无关内容。

最终拼出来的文本长这样：

````
岗位: 后端开发工程师
技术语言: Java
面试难度: 进阶
简历亮点: 微服务, Redis, 性能优化
技术技能: Java, Spring, MySQL, Redis
简历摘要: 5年后端经验，负责订单系统重构，引入 Redis 做缓存与限流...
检索目标: 岗位JD、必备技能、常见面试题、重点考察维度
````

这段文本仅用来做向量检索。知识库中的内容在建索引时就已经完成向量化并存储，在线环节只需将拼接好的检索语句转为向量，再到 Milvus 中匹配相似度最高的内容块即可。

##### 第四步：向量检索

检索语句拼好后，进入「向量化 + Milvus 搜索」两步：

1. 把检索语句变成向量

首先将组装好的检索语句转换成向量格式，核心代码如下：

````
# app/rag/service.py（节选）
embedding_service = create_embedding_service()
query_vector = embedding_service.embed_query(query)
````

系统会根据配置 RAG_EMBEDDING_PROVIDER 自动选择向量生成方式：

- local：本地哈希算法，生成 256 维向量，无需外部依赖

- openai：调用 OpenAI 官方接口，生成语义向量

2. 在 Milvus 里搜最相关的 chunk

获取检索向量 query_vector 后，系统会进入 Milvus 执行精准检索，核心逻辑在 app/rag/milvus_store.py 文件中，主要分为两步筛选：

第一次筛选：按岗位过滤，避免跨岗位干扰

先通过 role_slug 严格限定检索范围，只查找当前岗位的知识，再计算向量相似度。

````
# app/rag/milvus_store.py（节选）
search_result = self._client.search(
    collection_name=self.collection_name,
    data=[query_vector],
    filter=f"role_slug == '{role_slug}'",   # 只搜当前岗位，不跨岗
    limit=limit,
    output_fields=["role_slug", "role_name", "doc_type", "section_title", "source_path", "content"],
)
````

举个例子：用户选择后端岗位，role_slug 为 backend_engineer，系统就只会在后端的知识块中匹配，不会检索到产品经理等其他岗位的内容。

第二次筛选：按余弦相似度排序，取最优结果

建索引时已配置 metric_type="COSINE"（余弦相似度），Milvus 会根据向量相似度排序，返回最匹配的结果，并封装成 RetrievedChunk 列表。代码示例：

````
sources = [
  RetrievedChunk(doc_type="jd",        section_title="岗位JD",       ...),
  RetrievedChunk(doc_type="skills",    section_title="必备技能",     ...),
  RetrievedChunk(doc_type="questions", section_title="常见面试题",   ...),
  RetrievedChunk(doc_type="rubric",    section_title="重点考察维度", ...),
]
````

假设面试岗位为后端，简历侧重 Redis 和高并发，top_k=4 时通常会返回：

| doc_type | section_title | 说明 |
| --- | --- | --- |
| jd | 岗位JD | 岗位职责与要求 |
| skills | 必备技能 | Java、数据库、中间件等 |
| questions | 常见面试题 | 样例面试题方向 |
| rubric | 重点考察维度 | 系统设计、一致性等 |

##### 第五步：内容封装并注入出题流程

前四步做完，Milvus 返回的是若干条检索结果对象 RetrievedChunk，每条都包含章节类型与对应正文。

这一步做两件事：先把检索结果整理成大模型可识别的摘要，再将相关数据统一并入面试流程，为后续出题提供支撑。

1. 把 chunk 拼成「岗位知识库摘要」

系统会按照jd → skills → questions → rubric的顺序，对检索到的知识块分类汇总，最终生成文本存入 planning_rag_context。为防止提示词内容超限，这段摘要整体字数控制在 3200 字以内。

2. 生成三类 RAG 数据并持久化

流程最终会产出三组字段，存入流程状态中：

| 字段 | 是否进入提示词 | 含义 |
| --- | --- | --- |
| planning_rag_context | 是 | 检索到的知识摘要 |
| planning_rag_focus_points | 否 | 岗位默认考察方向，来自 RoleProfile，不是检索内容 |
| planning_rag_sources | 否 | 命中 chunk 的来源信息，仅用于日志/debug |

检索完成后，这三组数据会合并进「开始面试」的参数字典，供后续 bootstrap、出题整条链路使用。整个面试周期仅在创建环节执行一次检索，后续追问、切换题目都会直接复用已有数据，不再重复查询 Milvus。

3. 注入提示词，辅助生成面试题

检索结果整个数据流转分为四个环节，层层衔接完成出题：

LLM 实际看到的提示词结构（简化示意）：

````
目标角色、技术语言、难度 …
工作经历、项目经历 …

岗位知识库摘要:          ← 只有知识摘要字段 planning_rag_context 出现在这里
<JD / 技能 / 样例题 / 考察维度 等检索结果>
（若为空则显示：暂无岗位知识库命中，请仅结合岗位名和简历生成题目。）

简历原文: …
请返回 4 道题的 JSON …
````

简单来说，RAG 的作用就是将岗位知识库内容插入到提示词中。大模型会结合候选人简历与岗位考核要点综合出题。这份摘要仅在后端流转，不会展示在前端页面。

##### 重点区分：focus_points 与 RAG 检索内容

这里需要厘清一个容易混淆的点：planning_rag_focus_points 虽然带有聚焦相关字样，但并非检索得到的知识库内容，而是岗位预设的固定考察标签。比如后端岗位默认配置的考察方向：系统设计、数据一致性、性能优化、故障排查。

- planning_rag_context（知识库摘要）：传入大模型提示词，用来告诉模型该岗位常规的考察内容和面试方向；

- planning_rag_focus_points（默认考察标签）：不进入提示词，大模型挂了或 mock 时，用它（加简历亮点）决定本地规则题的考察维度。

两个字段各司其职、互不冲突

##### 降级机制

项目核心设计原则：RAG 功能异常，绝不中断面试创建流程。各类异常场景的系统处理逻辑如下：

| 情况 | 知识摘要 | LLM 出题提示词 | 能否创建面试 |
| --- | --- | --- | --- |
| RAG 未开启（RAG_ENABLED=false） | 空 | 兜底文案，靠简历 + 岗位信息 | 正常 |
| 岗位名无法匹配到已知角色 | 空 | 同上 | 正常 |
| 岗位已识别，检索异常（向量库失败、维度不匹配、Embedding 报错等） | 空 | 同上 | 正常 |
| 岗位已识别，索引未建或检索零命中 | 空 | 同上 | 正常 |
| 检索成功 | 有摘要 | 注入岗位知识库内容 | 正常 |

上表前三行 LLM 出题的提示词只能靠简历 + 岗位信息，是因为知识摘要都为空——对 LLM 来说等于没用 RAG。
