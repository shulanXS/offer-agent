#### 三个 Agent 如何分工又不打架

V1 版方案里，我们用 LangGraph 写了三套流程：出题规划流程、面试对话流程、打分评估流程。但这三套逻辑全都堆在同一个workflow.py文件，靠同一个CvInterviewWorkflow类统一调度。一个类同时要管三套独立运行状态，各个模块该干什么、边界在哪完全分不清，很容易乱套。

到 V2，我们把三套 Agent 拆成三个独立文件夹模块：面试规划、面试对话、面试评分。

V2 目录结构示例：

````
backend/app/agent/
├── interview_planning/      # 规划阶段
│   ├── agent.py             # LLM 调用、重试、降级
│   ├── validator.py         # 结构校验与维度检查
│   ├── templates.py         # 模板降级
│   └── prompts.py           # Prompt 组装
├── interview/               # 对话阶段
│   ├── graph.py             # LangGraph StateGraph
│   ├── decide.py            # 决策 Agent
│   ├── routing.py           # 条件边路由
│   └── nodes/               # 各节点实现
└── interview_evaluation/    # 评估阶段
    ├── agent.py
    ├── validator.py
    └── prompts.py
````

拆分代码本身不难，真正棘手的是怎么让它们配合工作时不互相冲突。我们的解决办法是用一份固定计划 JSON 做统一协议：规划 Agent 生成计划后就固定不变，面试、评分 Agent 只读取、不修改、不重新解读。所有提问都能对应计划里的考点，打分维度和计划考点一一对应，下游只负责执行，没有自主解读的空间。

这样就彻底避免了多 Agent 协同时，因为理解不一致导致整体输出跑偏失控的问题。

#### Planning + HITL：计划可以调整，但不能无限重来

出面试计划看着简单，丢个提示词给大模型就能生成，难就难在平衡：既要让用户能调整、有掌控感，又不能任由他无限刷新乱刷。

要是不限次数，求职者会一直刷，直到考题全是自己熟的，练习根本没效果；但一点不让改，计划不合心意用户直接就不用了。

V2 这边用人工干预加硬性限制来解决：用户最多只能重新生成两次，每次刷新都得说清楚调整方向，比如多加点系统设计题、贴合JD考点，不能毫无理由反复刷。

V2 页面示例：

![页面图片](../assets/338-d017b54e82ca3f3e.png)

等用户确认好最终版本，系统会把这份计划ID存进数据库，后面面试 Agent 只认这份固定计划，再也不能修改。

而且次数限制是代码直接计数管控，到次数就拦截，不靠大模型自己判断。两次机会用完，页面上的重新生成按钮就变灰。

#### ODA 架构：决策和表达必须分开

V1里生成回复的节点一口气干两件事：判断该追问还是换话题，顺便输出面试官话术，两步全塞在一次大模型调用里，只给一段提示词让模型直接出对话。

这么做有个很大的弊端：没法单独校验判断逻辑对不对。你只能看到模型最后说出来的话，完全分不清它是打算追问还是切换考题，更搞不懂这么判断的依据是什么。

V2把这两步拆分开，做成「观察-判断-输出」三段流程：

- 观察层（Observe）：整理全部上下文：当前考察主题、考核要点、候选人刚刚的回答、还有哪些关键信息没问到；

- 判断层（Decide）：读取上面所有内容，输出一份结构清晰的判断结果，写明要执行什么动作、这么选的理由、还需要候选人补充哪些内容；

- 输出层（Act）：不用思考决策，单纯把这份判断转换成口语话术就行。

````
# Decide 输出结构化决策，不生成话术
{
    "action": "probe_depth",
    "reason": "候选人提到了 Redis 缓存，但未说明选型依据",
    "expected_information": ["选型原因", "与其他方案的对比"]
}

# Act 读决策，生成话术
# "你提到用了 Redis，能说说为什么选它而不是其他缓存方案吗？"
````

#### 三层记忆：Agent 如何记住说过什么而不被撑爆

一场面试总共45分钟，候选人会说一大堆话。要是每次调用大模型都把全部聊天记录一股脑塞进去，会出现两个麻烦：一方面白白消耗大量 token，另一方面内容太多，模型很难从一堆历史信息里揪出重点。

V2 分了三层记忆，分别对应三种不同的留存需求：

> 图片尚未保存：[在原页面查看](https://acn2lw4rwc26.feishu.cn/wiki/XymbwVzcXiPL3Lkx6ZfcLQhpnXd)（图片标识：Ch6hbkQYToIoe4x1ndRcPMdTn5c）

1. 短期记忆只保留当前考题的对话记录。组装上下文的时候，只会拉取当下这个主题的聊天内容，别的主题记录一概不带。切换考题之后，之前主题的原始对话会压缩成简短摘要存起来，不再放进提示词传给模型。

2. 中期记忆是整场面试专属的结构化信息。候选人每答完一轮，系统会单独跑一个提取节点，梳理他的核心观点、已经佐证的考察点、还差哪些信息、回答里有没有前后矛盾的地方，全部按固定格式存好。就算切换考题，这些内容也不会丢，既能给判断节点用来针对性追问，后续评分Agent也能直接读取使用。

3. 长期记忆是多场面试汇总的个人练习档案。练过好几次之后，系统会记下他反复答不好、经常缺失的考察要点。现在V2会在评估报告里用到这份长期档案，用来做本场和上一场面试的对比分析。

三层记忆分工清晰、互不掺和。短期记忆不会参与打分流程，长期记忆也不会干扰本场面试的实时判断，三层完全隔离开。

#### 证据驱动的评估：分数要说得清依据

V1 的评估方式是：把全部对话记录一次性给 LLM，让它打分。这有一个根本问题：LLM 每次打分的依据可能不同，同样的对话在不同调用下可能得到差距明显的分数，也没有办法追溯"这个分数是基于哪句话"。

V2 的评估 Agent 不直接读对话历史，它消费的是面试过程中积累的结构化证据。每项能力的评分必须引用候选人的原话，每条引用在对话记录里必须能回溯，没有足够证据的考察方向不给确定分数。

这个设计带来了一个额外的好处：评估维度和计划主题是同一套，不会出现"面试考了系统设计，评分报告里出现一个叫软件工程能力的新维度"这种割裂感。报告里的每一项都能追溯到计划里的哪个考察方向。

> 这五个设计不是孤立的功能，而是紧密咬合的：计划约束面试，面试积累证据，证据支撑评估。后面的模块会逐一展开每个设计背后的工程细节。
