# 整体改造方案

目录路径：实战项目 / AI面试智能体 / V2 版本优化 / 核心方法论 / 改造文档示例 / 整体改造方案

[原页面](https://acn2lw4rwc26.feishu.cn/wiki/RFSOwsZiwiqtCakE8Htc21zhnAf)

#### 1. 文档目的

本文档用于指导 AI 在现有项目基础上，分阶段将旧工作台升级为更专业的 AI 模拟面试官新版工作台。

后续所有新版工作台改造都必须遵循本文档。每次只执行一个阶段或一个明确子任务，完成验证后才能进入下一阶段，避免一次性新增大量代码导致系统不可控。

本文档是新版工作台总体路线图，只维护整体目标、阶段顺序和阶段完成状态。具体功能需求与技术设计应写入对应专题文档。

当专题文档与本文档出现细节冲突时：

1. 产品范围和阶段边界以本文档为准。

2. 专题内部的产品规则、数据结构、接口和验收细节以专题文档为准。

3. 需要改变整体范围或阶段顺序时，才修改本文档。

4. 仅调整某项能力时，只修改对应专题文档。

一次改造必须归属唯一主专题。即使代码变更跨越前端、后端、数据库和 Prompt，也只修改该主专题文档；其他专题只作为依赖读取，不在同一次改造中同步调整。

#### 2. 当前基线

旧工作台已具备：

- JWT 登录和用户额度

- 简历上传、文本提取与结构化解析

- 岗位、技术语言和难度配置

- 根据简历和岗位知识库生成固定面试题

- 固定追问、面试总结和 SSE 流式展示

- SQLite 会话持久化

- React 单页工作台

旧工作台的主要限制：

- 固定生成 4 道题

- 每道题固定追问一次

- 缺少校招与社招差异

- 不支持候选人提供目标岗位 JD

- 出题、追问与评分主要依赖单次 Prompt

- 没有结构化记录候选人证据、风险和未验证信息

- 评估结果缺少能力维度、证据引用和逐题复盘

#### 3. 新版产品目标

新版工作台的产品定位：

> 根据候选人的简历、面试类型、目标岗位和可选 JD，生成一场有明确边界、能够动态追问、并提供可解释复盘的 45 分钟专业模拟面试。

新版工作台必须实现四个核心价值：

1. 针对性：问题需要结合简历、校招或社招类型、目标岗位与可选 JD。

2. 真实性：面试官根据回答动态追问、切换主题和调整难度。

3. 可控性：面试有明确主题、轮数、追问和时间边界，不允许无限运行。

4. 可提升性：评估必须说明依据，并给出可以执行的改进建议。

新版工作台实施采用 LLM-first 原则：

- 真实 LLM 路径是产品主路径，也是专业能力验收路径；须在 .env 配置有效 provider 与 Key。

- 已移除 mock 模式；LLM 失败时走规则降级或模板降级（见各专题与 LLM_README.md）。

- 不得用复杂本地规则代替应由 LLM 和 Agent 工作流实现的核心能力；降级仅保证流程可继续、结构合法。

#### 4. 产品链路

新版工作台的完整链路：

````
登录
  ↓
上传并确认简历
  ↓
配置目标面试
  ↓
可选：粘贴或上传 JD
  ↓
生成面试计划摘要
  ↓
候选人确认或按建议重新生成计划
  ↓
锁定计划并开始 45 分钟面试
  ↓
根据回答动态追问与切换主题
  ↓
生成能力评估和逐题复盘
  ↓
根据薄弱项再次练习
````

#### 5. 新版产品规则

##### 5.1 面试配置

必填配置：

- 简历

- 目标岗位

- 技术语言

- 目标难度

- 面试类型：校招或社招

可选配置：

- 粘贴 JD 文本

- 上传 JD 文件

- 希望重点练习的方向

新版首期固定面试时长为 45 分钟，不提供其他时长选项。

##### 5.2 校招与社招差异

校招重点：

- 技术与专业基础

- 项目、实习和竞赛经历

- 问题分析能力

- 学习能力和成长潜力

- 沟通表达

校招不能强制要求候选人具备大型生产系统、复杂线上事故或团队管理经验。缺少真实经历时，可以使用情景题继续考察。

社招重点：

- 项目真实性与个人贡献

- 技术深度

- 架构设计与方案取舍

- 线上故障处理与工程质量

- 业务理解

- 协作和推动能力

社招需要重点验证候选人具体负责了什么、为什么采用某个方案、结果如何验证、方案存在哪些代价。

##### 5.3 JD 使用规则

有 JD 时：

- 解析 JD 的职责、必备技能、加分技能、经验要求、业务背景和重点能力

- 面试计划优先覆盖 JD 核心要求

- 最终报告展示 JD 要求的已验证项、风险项和未验证项

无 JD 时：

- 使用目标岗位知识库和简历生成通用岗位面试

- 最终报告展示岗位通用能力表现

JD 不应直接作为超长文本反复传递给所有 Agent。上传或粘贴后，应先生成结构化 JD。

##### 5.4 面试计划预览

计划预览向候选人展示：

- 目标岗位

- 校招或社招

- 是否使用 JD

- 固定时长 45 分钟

- 预计考察主题数量

- 主要考察方向

- 重点参考的简历经历或 JD 要求摘要

计划预览不能展示：

- 完整题目

- 具体追问

- 评分标准

- 预期答案

- 内部风险验证点

##### 5.5 计划重新生成

首次生成计划后，候选人最多可以额外重新生成 2 次，最多产生 3 个计划版本。

重新生成时必须选择一个调整方向：

- 更贴合我的简历经历

- 更贴合目标 JD，仅在存在 JD 时显示

- 增加技术深度

- 增加基础知识考察

- 增加项目与实战考察

- 调整当前考察方向

- 换一套不同的面试计划

可选信息：

- 最多选择两个重点方向

- 最多填写 200 字补充建议

产品规则：

- 前端展示剩余重新生成次数

- 后端强制校验最多额外重新生成 2 次

- 新计划必须与上一版存在有效差异

- 开始面试后计划锁定，禁止继续重新生成

- 保存计划版本和重新生成原因

##### 5.6 45 分钟面试边界

新版首期采用以下确定性边界：

| 项目 | 限制 |
| --- | --- |
| 面试时长 | 45 分钟 |
| 计划主题数 | 4 至 5 个（优先生成 5 个） |
| 必须覆盖主题 | 至少 4 个 |
| 单主题最大追问次数 | 2 次 |
| 单主题最大回答轮数 | 3 轮 |
| 整场最大回答轮数 | 12 轮 |
| 正常回答轮数 | 8 至 10 轮 |
| 收尾预留时间 | 5 分钟 |
| 计划额外重新生成次数 | 2 次 |

满足以下任意条件时结束面试：

1. 达到 45 分钟。

2. 达到 12 个回答轮次。

3. 所有必须主题已覆盖，并且主要证据充分。

4. 剩余时间或轮数不足以开始新主题。

5. 候选人主动结束。

6. 候选人连续多轮表示不会或无法继续。

Agent 可以决定是否追问、切题或提前结束，但不能突破代码定义的时长、轮数和追问限制。

前端不显示固定的“第几题”，而显示：

- 已完成主题数

- 当前考察方向

- 当前主题是否处于深入追问

- 预计剩余时间

面试开始前需要明确告知候选人：

> 本次面试预计 45 分钟，将覆盖约 4 至 5 个能力方向。系统会根据回答情况进行追问，单个方向最多追问两次。

##### 5.7 新版评估报告

评估报告需要回答：

1. 候选人整体表现如何？

2. 结论基于哪些回答证据？

3. 哪些岗位能力表现较好？

4. 哪些能力存在风险或尚未验证？

5. 每道题可以如何改进？

6. 下一次应该重点练习什么？

报告至少包含：

- 总体表现摘要

- 岗位匹配度，有 JD 时展示

- 评估置信度

- 各能力维度评分

- 每项能力的回答证据

- 风险和未验证项

- 逐题复盘

- 可执行的后续练习建议

评分规则：

- 没有证据时不能给高分

- 未覆盖能力应标记为未验证，不能直接判低分

- 校招和社招必须使用不同评价标准

- 不能根据回答长度直接评分

- 最终报告不应输出真实招聘录用结论

#### 6. 新版 AI Agent 设计

##### 6.1 多 Agent 协作

多 Agent 协作是将复杂面试任务拆分为职责明确的 Agent 或工作流节点。它不是简单增加多个模型，也不是让多个 Agent 自由聊天。

新版首期建议采用三个核心 Agent：

###### Planning Agent

职责：

- 读取简历、面试类型、岗位、可选 JD 和岗位知识

- 生成 45 分钟结构化面试计划

- 根据候选人的重新生成建议调整计划

- 确保计划满足主题数、必须主题和轮数边界

###### Interview Agent

职责：

- 读取当前主题、工作记忆和候选人最新回答

- 分析回答中已经覆盖与缺失的信息

- 决定追问、切题、升降难度或结束

- 生成自然的面试官话术

Interview Agent 内部应拆成三个步骤：

````
Evidence Extraction
  ↓
Next Action Decision
  ↓
Question Generation
````

###### Evaluation Agent

职责：

- 根据面试过程积累的证据生成能力评估

- 引用候选人的具体回答依据

- 区分风险和未验证项

- 生成逐题复盘与练习建议

不建议首期创建大量 Agent 类。Evidence Extraction 和 Next Action Decision 可以先作为 LangGraph 工作流节点实现。

##### 6.2 双层决策

Interview Agent 必须将“做什么”和“怎么说”分开。

第一步输出结构化决策：

````
{
  "action": "probe_tradeoff",
  "target_topic": "系统设计",
  "reason": "候选人说明了最终方案，但没有解释备选方案",
  "expected_evidence": ["备选方案", "选择依据", "方案代价"]
}
````

第二步根据决策生成自然问题：

````
当时还考虑过哪些方案？最终选择当前方案时，最主要的约束是什么？
````

允许的动作集合：

````
probe_detail
probe_ownership
probe_metric
probe_tradeoff
probe_risk
increase_difficulty
decrease_difficulty
next_topic
finish
````

模型只能从允许的动作中选择。非法动作必须被后端拒绝或降级。

##### 6.3 Human-in-the-loop

计划预览与重新生成是新版工作台的人工介入节点：

````
Agent 生成计划
  ↓
候选人查看计划摘要
  ↓
候选人提出调整方向
  ↓
Agent 重新规划
  ↓
候选人确认并锁定计划
````

该能力需要体现：

- 用户反馈驱动重新规划

- 计划版本管理

- 新旧计划差异校验

- 次数限制

- 确认后锁定

##### 6.4 确定性边界与 Agent 决策

新版工作台必须结合概率性模型和确定性业务规则：

- Agent 决定下一步最合理的动作

- 后端规则决定该动作是否允许执行

- LangGraph 控制状态流转

- 数据库存储可恢复状态

不能把时间、轮数、追问次数和重新生成次数交给模型自行遵守。

#### 7. 知识边界（V2 暂不改造 RAG）

V2 首期不实施 Planning / Interview / Evaluation 分阶段岗位知识 RAG 改造。计划生成、动态面试与评估以 LLM + 本地模板/规则降级 为主路径；get_planning_context()、get_interview_memory_context() 等接口在 V2 中保持空上下文或本地降级即可。

数据边界（仍须遵守）：

| 数据 | 推荐存储方式 |
| --- | --- |
| 当前候选人简历 | 结构化业务数据 |
| 当前 JD | 会话 configuration_json 中的 jd_text 原文 |
| 当前面试回答 | 会话消息 |
| 当前面试证据和风险 | 工作记忆 |
| 历史能力趋势 | 长期记忆（见专题 07） |

简历、JD 和当前回答不应直接混入公共岗位知识库。

#### 8. 记忆设计

##### 8.1 短期记忆

短期记忆保存当前主题最近的问答，用于：

- 保持当前对话自然连贯

- 避免重复问题

- 生成承接话术

切换主题后，可以将完整对话压缩为主题摘要。

##### 8.2 工作记忆

工作记忆记录本场面试已经确认的信息，是新版首期最重要的记忆能力。

建议结构：

````
{
  "claims": [
    {
      "content": "负责订单服务架构设计",
      "status": "partially_verified"
    }
  ],
  "evidence": [
    {
      "topic": "数据一致性",
      "signal": "positive",
      "quote": "使用本地消息表和补偿任务",
      "strength": 0.8
    }
  ],
  "risks": [
    "尚未说明订单系统实际流量"
  ],
  "covered_topics": ["项目所有权"],
  "uncovered_topics": ["故障处理"]
}
````

工作记忆用于：

- 判断是否继续追问

- 防止跨主题重复提问

- 发现前后矛盾

- 控制面试进度

- 生成最终评估

工作记忆必须是结构化状态，不能只依赖完整聊天记录或纯文本摘要。

##### 8.3 长期记忆

长期记忆记录候选人跨场次的成长情况，例如：

- 重复出现的薄弱项

- 已改善的能力

- 历次能力评分趋势

- 推荐专项练习方向

长期记忆首期只预留模型，不参与当前面试评分。

长期记忆只能用于（详见 07 跨场次学习档案）：

- 练前 HITL 推荐：候选人显式采纳后，纳入下一场 configuration / Planning 的 focus_topics

- 报告中的跨场对比与练习建议增强

- 能力趋势展示

不得静默注入 Planning；不得进入 04 对话或 06 本场评分主路径。不能因为历史表现较差而降低当前面试评分。

#### 9. 主工作台升级原则

##### 9.1 替换约束

- / 直接承载新版工作台。

- 本分支不再维护旧工作台入口，不再提供 /v2 双入口。

- 允许对旧面试接口、Schema、状态和数据表做破坏性改动。

- 认证、用户、简历、LLM Factory、通用配置和基础工具优先复用。

- 旧面试工作流、服务、会话、消息和评估逻辑可以作为参考，但不作为兼容契约。

- 不为了保留旧工作台而复制一套并行业务；新版能力应逐步成为唯一主路径。

##### 9.2 旧能力处理规则

实现每个专题前，必须先识别现有能力，并按以下三类处理：

###### 直接复用

职责和契约仍然适合新版工作台的能力应直接保留：

- 认证 API、JWT Token、当前用户和用户额度

- 用户与简历数据、现有简历列表和详情 API

- LLM Factory、Provider 配置和模型客户端

- 配置、错误响应、安全、日志、SSE 等通用基础工具

- Embedding、向量存储、索引等既有设施（V2 首期不改造、不纳入交付验收）

###### 抽取公共能力

当前实现位于旧业务模块内部、但能力本身适合长期复用时，可以小步抽取到公共模块：

- 文件文本抽取

- 通用结构化输出解析和校验

- 不包含旧固定题序规则的流式和持久化辅助能力

- 新版页面需要复用的通用前端组件

抽取前必须明确当前调用路径和预期新调用路径。抽取后只需要验证新版主路径和仍被复用的基础能力，不需要保持旧面试流程可用。不得仅为了可能的未来复用创建抽象或大规模重构。

###### 替换重构

产品规则、状态模型或后续演进方向与旧工作台不同的能力应替换重构：

- Planning、Interview、Evidence 和 Evaluation 工作流

- 新版面试业务服务、状态机和 Prompt

- 新版面试会话、计划、消息、工作记忆和评估数据

- 新版 API Schema、接口和页面流程

旧 InterviewService、CvInterviewWorkflow、interview_sessions、messages 和评估结构可以被替换、迁移或废弃，不要求兼容旧行为。

每篇专题必须在“依赖契约”中明确本专题的直接保留、允许抽取和替换重构能力。发现现有公共契约不能满足需求时，应先停止当前小步，明确契约调整和新版主路径验证范围。

#### 10. 分阶段实施计划

##### 通用执行规则

每个阶段必须遵守：

1. 开始编码前先读取当前代码和本文档。

2. 只实现当前阶段明确列出的内容。

3. 不提前实现后续阶段的数据模型、页面或 Agent。

4. 每个阶段完成后运行对应验证。

5. 能通过前端验证的功能，必须提供前端可操作入口。

6. 仍被复用的基础能力必须验证，不要求旧面试流程继续可用。

7. 验证失败时先修复当前阶段，不得继续下一阶段。

8. 每个阶段完成后记录实际变更、验证结果和遗留问题。

##### 阶段 0：建立测试基线与替换边界

###### 产品目标

建立可重复验证的基础能力测试，并明确旧工作台将被新版主路径替换。

###### 本阶段范围

- 记录旧工作台当前可复用能力和将被替换的能力

- 增加最小后端测试基础

- 增加认证、健康检查、简历解析或 V1 工作流（含 LLM 失败降级）等基础测试

- 保留前端生产构建验证

- 不创建新版页面和业务功能

###### 建议验证场景

- 用户可以登录

- 用户可以上传并解析简历

- 仍被复用的基础接口可用

- 旧面试流程作为参考路径记录，不作为后续兼容目标

###### 验收方式

- 后端测试命令能够运行

- 基础能力测试通过

- frontend 的生产构建通过

- 人工确认旧工作台现状和替换范围

###### 停止条件

测试基线未建立或替换范围不清晰时，不进入阶段 1。

##### 阶段 1：替换主工作台入口与最小骨架

###### 产品目标

让用户访问 / 时进入新版工作台骨架，旧工作台不再作为产品入口维护。

###### 本阶段范围

- 将 / 前端入口替换为新版工作台

- 可以复用已经完成的新版页面骨架，但需要移除 /v2 双入口假设

- 保留或调整健康检查接口

- 新版工作台复用现有登录状态

- 新版页面展示产品标识和后续阶段入口占位

- 不实现面试配置、JD、计划或动态面试

###### 前端验证

- 访问 / 进入新版工作台

- 刷新 / 和新版内部路由仍可正常加载

- 新版工作台可以识别当前登录状态

- 不再展示旧工作台入口和返回旧版入口

###### 后端验证

- /healthz 正常

- 新版健康检查或等价接口正常

###### 停止条件

如果主入口无法稳定加载，或登录态无法恢复，不进入阶段 2。

##### 阶段 2：新版面试配置页面

###### 产品目标

候选人可以在新版工作台中完成面试配置，但暂时不生成真实面试计划。

###### 本阶段范围

- 新版工作台复用现有简历列表和简历详情

- 增加固定目标岗位、技术语言和难度配置

- 增加校招或社招选择

- 固定展示 45 分钟面试时长

- 增加可选的重点练习方向

- 建立新版配置请求 Schema

- 使用前端本地摘要验证配置提交，不调用 Agent

- 不实现 JD 上传和真实 Planning Agent

###### 前端验证

- 可以选择已解析简历

- 可以切换校招和社招

- 页面明确展示固定 45 分钟

- 可以配置岗位和重点方向

- 提交后可以看到配置摘要

- 刷新前后配置行为符合当前阶段设计

###### 后端验证

- 新版配置 Schema 对非法面试类型进行拒绝

- 重点方向数量和字段长度存在限制

- 可以替换旧 StartInterviewRequest，但必须保证新版配置校验清晰

###### 停止条件

配置页面无法完整提交或新版配置 Schema 不稳定时，不进入阶段 3。

##### 阶段 3：JD 粘贴、上传与结构化解析

###### 产品目标

候选人可以选择不提供 JD、粘贴 JD 或上传 JD，并查看结构化解析结果。

###### 本阶段范围

- 创建 JD 数据表和 Repository

- 支持 JD 文本粘贴

- 支持 PDF、DOCX、TXT、MD 上传

- 复用现有文件文本提取能力时，可以抽取为通用工具

- 使用 LLM 生成结构化 JD；LLM 失败时走规则/模板降级（本阶段 JD 解析若未实现则见 02 专题边界）

- 使用 LLM 对已选简历进行新版深度分析，基础简历解析继续作为输入

- 支持用户查看和确认 JD 解析摘要

- 无 JD 时明确展示通用岗位模式

- 不生成真实面试计划

###### JD 结构化字段

- 岗位名称

- 工作职责

- 必备技能

- 加分技能

- 经验要求

- 业务背景

- 重点能力

###### 前端验证

- 可以跳过 JD 并进入通用岗位模式

- 可以粘贴 JD 并查看解析摘要

- 可以上传 JD 文件并查看解析摘要

- 可以删除或替换当前 JD

- 页面能够区分有 JD 和无 JD

- 可以查看新版简历深度分析摘要

###### 后端验证

- JD 文件类型和大小限制有效

- JD 归属于当前用户

- 非当前用户不能访问 JD

- JD 解析失败时返回明确错误

- 简历上传、列表和详情在新版工作台中正常

- 新版简历深度分析使用独立结构，不污染基础简历解析结构

###### 停止条件

JD 无法稳定解析、用户隔离失败或基础简历解析不可用时，不进入阶段 4。

##### 阶段 4：Planning Agent 与计划预览

###### 产品目标

根据简历、校招或社招、岗位和可选 JD，生成一份可确认的 45 分钟面试计划摘要。

###### 本阶段范围

- 创建新版面试会话和面试计划数据表

- 实现 Planning Agent

- 生成 4 至 5 个考察主题

- 标记至少 4 个必须覆盖主题

- 为每个主题配置最大轮数和预期验证信号

- 生成候选人可见的计划摘要

- 计划状态支持 planning 和 plan_ready

- 暂不实现计划重新生成

- 暂不开始真实面试

###### 计划至少包含

````
{
  "duration_minutes": 45,
  "max_answer_rounds": 12,
  "max_probes_per_topic": 2,
  "topics": [
    {
      "name": "系统设计",
      "required": true,
      "max_rounds": 3,
      "expected_signals": ["容量分析", "方案取舍", "异常处理"]
    }
  ]
}
````

###### 前端验证

- 提交配置后展示计划生成状态

- 生成完成后展示计划摘要

- 校招计划明显偏向基础、项目和潜力

- 社招计划明显偏向项目所有权、技术深度和方案取舍

- 有 JD 时计划摘要展示 JD 相关重点

- 无 JD 时展示通用岗位计划来源

- 页面不泄露完整题目和评分细则

###### 后端验证

- 计划主题数、必须主题数和轮数边界被代码校验

- 计划不符合结构时能够重试或降级

- 计划版本初始为 1

- 新版会话、计划和消息结构可恢复；旧会话数据迁移或废弃策略明确

###### 停止条件

如果计划边界只能依赖 Prompt 而没有代码校验，或校招与社招计划无明显差异，不进入阶段 5。

##### 阶段 5：计划重新生成与 Human-in-the-loop

###### 产品目标

候选人可以根据自己的不满意原因定向调整面试计划，并在确认后锁定计划。

###### 本阶段范围

- 增加重新生成计划按钮

- 增加调整方向选择

- 支持最多两个重点方向

- 支持最多 200 字补充建议

- 后端限制最多额外重新生成 2 次

- 保存计划版本、调整原因和补充建议

- 校验新旧计划存在有效差异

- 增加确认并锁定计划能力

- 面试开始前允许重新生成，锁定后禁止重新生成

- 暂不实现动态面试

###### 前端验证

- 按钮展示剩余重新生成次数

- 点击按钮后必须选择调整方向

- 有 JD 时才展示“更贴合目标 JD”

- 每次重新生成后计划版本递增

- 第 2 次重新生成后按钮禁用

- 确认计划后无法继续重新生成

- 页面能够查看当前计划版本

###### 后端验证

- 绕过前端直接调用接口也不能超过 2 次额外重新生成

- 锁定计划后重新生成接口返回冲突错误

- 新计划不能与上一版完全相同

- 历史计划版本可以查询或审计

###### 停止条件

如果次数限制只存在于前端，或锁定后仍可修改计划，不进入阶段 6。

##### 阶段 6：受控动态面试最小闭环

###### 产品目标

基于已锁定计划完成一场有边界的动态面试，先实现可控闭环，再增加复杂证据能力。

###### 本阶段范围

- 创建新版消息存储

- 实现新版面试状态流转

- 支持计划确认后开始面试

- 根据当前主题和最新回答决定追问或切题

- 实现允许动作集合和代码校验

- 实现单主题最多追问 2 次

- 实现整场最多回答 12 轮

- 实现用户主动结束

- 实现 45 分钟截止与 5 分钟收尾判断

- 使用简单主题摘要作为最小工作记忆

- 暂不实现完整证据化评分

###### 前端验证

- 面试开始前展示边界说明

- 页面显示已完成主题数和当前主题

- 追问时显示正在深入当前主题

- 面试不会展示虚假的固定题号

- 单主题不会无限追问

- 达到最大轮数后自动结束

- 用户可以主动结束

- 刷新页面后会话可以恢复

###### 后端验证

- 非法动作被拒绝或降级

- Agent 不能突破单主题追问限制

- Agent 不能突破总回答轮数

- 只有锁定计划才能开始面试

- 已完成面试不能继续回答

- 状态可持久化和恢复

###### 停止条件

如果动态面试存在无限循环、状态无法恢复或边界只依赖模型遵守，不进入阶段 7。

##### 阶段 7：结构化工作记忆与证据提取

> 专题文档：05-context-memory-evidence.md

###### 产品目标

让面试官能够记住候选人已经说过什么、哪些信息已经验证、还缺少什么，并据此做出更专业的追问。

###### 本阶段范围

- 实现 Evidence Extraction 节点

- 从回答中提取声明、证据、风险和缺失信息

- 建立结构化工作记忆

- Next Action Decision 读取工作记忆做决策

- 避免重复提问已经充分验证的内容

- 支持发现潜在前后矛盾

- 切换主题后生成主题摘要

- 暂不实现跨场次长期记忆

###### 每轮最小分析结果

````
{
  "answer_quality": "partial",
  "claims": [],
  "evidence": [],
  "missing_information": [],
  "risks": [],
  "next_action": "probe_metric"
}
````

###### 前端验证

候选人端保持自然面试体验，不直接展示内部证据和风险。

可以增加仅开发环境可见的 Agent 调试面板，展示：

- 当前主题

- 当前回答轮数

- 已提取证据数量

- 缺失信息

- Agent 选择的动作

- 决策原因

###### 后端验证

- 回答分析结果通过结构化 Schema 校验

- 工作记忆随着每轮回答增量更新

- 已覆盖主题和未覆盖主题状态正确

- Decision 节点读取工作记忆，而不是只读取最新回答

- 模型输出异常时存在规则降级

###### 停止条件

如果工作记忆仍然只是完整聊天记录，或最终决策不读取结构化记忆，不进入阶段 9。

##### 阶段 9：证据驱动评估与逐题复盘

> 专题文档：06-evaluation-and-practice.md
> 实施状态（2026-06-11）：专题 06 首期已完成（见该文档 §13）；阶段 10 / 专题 07 跨场档案不阻塞本阶段验收。

###### 产品目标

生成可解释、可复盘、能够指导下一次练习的专业评估报告。

###### 本阶段范围

- 实现 Evaluation Agent

- 根据工作记忆生成能力评估

- 每项能力引用候选人回答证据

- 区分风险和未验证项

- 有 JD 时生成 JD 匹配分析

- 无 JD 时生成岗位通用能力分析

- 生成逐题复盘和可执行练习建议

- 不实现真实招聘录用建议

###### 前端验证

- 展示总体表现与置信度

- 展示各能力维度结果

- 每个评分可以查看回答证据

- 展示风险和未验证项

- 有 JD 时展示 JD 匹配分析

- 展示逐题复盘

- 展示下一步练习建议

- 未覆盖能力不会被错误显示为低分

###### 后端验证

- 评估结果通过结构化 Schema 校验

- 每项高分或低分都有证据或明确说明

- 未验证项不会参与不合理扣分

- 评估不按回答字符数直接计算

- 校招和社招使用不同评分标准

###### 停止条件

如果评分无法追溯到证据，或未验证项被直接判低分，不进入阶段 10。

##### 阶段 10：长期记忆与成长闭环

> 详细规格：07 跨场次学习档案。不阻塞 01–06 首期交付。

###### 产品目标

帮助候选人通过多次模拟面试看到能力变化，并获得下一次练习建议。

###### 本阶段范围

- 保存历次能力维度结果

- 汇总重复出现的薄弱项

- 展示已改善能力和能力趋势

- 练前 HITL 推荐：采纳后纳入 Planning 的 focus_topics；未采纳则不注入

- 支持基于薄弱项发起下一次专项练习（报告 / 趋势 / 02 预填）

- 长期记忆不参与 04 对话与 06 本场评分

###### 前端验证

- 用户可以查看历次面试记录

- 用户可以查看能力趋势

- 用户可以基于薄弱项开始新面试

- 当前面试评分不会因历史低分自动降低

###### 后端验证

- 长期记忆按用户和岗位隔离

- 历史数据不作为当前评分证据

- 删除历史会话时长期记忆处理符合产品规则

###### 停止条件

如果长期记忆影响当前评分公正性，不完成本阶段。

##### 阶段 11：全局收尾验证与工程增强

###### 产品目标

在前述各专题已经完成局部测试、安全、降级和观测要求的基础上，执行全局收尾验证与工程增强。

###### 本阶段范围

- 审核各专题是否已经落实日志脱敏和敏感字段保护

- 审核各专题是否已经记录必要的 Agent 决策轨迹

- 汇总延迟、模型、Token、检索命中和降级情况

- 增加计划与工作流恢复测试

- 增加 Prompt 和模型回归评测数据集

- 评估是否接入模型原生流式输出

###### 推荐观测字段

````
trace_id
plan_version
current_topic
answer_round
selected_action
decision_reason
evidence_count
model
latency
token_usage
fallback_used
````

###### 前端验证

- 候选人端错误提示清晰

- 请求失败后能够恢复或重试

- 页面刷新后计划、面试和评估状态可以恢复

- 开发环境调试面板能够定位 Agent 决策问题

###### 后端验证

- 日志中不存在明文手机号、邮箱和完整简历

- Agent 决策轨迹可追踪

- 模型失败有降级策略

- 新版主路径测试和仍被复用的基础能力测试均通过

| 面试中刷新页面 | 是否恢复正确状态 |
| 提前结束 | 是否正确生成未验证项 |
| 模型输出非法动作 | 是否拒绝或降级 |
