#### 2. 改造目标

让候选人在新版工作台中选择简历并完成目标面试配置，同时支持不提供 JD 或粘贴 JD 文本两种模式。

本专题完成后，候选人可以在配置页填写完整面试信息并点击「生成面试计划」；面试配置不做持久化，校验与计划生成由专题 03 在用户提交时一次性完成。

#### 3. 本专题范围

##### 负责

- 选择现有简历

- 配置目标岗位、技术语言、目标难度

- 选择校招或社招

- 固定展示 45 分钟

- 展示前端规则推荐的重点练习方向，用户最多保留或调整前 6 个

- 复用现有简历上传和基础解析结果

- JD 文本粘贴、替换和删除

- 有 JD 与无 JD 模式

- 配置固定选项的后端维护与前端读取

- 配置页 UI 与前端表单状态

##### 不负责

- 面试配置持久化

- 独立配置校验 API

- 生成面试计划

- 根据 JD 出题

- 动态面试

- JD 匹配评分

- JD 文件上传

- JD 结构化解析

- 简历优化和简历改写建议

- 独立的简历深度分析任务

- 正式面试对话、逐题追问和评估报告

- 岗位知识库的完整建设（V2 不改造 RAG）

#### 4. 依赖契约

- 消费专题 01 提供的新版页面容器、登录状态和现有简历读取能力。

- 向专题 03 输出页面上的标准化面试配置草稿、基础简历解析结果引用和可选 JD 文本；在用户点击「生成面试计划」时随请求提交，不做本专题持久化。

- 专题 03 负责接收配置 payload、校验、创建会话并生成计划。

- JD 文本属于配置草稿的一部分，由专题 03 在生成计划时使用。

- 专题 03 的 Planning Agent 在生成面试计划时直接基于基础简历解析结果、配置和可选 JD 文本做内部分析。

- 用户提交「生成面试计划」后，jd_text 随 configuration_json 持久化到会话（由专题 03 写入），供 Planning、动态面试与评估（06）读取；首期只有 JD 原文，没有 structured_jd 或独立 JD 表。

##### 旧能力处理边界

- 直接保留：认证与用户隔离、现有简历数据和读取 API、简历原文与基础解析结果、LLM Factory、文件类型与大小等通用配置。

- 替换重构：新版面试配置页、JD 文本输入、固定选项读取 API。

- 禁止混用：不要在本专题新增简历优化/简历深度分析链路；不要把 JD 原文写入公共岗位知识库；不要引入独立配置表或配置持久化。

- 验证要求：简历上传、解析、列表和详情在新版工作台中必须保持可用。

#### 5. 产品规则

##### 5.1 配置字段

|  |  |
| --- | --- |
|  |  |
|  |  |
| target_role | 必填，固定选项：前端开发、后端开发、全栈开发、Agent 开发 |
| language | 必填，固定选项：Java、Python、Go、JavaScript |
| target_level | 必填，固定选项：入门、进阶、挑战 |
| duration_minutes | 固定为 45，不允许前端修改 |
| focus_topics | 可选，前端规则推荐（非 LLM），最多保留 6 个 |
| jd_text | 可选，用户粘贴的 JD 文本 |

固定选项维护规则：

- target_role、language、target_level、interview_type 的可选值由后端统一维护。

- 前端通过选项接口读取，不在页面中重复硬编码业务枚举。

- 首期可以在后端常量中维护；后续如需运营配置，再迁移为数据库字典。

- 前端仅允许选择后端返回过的选项值。

interview_type 负责区分校招和社招的面试侧重；target_level 只表达本场题目难度，不表达职级。

JavaScript 表示主语言为 JavaScript。系统可以在前端开发或全栈开发场景下将 TypeScript、Node.js 和前端工程化作为关联考察方向，但不能把 TypeScript 当成用户明确选择的主语言。

全栈开发 保持通用岗位含义，不改成 AI 全栈开发。AI/Agent 方向由 Agent 开发 单独承载，避免全栈岗位含义被收窄。

岗位能力边界和“该岗位应该面什么”不由配置页硬编码决定。专题 03 使用 LLM 主路径 + 本地岗位模板降级推断考察方向。

##### 5.2 focus_topics 规则

focus_topics 不是让用户自由填写的大量配置，而是前端根据 校招/社招 + 目标岗位 用本地静态列表规则生成候选（buildRecommendedFocusTopics），不读简历、不调 LLM。

规则输入包括：

- 校招或社招

- 目标岗位（Agent 开发等会追加专项标签）

推荐结果最多 6 个，前端只展示这些候选项供勾选。候选人可以取消不想练的方向，但首期不支持自由新增任意文本。

与 Planning 的分工： 本页 focus_topics 只表达候选人本场想练的方向偏好；具体考察主题与 expected_signals 由专题 03 Planning Agent 结合简历、配置与可选 JD 生成。

推荐项可以包括但不限于：

- 项目深挖

- 技术基础

- 系统设计

- 业务理解

- 问题排查

- 沟通表达

- 算法与编码

- Agent 工程能力

focus_topics 只表示本场面试的候选关注方向，不等同于完整面试计划，也不直接决定题目列表。

##### 5.3 JD 模式

候选人二选一：

1. 不提供 JD：使用岗位通用模式。

2. 粘贴 JD 文本。

JD 文本框可以为空。为空时表示不提供 JD，后续 Planning Agent 使用岗位通用模式。

实现约定（无独立 jd_mode 字段）： 是否「有 JD」由 jd_text.trim() 是否非空推导；配置页用 Badge 展示「已提供 JD」/「未提供 JD」，请求 payload 只传 jd_text 字符串。

##### 5.4 JD 文本规则

- JD 文本是用户输入，必须视为不可信内容。

- 首期不做结构化解析，不要求展示 JD 摘要。

- 文本过短时前端可以提示，但不阻止无 JD 模式继续。

- 文本过长时由专题 03 在生成计划时拒绝；前端输入框限制 8000 字作为软约束。

- 替换 JD 只更新当前页面草稿，不影响简历数据。

##### 5.5 不过度配置化

本专题的目标不是让候选人填写大量配置，而是收集必要配置项；重点方向由前端规则推荐，计划与考察深度由专题 03 Planning Agent 结合简历与可选 JD 生成。

前端只暴露必要控制项：

- 简历

- 校招或社招

- 目标岗位

- 技术语言

- 目标难度

- 可选 JD 文本

- 前端规则推荐的重点方向确认

其他信息应由专题 03 的 Planning Agent 在生成面试计划时内部分析，不在本专题提前生成用户可见报告。

##### 6.3 JD 文本结构

````
{
  "jd_text": "用户粘贴的 JD 文本，可为空"
}
````

- 有/无 JD 模式由 jd_text 是否非空推导，不单独传 jd_mode。

- 配置页草稿阶段不持久化；用户点击「生成面试计划」时随 POST /api/interviews 提交，写入会话 configuration_json（专题 03）。

- 默认不将完整 JD 原文写入普通日志。

##### 6.4 配置草稿 Schema

配置页维护的前端草稿结构，供专题 03 接收：

````
{
  "resume_id": "resume-id",
  "interview_type": "experienced",
  "target_role": "backend",
  "language": "java",
  "target_level": "intermediate",
  "duration_minutes": 45,
  "focus_topics": ["系统设计", "项目深挖"],
  "jd_text": "optional JD text"
}
````

##### 6.5 输出契约

本专题向专题 03 输出的是一次性配置草稿，不是持久化实体：

- 用户在配置页点击「生成面试计划」时，前端将 §6.4 结构随专题 03 的创建/计划接口提交。

- 不做 configuration_id、不做 confirmed 状态、不做独立配置表。

- 校验（简历归属、枚举、长度、focus_topics 数量、JD 长度等）在专题 03 创建计划时完成。

简历面试所需的项目分析、技术栈排序、真实性验证点和追问策略由专题 03 的 Planning Agent 基于基础简历解析结果内部完成。

##### 6.6 API

本专题仅提供：

````
GET /api/interview-options
````

以下能力明确移出本专题，由专题 03 负责：

````
POST /api/interview-configurations/validate   # 已取消
POST /api/interview-configurations            # 已取消
GET /api/interview-configurations/{id}        # 已取消
````

#### 7. 分步实施

##### 小步 1：面试配置页面

实现：

- 选择简历、校招/社招、岗位、语言、难度。

- 使用本地规则列表展示重点方向候选项，并允许用户最多保留 6 个。

- 固定展示 45 分钟。

不实现：

- 后端选项接口。

- JD 功能。

- 生成面试计划。

完成条件：

- 候选人可以完成无 JD 配置交互。

##### 小步 2：后端固定选项

实现：

- 新增后端固定选项接口。

- 前端从后端选项接口读取岗位、语言、难度和面试类型。

不实现：

- 配置校验 API。

- 配置持久化。

- JD 功能。

- 真实 LLM 推荐重点方向。

完成条件：

- 配置页选项与后端枚举一致。

##### 小步 3：JD 文本输入

实现：

- 创建面试页增加可选 JD 文本框。

- JD 文本框支持粘贴、编辑和清空。

- 不填写 JD 时保持通用岗位模式。

- 前端输入框限制 8000 字。

不实现：

- JD 文件上传。

- JD 结构化解析。

- 后端配置校验。

- 正式面试计划。

完成条件：

- 配置页支持无 JD 和粘贴 JD 两种模式。

##### 小步 4：收尾

实现：

- 主按钮文案改为「生成面试计划」。

- 移除本专题已实现的 POST /api/interview-configurations/validate 及相关前端调用。

不实现（移交专题 03）：

- 配置持久化（草稿阶段）。

- 点击「生成面试计划」时的 POST /api/interviews 与会话创建（03 接入后由配置页触发）。

完成条件：

- 02 专题 UI 与选项契约闭合；计划生成由专题 03 承接。

#### 8. 测试与验收

- 校招、社招选项可切换。

- 无 JD、文本 JD 两种模式在页面上可用。

- focus_topics 来自前端规则推荐（校招/社招 + 岗位），最多 6 个，不支持自由发散输入。

- JD 文本为空时表示通用岗位模式。

- 前端 JD 输入框限制 8000 字。

- 简历上传和读取在新版工作台中可用。

- 「生成面试计划」提交 POST /api/interviews（含 jd_text、focus_topics 等），由专题 03 校验并生成计划。

- 不存在本专题独立的配置持久化或校验 API。

- 前端构建和后端测试通过。

#### 9. 质量、安全与降级

- 不记录完整 JD 原文和简历原文日志。

- JD 文本必须在后续 Planning Agent prompt 中标记为不可信输入，防止其指令覆盖系统要求。

- 本专题不调用 LLM 解析 JD，不新增独立规则解析路径（JD 结构化属后续专题）。

#### 10. 停止条件

- 简历基础功能不可用。

- 有 JD 和无 JD 模式无法明确区分。

- 配置页字段不足以供 Planning Agent 使用。

- 配置选项在前后端不一致。
