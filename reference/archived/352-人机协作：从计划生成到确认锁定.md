一场面试开始之前，系统需要生成一份计划。这个过程不是一次性的 LLM 调用，而是一个有完整状态流转、多个人工介入点和最终锁定机制的工作流。

#### Planning Agent 如何生成计划

用户在配置页面填完信息并提交后，会调用 /api/interviews 这个接口，正式触发规划 Planning Agent 开始工作。

整个生成面试计划的过程分为两层：大模型生成内容 + 代码规则校验。大模型会根据用户配置、简历和 JD，智能生成包含四到五个考察主题的结构化面试计划；之后代码层会严格兜底，确保最终输出完全符合我们的业务规则。

这套设计有三个核心亮点：

亮点 1：带纠错反馈重试，不盲目重生成

如果第一次生成的计划校验不通过，系统会把具体的报错原因，直接塞进下一轮的提示词里给到模型。多次重试全部失败后，系统才会触发模板降级方案，保证流程不中断。

代码示例：

````
# offer-agent/backend/app/agent/interview_planning/agent.py
class PlanningAgent:
    def generate_plan(self, *, configuration, resume, ...):
        # 存储上一轮校验失败的报错信息，用于传给LLM做纠错引导
        validation_feedback = ""
        # 循环重试，最多执行MAX_PLANNING_ATTEMPTS次生成逻辑
        for attempt in range(1, MAX_PLANNING_ATTEMPTS + 1):
            # 拼接提示词，带上上一轮的校验错误反馈，让模型针对性修正输出
            prompt, system_prompt = build_planning_prompt(
                ..., validation_feedback=validation_feedback, ...
            )
            try:
                # 调用LLM生成结构化的面试计划原始JSON数据
                payload = client.generate_json(prompt, system_prompt, ...)
                validated = validate_and_normalize_plan(payload, configuration=configuration)
                # 校验全部通过，返回LLM生成的标准计划，标记来源为大模型、未启用降级
                return {**validated.plan, "source": "llm", "degraded": False}
            except PlanValidationError as exc:
                validation_feedback = str(exc)
        # 三次全失败，走模板降级
        return build_template_fallback_plan(configuration, resume, ...)
````

亮点 2：校验兼顾格式与内容覆盖度，区分校招 / 社招硬性要求

校验文件里专门写了维度校验逻辑，会严格区分校招和社招，检查面试计划是否覆盖必备考察维度，少任何一项都会校验失败、自动重试。

亮点 3：摘要防泄露校验，拦截完整面试题干提前暴露

每次生成面试计划后，系统都会执行摘要安全校验，确保对外展示的精简摘要里，绝对不会泄露具体的开场试题。

代码示例：

````
# offer-agent/backend/app/agent/interview_planning/validator.py
def _assert_summary_safe(candidate_summary: dict, opening_questions: list[str]) -> None:
    joined_summary = " ".join(candidate_summary.get("reference_summary", []))
    for question in opening_questions:
        compact_question = question.strip()
        if len(compact_question) >= 20 and compact_question in joined_summary:
            raise PlanValidationError("candidate_summary 不得泄露完整 opening_question")
````

#### 三种人工介入模式

面试计划生成之后，用户会进入预览页面，只能看到精简的计划摘要，包括各个考察方向、是否必考、预估时长，以及系统重点参考了简历的哪些内容。

在这个阶段，我们设计了三种人工介入方式，分别对应不同的人机协作场景：

1. 审批模式

用户预览后如果觉得整体考察方向没问题，直接确认锁定就行。这是成本最低的介入方式，用户只需要做一个判断：认不认可这套面试计划。

> 图片尚未保存：[在原页面查看](https://acn2lw4rwc26.feishu.cn/wiki/Od9zwahVwi9aOOkGN2ocqtmJnbg)（图片标识：EshebwGcFo2WM0xS5RycaVCgnOH）

2. 修正模式

如果用户觉得计划偏差比较大，可以选择对应的优化策略重新生成。V2 提供了六种标准化的修正策略：贴合简历、贴合JD、加深技术深度、加强基础考察、增加实战案例和换一套计划。

> 图片尚未保存：[在原页面查看](https://acn2lw4rwc26.feishu.cn/wiki/Od9zwahVwi9aOOkGN2ocqtmJnbg)（图片标识：Z2Vib5ERIoVHKtxQFV8c4oGln50）

用结构化策略而不是自由文本的原因：策略是有机器后验逻辑的。后端在收到新计划后，会执行策略后验，检查新计划是否确实反映了策略意图。

策略后验逻辑：

````
# offer-agent/backend/app/services/interview_planning/regeneration.py
def validate_regeneration_strategy_outcome(
    *,
    plan: dict[str, Any],
    candidate_summary: dict[str, Any],
    configuration: dict[str, Any],
    resume: dict[str, Any],
    regeneration_feedback: dict[str, Any],
    previous_plan_summary: dict[str, Any] | None,
) -> None:
    strategy = regeneration_feedback["regeneration_strategy"]
    topics = plan.get("topics", [])
    # 策略1：校验计划是否贴合JD岗位要求
    if strategy == "align_jd":
        _validate_align_jd(topics, candidate_summary, configuration)
    # 策略2：校验计划是否贴合用户简历核心经历
    elif strategy == "align_resume":
        _validate_align_resume(topics, candidate_summary, resume)
    # 策略3：校验新版计划与上一版存在实质性内容差异
    elif strategy == "different_plan":
        _validate_different_plan(topics, previous_plan_summary)
````

注意，代码里只给 3 种策略做自动化后验校验，是因为另外 3 种策略「加强技术深度/加强基础考察/加强实战案例」，没有唯一标准，硬写校验规则易误判，目前靠 Prompt 引导，用户预览时再确认。

3. 自定义采纳模式

六种策略里，只有「更换全新计划」支持用户输入最多200字的自定义说明，用来指定自己想重点练习的方向，比如专门练系统设计。

> 图片尚未保存：[在原页面查看](https://acn2lw4rwc26.feishu.cn/wiki/Od9zwahVwi9aOOkGN2ocqtmJnbg)（图片标识：QUMSbuHXLotLXrxoZiacESP4nba）

因为常规策略的意图都非常明确，加自定义说明反而会产生歧义，导致无法自动化校验。只有完全换新计划的场景，才适合让用户自定义补充需求。

#### 确认即锁定

用户确认计划后，系统执行一个状态转换：

````
plan_ready  →  plan_confirmed
````

同时在面试会话上记录 confirmed_plan_id，指向这个版本的计划。

这个设计解决了一个实际问题：同一个面试会话可能有多个计划版本，用户重新生成了几次就有几个版本。Interview Agent 需要一个明确的锚点，知道应该读哪个版本。confirmed_plan_id 就是这个锚点，面试启动时只读这一个版本，不读其他版本，也不重新生成。

> 确认后的计划是 Interview Agent 和 Evaluation Agent 的唯一真相来源。它的内容在面试期间不能被任何东西改变。

这个链路的核心设计思想是：人工决策只在计划阶段发生，一旦确认，后续环节全部由系统按契约执行。用户不需要在面试进行中干预，也不需要担心系统自行修改计划。人的判断和机器的执行，在确认这个节点上完成了交接。
