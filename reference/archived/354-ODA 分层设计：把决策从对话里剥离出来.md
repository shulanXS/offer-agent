我们之前在《智能体：深入 Agent 开发》里讲过 Agent 的通用循环范式  [ReAct 范式](https://acn2lw4rwc26.feishu.cn/wiki/F63JwfGdEi6ArZka2AwcolAynKb)，核心逻辑是「观察环境 Observation → 执行行动 Act」的迭代闭环

这次的面试 Agent 的 V2 升级，就是在 ReAct 的基础上做了精细化分层拆解，形成了「观察 Observation - 决策 Decide - 执行 Action」的 ODA 流程。我们核心只做一件事：把 Agent 的决策思考和对外话术彻底拆开，不再用一个 Prompt 包揽所有逻辑，以此解决旧版一体化写法带来的各类工程问题。

#### V1 的问题：决策和话术绑在一起

V1 用一个 Prompt 同时完成追问方向判断与话术生成，模型直接输出可对外使用的提问语句：

````
# offer-agent/backend/app/agent/workflow.py
def build_follow_up_with_llm(*, question, answer, ...) -> str:
    prompt = f"""
你是一个教学版面试官，请基于候选人的上一轮回答，生成一句自然的追问。

当前题目: {question['prompt']}
考察重点: {question['focus']}
上一轮回答: {answer}
追问方向提示: {question['follow_up_hint']}

请返回 JSON：{{"message": "一句可直接说给候选人听的追问"}}
"""
    return llm_generate(prompt)
````

这么做会引出三个很棘手的工程痛点：

1. 过程没法追溯：最后只拿到一句追问，我们无从确认模型有没有对照面试方案里要求考察的要点去判断；

2. 决策无法测试：产出只有纯文本话术，针对提问策略好坏这层核心逻辑，根本写不了单元测试；

3. 没有容错兜底：一旦大模型调用出错，整条追问流程直接瘫痪，不存在中间数据层用来做规则兜底。

除此之外切换话题的逻辑也很死板，只能按题号依次往下走，不能根据候选人答出的信息灵活调整。而 V2 的核心改造思路，就是把决策逻辑单独抽离出这段统一提示词。

#### V2 的 ODA：三层职责

V2 每一轮回答走 Observe → Decide → Act 三步，各自有独立 Prompt、LLM 调用和降级逻辑。

##### 1.
Observe：只收集信息，不做任何判断

这个环节只做信息汇总，完全不去思考要不要追问。 Observe 会读取面试方案、完整对话记录、记忆存储和候选人最新回答，整理出当下对话的全部现状，打包好传给下一层决策模块。

代码示例：

````
# offer-agent/backend/app/agent/interview/nodes/observe.py
def build_observe_node(state: InterviewReplyState) -> InterviewReplyState:
    observe_context = build_observe_context(
        plan_json=state["plan_json"],
        configuration=state["configuration"],
        resume=state.get("resume"),
        runtime_state=state["runtime_state"],
        topic_messages=state.get("topic_messages") or [],
        latest_answer=state["latest_answer"],
        trace_id=state.get("trace_id", ""),
    )
    return {
        **state,
        "observe_context": observe_context,
        "memory_context": observe_context.get("memory_context") or {},
    }
````

##### 2.
Decide：输出标准化判断，不生成聊天话术

实现类在 decide.py，这里只产出 LLM 能读懂的结构化决策数据，绝不生成直接发给候选人的问句。 能执行的操作都是提前定好的固定类型，比如深挖细节、切换话题、结束面试等。如果大模型调用失败，会自动启用预设规则兜底。

````

典型 JSON 输出如下：

````
{
  "action": "probe_tradeoff",
  "target_topic_id": "topic-2",
  "reason": "候选人说明了最终方案，但没有说明备选方案",
  "expected_information": ["备选方案", "选择依据", "代价"],
  "should_change_topic": false
}
````

##### Act：只表达，不推理

实现类在 act.py，Act 只干一件事：拿着前面决策好的理由和需要询问的信息，转换成一段 40 到 120 字自然通顺的提问，不会再自己判断要不要追问。

典型的输出如下：

````

  "message": "你刚才说的最终方案我听到了，当时还考虑过哪些备选架构？没选它们主要是出于哪些约束或代价？"

候选人界面上看到的就是这句自然可直接朗读的话，不包含 action、reason 等机器字段。
