前面两篇我们讲完 ODA 分层职责，以及如何用 LangGraph 把整套逻辑搭成执行流程图。这一篇介绍流程图运行时的两套保障机制：

- 一是边界守卫，靠固定代码强制执行硬性规则；

- 二是降级方案，万一调用大模型失败，面试流程也不会直接中断

#### 第一道防线：边界守卫

Interview Agent 里有两类规则，性质完全不同。

1. 软判断

候选人说的够不够深？这个方向还值不值得追问？下一个问题该怎么说？这些问题没有确定性的答案，需要理解上下文、对照信号、做出综合判断。这是 LLM 擅长的领域，交给 Decide 和 Act。

2. 硬约束

整场面试最多 12 轮回答。单个主题最多 3 轮。45 分钟后强制结束。这些规则的特点是：有精确定义，必须无条件执行，不允许 LLM 用「候选人情况特殊」等理由绕过。

把硬约束交给 LLM 有三个典型问题：

1. 幻觉：模型可能产生「这道题还没考完，再追问一次吧」的自我说服，静默地突破轮数限制。

2. 被 prompt 说服：如果候选人的回答里出现「我们还没聊完这个主题」，模型可能把这个当成合理理由接受。

3. 不可测试：你没办法写一个确定性的测试来断言「LLM 会在第 12 轮停止」。

![页面图片](../assets/356-639a65b084bd3c5a.png)

V2 版本把所有硬性限制从提示词里剥离，统一放到boundaries.py 纯代码模块执行，完全脱离大模型。

##### 边界守卫的实现

enforce_boundaries是流程图中紧跟信息收集 Observe 之后的节点，会在执行 Decide 决策节点前优先运行，输出边界判定结果。

代码示例：

````
# offer-agent/backend/app/services/interview/boundaries.py
def evaluate_forced_action(
    *,
    runtime_state: dict[str, Any],
    plan_json: dict[str, Any],
    current_topic_id: str,
) -> BoundaryVerdict:
    deadline_at = str(runtime_state.get("deadline_at") or "")
    answer_round = int(runtime_state.get("answer_round") or 0)
    topic_round = int(runtime_state.get("current_topic_round") or 0)
    probe_count = int(runtime_state.get("current_topic_probe_count") or 0)
    
    # 规则1：超过面试截止时间，强制结束面试
    if is_past_deadline(deadline_at):
        return BoundaryVerdict(forced_action="finish", reason="deadline_reached")

    # 规则2：全局回答轮数达到上限，强制结束
    if answer_round >= MAX_ANSWER_ROUNDS:
        return BoundaryVerdict(forced_action="finish", reason="max_answer_rounds")

    # 规则3：进入收尾倒计时区间
    if is_wrap_up_zone(deadline_at):
        if required_topics_covered(runtime_state=runtime_state, plan_json=plan_json):
            return BoundaryVerdict(forced_action="finish", reason="wrap_up_required_topics_covered")
        following = next_topic(plan_json, current_topic_id)
        if following is None:
            return BoundaryVerdict(forced_action="finish", reason="wrap_up_no_more_topics")
        return BoundaryVerdict(forced_action="next_topic", reason="wrap_up_cover_required_topics")

    # 规则4：单个主题回答轮数超限
    if topic_round >= MAX_TOPIC_ANSWER_ROUNDS:
        following = next_topic(plan_json, current_topic_id)
        if following is None:
            return BoundaryVerdict(forced_action="finish", reason="topic_round_limit_last_topic")
        return BoundaryVerdict(forced_action="next_topic", reason="topic_round_limit")

    # 所有硬性规则均未触发，无强制动作，正常进入Decide
    return BoundaryVerdict(forced_action=None)
````

一旦enforce_boundaries判定需要强制终止或切换话题，流程图会直接走对应分支，跳过后续 Decide、Act 节点。整个过程大模型无法参与、也不能修改最终判定结果。

同时边界规则方便写稳定单元测试：我们只需构造出达到最大轮数、超时等场景的全局状态，就能断言代码一定会返回强制结束指令，测试结果稳定，不依赖模型输出。

#### 第二道防线：降级设计

边界守卫解决了「LLM 不该管的事」，降级设计解决的是「LLM 管的事但 LLM 挂了的情况」。V2 的降级分两层，针对不同节点：

##### Decide 节点：规则降级

如果调用大模型生成决策失败，系统会执行rule_fallback.py中的兜底逻辑。这套逻辑读取对话记忆里缺失的信息，依靠固定规则算出下一步操作。

````
# offer-agent/backend/app/agent/interview/rule_fallback.py（节选）
def build_rule_fallback_decision(
    *, topic, latest_answer, runtime_state, has_next_topic, memory_context=None,
) -> dict[str, Any]:
    """     
    LLM调用失败时的决策兜底函数     
    不依赖大模型，仅依靠记忆、固定规则生成合法决策动作，保证流程不中断     
    """
    next_gap = pick_next_gap(memory_context, last_probed_information=last_probed)

    # 场景1：当前主题信息已经收集完整
    if topic_is_sufficiently_covered(memory_context):
        if has_next_topic:
            return {
                "action": "next_topic",
                "reason": "当前主题期望信号已基本覆盖，准备切换下一主题",
                "expected_information": [],
                "should_change_topic": True,
            }
        return {"action": "finish", "reason": "所有主题已完成", ...}

    # 场景2：还有可深挖的信息缺口，且未超过单主题追问上限
    if memory_has_actionable_coverage(memory_context) and next_gap and probe_count < MAX_TOPIC_PROBE_COUNT:
        signal = str(next_gap.get("signal", "")).strip()
        action = probe_action_for_signal(signal, topic)
        return {
            "action": action,
            "reason": f"仍需补充与主题相关的「{signal}」",
            "expected_information": [signal],
            "should_change_topic": False,
        }
    # 无明确缺口，使用通用兜底追问动作
    return {"action": build_rule_fallback_probe_action(topic), ...}
````

规则降级能保证 Decide 的输出格式合法，也能保证基本的面试逻辑连续，只是追问质量不如 LLM。

##### Act 节点：模板降级

如果调用大模型生成提问话术失败，会执行services/interview/actions.py的模板兜底逻辑：先提取候选人回答内容做过渡承接，再根据决策类型匹配预设提问模板。

````
# offer-agent/backend/app/services/interview/actions.py（节选）
def build_template_fallback_act_message(
    action, topic, *, latest_answer="", target_signal="", last_action="", verify_contradiction=False,
) -> str:
    """     
    LLM生成话术失败时的模板兜底函数     
    基于固定模板拼接提问，保证输出通顺可读     
    """
    bridge = _build_bridge(latest_answer)   # 从 latest_answer 截取要点作承接
    signal = str(target_signal or "").strip()
    question = _probe_question_for_action(action, topic=topic, target_signal=signal)
    if bridge and question:
        return f"{bridge}{question}"
    ...


def _probe_question_for_action(action, *, topic, target_signal) -> str:
    """根据决策动作，匹配预设固定提问模板"""
    templates = {
        "probe_tradeoff": f"{signal_prefix}当时还考虑过哪些方案？最终选择这个方案的主要约束是什么？",
        "probe_ownership": f"{signal_prefix}你个人具体负责了哪些工作？结果是如何衡量的？",
        ...
    }
````

两层降级的差异

| 层次 | 降级方式 | 保证什么 | 不保证什么 |
| --- | --- | --- | --- |
| Decide | 规则推导 | 结构合法、逻辑连续 | 追问质量与 LLM 等价 |
| Act | 模板组合 | 话术可读、格式正确 | 语言自然度与 LLM 等价 |

两层降级都不尝试模拟 LLM 的专业判断能力。降级的目标是让面试能继续跑下去，不是让候选人感知不到差异。
