# 为什么面试需要三层记忆？

目录路径：实战项目 / AI面试智能体 / V2 版本优化 / 四大优化点 / Agent 记忆体系：短期、中期和长期记忆 / 为什么面试需要三层记忆？

[原页面](https://acn2lw4rwc26.feishu.cn/wiki/S14Kwck9iiY1TYkeFC6cZ4pPn7b)

如果你让一个 Agent 做面试官，第一个会遇到的问题不是它能不能提问，而是它怎么记住东西。

记住什么？表面上是记住候选人说了什么。但仔细想，这件事包含三个不同的维度。

1. 当前这道题在聊什么

——短期记忆

候选人刚说的那句话、面试官上一轮的追问，这些是做下一个决定的直接依据。这类信息的特点是：最近的最有用，时间稍长就可以被压缩掉。

2. 这场面试到目前为止证明了什么

——中期记忆（也叫工作记忆）

某个项目有没有说清楚项目职责？回答里有没有具体指标？这些是跨越多轮对话积累下来的结构化事实。单靠最近几条消息看不到这个全貌，需要专门的数据结构来维护。

3. 这个候选人历史上哪些地方反复出问题

——长期记忆

这不是本场的数据，而是多场练习下来沉淀的规律。比如某个候选人在「项目结果量化」上连续三场都没有覆盖，这是值得在练前推荐里提醒的信息。

#### V1 的状态

V1 没有专门设计记忆结构。backend/app/agent/workflow.py 里的 build_follow_up_with_llm 每次只拿当前题目和候选人的上一条回答调用 LLM：

````
# offer-agent/backend/app/agent/workflow.py（节选）
def build_follow_up_with_llm(*, question, answer, ...):
    # Prompt 只注入「当前题目 + 上一条回答」，不含历史轮次
    prompt = f"""
当前题目: {question['prompt']}
上一轮回答: {answer}
"""
    return _spoken_message_from_llm(client, prompt=prompt, ...)
````

每次 LLM 调用都是无状态的。对话第三轮时，Agent 不知道第一轮候选人说了什么；当前主题结束后，下一个主题的 Agent 对之前发生的事一无所知；整场面试结束后，没有任何东西记录下哪些信号已经被覆盖、哪些还没有。

这带来了三个直接问题：

- 追问方向没有依据，只凭 LLM 在当轮的感觉猜测；

- 无法判断候选人有没有覆盖面试规划里期望的信号；

- 多场练习的数据完全孤立，薄弱点无法被识别。

#### V2 的三层实现

V2 把三个维度拆成三层独立实现：

| 记忆层次 | 定位 | V2 实现 | 用途 |
| --- | --- | --- | --- |
| 短期记忆 | 当前主题的对话上下文 | topic_messages（当前主题的消息列表，按 topic_id 筛选）+ topic_summaries（已完成主题的压缩摘要字典） | 进入 Observe，让 Agent 知道这道题聊到了哪 |
| 中期记忆 | 本场考察进度与信号缺口 | working_memory（按主题组织的 claims 声明、evidence 证据、missing_information 缺口等结构化字段） | 进入 Decide，驱动追问方向 |
| 长期记忆 | 跨场次薄弱点规律 | learning_profiles（按用户+简历+岗位聚合的历史档案）+ outcomes（每场结果快照） | 进入练习推荐，供候选人参考采纳 |

三层之间有一个关键原则——各层只服务对应的决策，不混用：

- 短期记忆进 Observe，让 Interview Agent 知道这道题聊到了哪。

- 中期记忆进 Decide，让 Interview Agent 知道哪些信号还没有覆盖。

- 长期记忆只影响评估报告里的练习推荐和「与上一场对比」，不进入面试过程的对话流、Decide、Act，也不影响本场评分主路径。

![页面图片](../assets/358-809baec2ef305e1a.png)

这个隔离不是技术限制，而是设计决策。如果长期记忆里记着「这个候选人上次对项目管理的回答很差」，而这个记忆进入了本场的评分，就意味着本场的评分结果混入了上一场的历史，候选人对此毫无感知，评估的公正性也就消失了。

后面三篇分别展开每一层的具体实现，以及每一层为了保证这种隔离做了哪些工程上的取舍。
