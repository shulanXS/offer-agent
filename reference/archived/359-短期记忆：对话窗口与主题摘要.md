# 短期记忆：对话窗口与主题摘要

目录路径：实战项目 / AI面试智能体 / V2 版本优化 / 四大优化点 / Agent 记忆体系：短期、中期和长期记忆 / 短期记忆：对话窗口与主题摘要

[原页面](https://acn2lw4rwc26.feishu.cn/wiki/B6Fdw3UfGi4SNvkzCB0cV7XWnGY)

短期记忆的核心作用是提供对话上下文：让 Interview Agent 在每次做决策时，能看到足够的对话历史，知道当前主题聊到了哪、之前的主题讨论了什么。

一场 45 分钟的面试，可能覆盖 4 到 5 个主题，每个主题 2 到 3 轮问答。如果把所有消息原封不动地传给每次 LLM 调用，Prompt 体积会越来越大，而且大量的内容和当前决策无关。短期记忆要解决的，就是这个问题：保证 Agent 在任意时刻都能看到足够的上下文，但不用看全部历史。

#### V1 的做法

V1 没有处理这个问题。所有消息塞进一个列表，每次调用 LLM 都带上全量历史。在会话较短的情况下，这能跑，但随着对话轮数增加，会出现两个问题：一是 Prompt 超出窗口限制，二是早期的无关消息干扰了当前决策。

#### V2 的两级结构

V2 把短期记忆拆成两部分，分别处理不同的需求。

##### topic_messages：当前主题的消息线程

这是对话窗口最核心的部分。回答节点按 meta.topic_id 从全量消息里筛出当前主题线程：

````
# offer-agent/backend/app/agent/interview/nodes/ingest.py（节选）
current_topic_id = str(current_topic["id"])

# 从全量消息里按 meta.topic_id 筛出「当前主题」线程
topic_messages = [
    message
    for message in state["all_messages"]
    if str((message.get("meta") or {}).get("topic_id", "")) == current_topic_id
]
````

这样，Decide 看到的始终是当前主题下完整的几轮问答，既不会因为消息太少丢失上下文，也不会因为早期主题的内容污染当前的判断。

##### topic_summaries：已完成主题的摘要

切题之后，历史主题的消息就不再需要原文，但 Decide 有时需要知道之前讨论了什么，比如判断「这个候选人有没有在之前的主题里已经提到过项目结果」。这时读的不是全量消息，而是 topic_summaries，一个按主题 ID 索引的摘要字典。

摘要在切题时自动生成，有两条路径：

1. 对话较短时，走规则生成

代码读取主题的 expected_signals，在候选人的回答里做关键词匹配，输出「已涉及哪些信号、还缺少哪些信号、回答要点截取」的结构化摘要：

````
# offer-agent/backend/app/services/interview/topic_summary.py（节选）
def build_rule_topic_summary(*, topic, topic_messages, user_answer) -> str:
    combined_user_text = _collect_user_text(topic_messages, fallback=user_answer)

    # 在候选人原话里做关键词匹配，对照 plan 的 expected_signals
    covered_signals = _match_plan_signals(topic, combined_user_text)
    missing_signals = _missing_plan_signals(topic, covered_signals)

    signal_part = ""
    # 有已覆盖信号 → 写入摘要
    if covered_signals:
        signal_part = f"已涉及期望信号：{'、'.join(covered_signals)}。"
    # 仍有缺口 → 最多列 3 条
    if missing_signals:
        signal_part += f"待补信号：{'、'.join(missing_signals[:3])}。"
    # ... 拼接主题名、objective、要点摘录
````

2. 对话较长时，走 LLM 压缩

LLM 拿到完整的对话历史，生成 80 到 220 字的中文摘要，保留候选人的原话要点，并点名已讨论的 plan 信号。

````
# offer-agent/backend/app/services/interview/topic_summary.py — _build_llm_topic_summary（节选）
prompt = f"""
请将下列主题对话压缩为 1-3 句中文摘要，供后续面试轮次参考。
要求：
1. 只返回 JSON：{{"summary": "..."}}
2. 保留候选人原话要点，不得编造未出现的事实
3. 若对话涉及 plan 期望信号，在摘要中点名已讨论的信号（使用 plan 原文）
4. 80-220 字
...
对话：
{_format_topic_messages(topic_messages)}
"""
payload = client.generate_json(prompt, ..., operation_name="interview_topic_summary")
summary = str(payload.get("summary", "")).strip()
````

举个例子：「项目所有权」主题预设需要收集三类关键信息（expected_signals）：职责边界清晰、个人贡献可量化、结果指标。候选人在该主题完成三轮沟通后切换下一主题，系统会自动生成一份主题摘要 topic_summary，示例内容如下：

````
主题【项目所有权】：
已涉及期望信号：职责边界清晰、个人贡献可量化。
待补信号：结果指标。
要点摘录：候选人描述负责订单服务整体设计与落地，提到了个人职责范围，
但未给出可量化的结果数据。
````

这份摘要会存入全局状态的 topic_summaries ["topic-1"] 中。完成主题切换后，该主题下完整的原始对话消息就不再塞入大模型提示词，只传递精简摘要，减少上下文冗余。

#### 短期记忆如何进入 Observe

build_observe_context 里，两类短期记忆被分别放入上下文字段：

- topic_messages：作为当前主题的对话历史，拼入 observe_context 的消息线程部分

- topic_summaries：以摘要形式写入 observe_context 的「已完成主题」字段

````
# offer-agent/backend/app/services/interview/context.py（节选）
def build_observe_context(*, plan_json, runtime_state, topic_messages, latest_answer, ...):
    # 已完成主题的摘要字典（切题时写入 runtime_state）
    topic_summaries = runtime_state.get("topic_summaries") or {}

    # 当前主题消息：保留最近 N 条 / 不超过字符上限
    context_topic_messages = trim_topic_messages(topic_messages)

    return {
        "current_topic": _find_topic(plan_json, current_topic_id),
        "topic_messages": topic_messages, # 当前主题原文（完整）
        "context_topic_messages": context_topic_messages, # 裁剪后版本，控制 Prompt 体积
        "topic_summaries": topic_summaries,
        "latest_answer": latest_answer,
        "memory_context": resolved_memory, # 中期记忆，与短期记忆并列注入 Decide
        ...
    }
````

Observe 组装完成后，observe_context 整体传给 Decide。Decide 读到的就是：当前主题的完整问答线程，加上过去已完成主题的摘要。Decide 不需要读完整的历史消息，但能通过摘要知道全局的信号覆盖状态。

摘要里标注的信号覆盖情况，也为中期记忆的工作记忆机制打了基础：两者合并后，形成更准确的缺口判断。

#### 整体流转路径

topic_messages / topic_summaries

→ Observe（build_observe_context 组装 observe_context）

→ Decide（格式化后写入 Prompt）
