面试评估有两种做法。

第一种：面试结束后，把完整的对话记录塞给 LLM，让它读完之后给出评分和分析。V1 用的就是这种方式。

第二种：在面试过程中持续提取结构化证据，评估时消费这些证据，而不是重读对话。V2 的做法。

这两种方式的差异不只是技术实现不同，它们代表了对「评估」这件事的不同理解。

#### V1 的问题

V1 版本通过重读对话打分，看起来很直观，但有几个根本性的问题：

- LLM 在评估时必须「现编」证据。它读完对话，决定给某个能力 3 分，然后需要找一些候选人说过的话来支撑这个分数。但这个顺序是有问题的：分数先有了，证据是找来凑的。LLM 不会去说「我找不到足够的证据，所以无法给出这个分数」，它会从对话里选几句话，把它们组织成看起来合理的理由。

- 重读对话无法区分「真的没说」和「说了很多但我漏看了」。一段 45 分钟的面试对话很长，LLM 在单次调用里读完之后，覆盖某个细节的概率是有限的。评分结果的稳定性因此很差，同样的对话跑两次，结果可能不同。

- 评分维度与真实面试考察目标脱节。能力维度从哪来？V1 的做法是给 LLM 一套预设的评分维度，比如「项目经历」「技术深度」「沟通能力」。但这套维度和本场面试的考察计划之间没有绑定关系。这场面试计划考察的是「项目所有权」和「系统设计取舍」，评估却在评「沟通能力」，两套体系是脱节的。

#### V2 的做法：评估是消费者

V2 的核心改变是：Evaluation Agent 不生产证据，它消费证据。整套流程会在面试过程中持续收集证据：候选人每一轮回答结束后，extract_evidence 节点都会从当前回答里提炼关键观点与对应佐证，存入工作记忆。每一条证据都会完整记录三项信息：

- quote：候选人的原始原话

- matched_signal：匹配到本次面试计划里对应的考察要点

- strength：这条证据的支撑力度

等到整场面试结束，工作记忆里就按不同主题攒好了完整的证据素材。

正式进入评估环节后，project_evaluation_memory 会整理工作记忆中的内容，按面试计划的主题分类打包。每个分类桶里包含三类信息：该主题下全部证据、已经覆盖到的考察要点、当前还缺失的考察要点。

````
# offer-agent/backend/app/services/interview/memory/project.py — project_evaluation_memory 输出（节选）
for topic_id in all_plan_topic_ids(plan_json):
    expected_signals = plan_signals_for_topic(topic)
    # strength ≥ 0.5 且匹配 signal → 计入 covered
    covered = sorted(covered_signals_for_topic(evidence, topic_id))
    missing = [s for s in expected_signals if s not in set(covered)]
    evidence_by_topic[topic_id] = {
        "evidence": topic_evidence,
        "covered_signals": covered,
        "missing_signals": missing,
    }
````

这个投影是确定性的，不经过 LLM，从工作记忆直接算出来。Evaluation Agent 拿到的是干净的结构化输入，不是原始对话。

#### 评估维度来自 plan_json，不另建

V2 的评估维度 = plan_json 的主题列表，没有第二套。Evaluation Agent 不允许自己创造能力维度，也不允许引入 plan 之外的考察方向。

````
# offer-agent/backend/app/services/interview_evaluation/competencies.py — derive_competencies（节选）
# 遍历 plan 主题，不另建评估维度
for topic_id in all_plan_topic_ids(plan_json):
    topic = find_plan_topic(plan_json, topic_id)
    bucket = evidence_by_topic.get(topic_id) or {}
    evidence = list(bucket.get("evidence") or [])
    covered = set(bucket.get("covered_signals") or [])
    expected = plan_signals_for_topic(topic)
    status = _derive_status(...)
    # unverified → score 为 None
    score = _derive_score(...)
    evidence_references = build_evidence_references(evidence, topic_messages)
````

这样设计的原因是：Planning Agent 在面试前确定了「这场面试考察哪些方向、每个方向期望看到什么信号」，Interview Agent 按照 plan_json 来追问，Evaluation Agent 也必须按 plan_json 来评分。如果评估能自己创造维度，它和前两个 Agent 之间的关系就断开了，面试计划形同虚设。

#### 证据链的完整流向

![页面图片](../assets/363-acf4006ff789ca19.png)

整套评估链路完全单向可追溯。最终打分用到的每一处依据，都能顺着链路逐层溯源：评分结果里的证据引用 → 候选人原始原话片段 → 单条提取证据 → 匹配到的考察指标 → 面试方案预先设定的考察要点，每一环都留有完整记录，全程有据可依。

这正是“先积累证据，后给出评判”的核心优势：最终评分结论依托面试全程持续沉淀的客观素材，而非模型读完对话后形成的主观整体印象。
