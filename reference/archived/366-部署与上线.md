#### 特殊点一：SQLite 文件的持久化

offer-agent 用 SQLite 作为数据库，这是它和前两个教程项目最大的不同。SQLite 是一个文件，所有数据都存在这个文件里。

1. 路径必须用绝对路径

相对路径会让数据库文件出现在进程的工作目录下，而工作目录不固定，Gunicorn 在哪个目录启动，文件就在哪里。下次重启进程，工作目录可能变了，新文件就创建在别处，原来的数据找不到了。

在 .env 里这样配置：

````
DATABASE_PATH=/home/deploy/offer-agent/data/offer_agent.db
````

注意直接写绝对路径，不需要 sqlite://// 前缀（项目内部用 pathlib.Path 处理路径，不依赖 SQLAlchemy URL 格式）。

在部署服务器上，先手动创建这个目录：

````
mkdir -p /home/deploy/offer-agent/data
````

2. 文件权限

Gunicorn 进程以什么用户身份运行，那个用户就需要对这个目录有读写权限。如果 Gunicorn 用 deploy 用户启动，执行：

````
chown -R deploy:deploy /home/deploy/offer-agent/data
````

3. 备份策略

SQLite 是单文件，备份很简单，直接复制文件就行。在 crontab 里加一条，每天凌晨备份一次：

````
# crontab -e
0 2 * * * cp /home/deploy/offer-agent/data/offer_agent.db \
    /home/deploy/offer-agent/data/backup/offer_agent_$(date +\%Y\%m\%d).db
````

也可以用 SQLite 自带的备份命令，在数据库有活跃连接时也能安全执行：

````
sqlite3 /home/deploy/offer-agent/data/offer_agent.db \
    ".backup /home/deploy/offer-agent/data/backup/offer_agent_$(date +%Y%m%d).db"
````

备份目录同样需要提前创建：mkdir -p /home/deploy/offer-agent/data/backup。

4. 容器化部署的注意点

仓库内暂无 Dockerfile；若自行容器化，数据库文件在容器内，容器一旦重建，数据就丢了。必须把数据目录挂载到宿主机：

````
docker run -v /home/deploy/offer-agent/data:/app/data ...
````

容器内的路径和 DATABASE_PATH 要对应。

#### 特殊点二：多 LLM provider 的 .env 管理

offer-agent 支持四个 LLM provider：OpenAI、Anthropic（Claude）、火山引擎（豆包）、mock。通过 LLM_PROVIDER 环境变量切换，只需要填写对应 provider 的 API key。

一份完整的生产环境 .env 示例，选哪个 provider 就填哪个 key：

````
# 数据库
DATABASE_PATH=/home/deploy/offer-agent/data/offer_agent.db

# JWT
JWT_SECRET=your-secret-key-change-this
JWT_EXPIRE_MINUTES=720

# LLM 配置，选择一个 provider
LLM_PROVIDER=openai
# LLM_PROVIDER=anthropic
# LLM_PROVIDER=volcengine
# LLM_PROVIDER=mock

# 只填你选的 provider 的 key
OPENAI_API_KEY=sk-xxx
# ANTHROPIC_API_KEY=sk-ant-xxx
# VOLCENGINE_API_KEY=xxx
````

如果你要把这个项目部署成公开可访问的 demo，用 mock 模式最省事：

````
LLM_PROVIDER=mock
````

不需要任何 API key，不花钱，响应速度也快。mock 模式返回预设的模拟内容，足够展示完整的用户流程。

因为 offer-agent 用了 settings_customise_sources 排除了系统环境变量，这些已有的变量不会影响本项目。项目只读 .env 文件里的配置，行为是可预期的。

#### 特殊点三：初始数据

数据库建表通过 init_db() 函数自动完成，项目启动时执行一次。这个函数用 executescript 运行建表 SQL，是幂等的——重复执行不会报错，不会清空数据，只在表不存在时创建。

也就是说，服务器上重启项目、重新部署，都不会丢数据。不需要做任何额外操作。

新注册的用户会自动获得5次面试配额，这是注册逻辑里写死的，无需手动干预。

如果你需要给特定用户增加配额，比如给自己的账号增加配额方便测试，直接用 sqlite3 命令行操作：

````
# 查看当前配额
sqlite3 /home/deploy/offer-agent/data/offer_agent.db \
    "SELECT username, quota_remaining FROM users WHERE username = 'your_username';"

# 增加配额
sqlite3 /home/deploy/offer-agent/data/offer_agent.db \
    "UPDATE users SET quota_remaining = quota_remaining + 10 WHERE username = 'your_username';"
````

不需要进后台界面，也不需要重启服务，命令执行完立即生效。

#### 部署验证

部署完成后，按照以下顺序逐个验证。本地开发也可对照第 4 篇的 curl 命令，把域名换成生产地址。

第一步，验证服务是否正常启动。

````
curl https://your-domain.com/healthz
# 期望返回：{"status": "ok", "app": "Offer Agent"}
````

第二步，验证认证接口。

````
# 注册
curl -X POST https://your-domain.com/api/auth/register \
    -H "Content-Type: application/json" \
    -d '{"username": "testuser", "password": "Test1234"}'

# 登录，拿到 token（字段名 access_token）
curl -X POST https://your-domain.com/api/auth/login \
    -H "Content-Type: application/json" \
    -d '{"username": "testuser", "password": "Test1234"}'
````

第三步，验证简历上传。

````
curl -X POST https://your-domain.com/api/resumes/extract \
    -H "Authorization: Bearer <your-token>" \
    -F "file=@/path/to/test_resume.txt"
````

第四步，验证 SSE 接口。 创建面试须用 POST 且带 JSON body；--no-buffer 让事件逐条输出：

````
curl --no-buffer -N -X POST https://your-domain.com/api/interviews/stream \
    -H "Authorization: Bearer <your-token>" \
    -H "Content-Type: application/json" \
    -d '{"resume_text": "张三\nJava开发工程师\n3年经验\n熟悉Spring Boot", "target_role": "后端开发工程师", "job_title": "Java开发工程师", "language": "Java", "difficulty_level": "进阶", "technical_skills": ["Java", "Spring Boot"], "highlights": ["负责过电商后端"]}'
````

能看到 session、delta 等事件分批次输出，说明 SSE 和 Nginx 配置都正常。生产环境若启用 RAG，可在 start.sh 前设置 AUTO_INDEX_RAG=true，或在部署脚本里手动执行 python3 scripts/index_role_knowledge.py。

如果 SSE 接口没有流式效果，整个响应一次性返回，回去检查 Nginx 配置里有没有 proxy_buffering off。这是 SSE 部署最常见的问题。
