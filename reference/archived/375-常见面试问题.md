# 常见面试问题

目录路径：实战项目 / AI面试智能体 / 常见面试问题

[原页面](https://acn2lw4rwc26.feishu.cn/wiki/FiLBwNwLUiWigIknkQncwELenib)

以下题目围绕 Offer Agent（AI 模拟面试官）整理，适合项目复盘、技术面试与自我演练。每道题后面附候选人角度的参考回答，并补充一条高频追问与对应回答，方便顺着一个问题继续展开。

#### 1.
先简单介绍一下这个项目，它解决什么问题？

我参与做的是一款 AI 模拟面试产品，叫 Offer Agent。求职者上传简历、选好校招还是社招、目标岗位和难度，系统会先给出这场 45 分钟大概考哪些方向，确认后再进入模拟对话，最后出一份能点开看原话依据的评估报告，还可以按薄弱项再练。对我来说，它不是一个「调大模型聊天」的 Demo，而是一条完整链路：有计划、能恢复、能解释，用户愿意反复用。

高频追问：如果只用一句话概括，你会怎么说？

追问回答：这个项目是把「模型不稳定」包进「面试流程稳定」里——用户得到的是一场像真面试的练习，而不是碰运气的一次生成。背后靠的是计划确认、对话边界和证据评分，让每次练习说得清、评得明。这也是它和普通 Chat 类产品最大的差别。

#### 2.
这个项目做过迭代吗？和最早能用的版本比，变化大不大？

做过，而且变化挺大的。最早那版能跑通主链路，但是固定几道题，每道题基本只追问一次，评估也是结束后把聊天记录丢给模型写总结。后来我参与迭代时，把形态改成了：先生成面试计划、用户确认锁定，再按多个考察方向动态追问或换题，整场有 45 分钟和轮数上限；评估改成面试过程中就在积累证据，报告里的分和计划里的考察点一一对应。本质上是从「脚本式问答」升级成「计划驱动 + 动态面试 + 可解释评估」。

高频追问：为什么要动这么大，而不是小修小补？

追问回答：因为我们发现小修解决不了三个真实痛点：不像真实面试、问的和评的对不上、出了问题很难查是模型还是流程的锅。只在 Prompt 上打补丁，用户体感还是「假」。所以要在产品阶段上重划：先确认考什么，再开聊，最后按同一份计划评。改动大，但后面加记忆、加边界、加降级才有抓手，不然都是在黑盒上堆功能。

#### 3.
你在项目里主要负责什么？

我主要负责后端这条主链路：面试计划的生成与确认、动态面试对话编排，以及和评估报告的衔接；中间也参与了工作记忆、证据提取、Planning 阶段 RAG 接入，还有一批降级和单测。前端我配合做了计划页、Live 面试页和评估页的状态对接。

高频追问：如果只能讲一个你亲手做的模块，你讲哪个？

追问回答：我会讲动态面试这一轮回复的编排：从收回答、检查时间和轮数、抽证据、做决策，到生成话术或切题，全程有日志和降级。有一次模型服务不稳定，就是靠决策层的规则降级和话术模板把流程撑住的，我顺着 trace 把整条链路查清楚，也在这个模块上补了测试。这个例子能讲清我既做 Agent 逻辑，也做工程兜底。

#### 4.
技术栈怎么选的？为什么前后端分开？

后端我选 FastAPI，因为项目本质是 API 驱动：登录、上传简历、生成计划、SSE 流式回复、拉评估，都要清晰的接口和类型约束，FastAPI 开发效率够高。前端用 React + Vite，要承载配置、计划预览、正式面试、报告和会话列表，状态很多，还要接 SSE，用 SPA 更合适。前后端分开，我改 Prompt 或改 Agent 时不用动页面，前端同学调交互也不用碰 Python 工作流，联调边界清楚。

高频追问：团队很小的话，你还会拆前后端吗？

追问回答：会，因为交互复杂度在这里摆着。我们这场面试不是单页表单，而是多阶段状态机加长链路 AI 调用，拆开的维护成本我能接受。如果是内部小工具、几个 CRUD 页面，我可能会前后端放一起；但这个产品要长期迭代 Agent 和页面，分离更划算。实际协作里，接口契约清晰也减少了扯皮。

#### 5.
后端代码有分层吗？大概怎么分的？

有的。我习惯分成五块：api 只管 HTTP、鉴权和参数校验；services 管会话、额度，以及把规划、面试、评估三个流程串起来；agent 目录里放和模型相关的工作流和 Prompt，只给 service 调，不直接对外；llm 是统一的模型工厂；db 是 SQLite 持久化。这样我换一家模型供应商，主要动 llm 层；改配额或会话状态，动 service；改追问策略，动 interview 的 agent，不会整个项目一起改。

高频追问：为什么不把逻辑都写在路由里？

追问回答：我早期也试过在 route 里直写，很快就读不懂了，而且没法单测。比如「计划校验失败重试」这种逻辑，放在 service 和 validator 里，我可以不启动 HTTP 就测。路由层我坚持只做薄封装：鉴权、把 body 转成 dict、调 service、返回响应。后面加 trace、加错误码，也是在这一层统一处理，业务代码保持干净。

#### 6.
为什么用 LangGraph，而不是几个普通函数串起来？

因为每轮回答背后不是一次函数调用就结束。我要记轮次、先看有没有超时或该强制换题、再从回答里抽证据、再决策、再生成话术，中间还有「重复追问要不要拦」这些分支。用 LangGraph 把这些收成显式节点和条件边，比在一个大函数里嵌套 if/else 好维护。另外我把写库放在图外面，图里节点尽量纯，这样我可以构造假 state 直接 invoke，测分支对不对。

高频追问：不用 LangGraph 最大的问题是什么？

追问回答：最大问题是状态和分支会散掉。短期写一个 compose_response 能跑，但加上证据、边界、降级之后，谁改了一处 if，另一处静默坏了很难发现。用图至少「这轮走了哪条边」能在设计上看见。我们后来排查一次「该切题没切题」，就是顺着图的边界节点定位的；如果是散函数，我要翻很多层才能拼出完整路径。

#### 7.
项目里几个 Agent？分别做什么？

我们拆成三个：Planning 负责生成本场考察计划，包括几个主题、每个主题期望看到什么信号；Interview 负责正式对话里追问、换方向或结束；Evaluation 负责出报告。我刻意让它们不要各自读配置各出各的题，而是 Planning 产出计划，用户确认后锁定，后面两个只认这份计划。这样报告里评的「项目深度」，就是计划里写的那道项目题，不会出现问 A 评 B。

高频追问：它们之间靠什么对齐？

追问回答：靠确认后的面试计划这一份 JSON。用户点确认，我们会记下锁定的面试计划 ID，Interview 开聊和 Evaluation 打分都只读这一版 JSON，不允许中途换考察清单。这是我个人觉得整个项目最关键的协作设计，解决了多 Agent 最容易出现的「各说各话」问题。如果计划要改，必须走重新生成，而且有次数限制。

#### 8.
从用户点「生成计划」到看到评估报告，后端主链路怎么走？状态怎么变？

我会按时间顺序讲：用户提交配置后，Planning 生成计划，会话处于计划待确认；用户确认后变成计划已锁定，并记下这一版计划的 ID；用户点开始面试时激活会话，扣减额度，把首条面试官消息写进消息表，状态变为对话中；之后每提交一次回答，走一轮「收回答 → 抽证据 → 决策 → 生成话术或切题」，消息和运行状态落库；用户结束或到时强制结束后进入评估中，后台按锁定的计划和工作记忆出报告，最后变为已完成。前端只是按状态进计划页、对话页或报告页，真数据都在 SQLite 里。

高频追问：额度是在哪一步扣的？

追问回答：在激活正式面试时扣，不是刚生成计划就扣。这样用户可以先预览、确认方向，甚至重新生成有限次数，满意了再消耗一次练习额度。如果生成计划就算一次，用户会觉得「还没开聊就少了机会」，和产品设计不一致。激活时还会初始化当前主题、工作记忆等运行状态，并生成第一句开场提问。

#### 9.
为什么面试前要多一步计划预览和确认？不能直接开聊吗？

两个原因。对用户来说，他得知道这场会考项目还是系统、会不会偏校招基础，方向不对可以换策略再生成，而不是一点开始就扣额度。对系统来说，确认后的计划就是后面所有环节的锚点，对话和评分都按这份来，减少漂移。我在产品上也把它设计成明确的人机协作：AI 出方案，人做审批，而不是全自动黑盒开聊。

高频追问：用户不满意计划能一直重新生成吗？

追问回答：不能。我们限制了额外重新生成的次数，超限后端直接返回错误，前端按钮也会灰掉。这是刻意的产品边界：否则用户可以一直刷，直到刷到熟悉的题，练习价值就没了。次数写死在代码里，不是让模型自己判断「差不多了」。用户真不满意，可以选不同调整策略，比如加强系统设计或更贴 JD，而不是无限刷新。

#### 10.
计划里已经有开场问了，为什么点「开始面试」还要等一会儿，不能立刻进对话页？

因为用户看到的第一句话，不是前端直接从计划里抄出来展示，而是激活接口在服务端跑完才落库。激活时要扣额度、初始化运行状态，还要把计划里的开场问改写成更口语的一句——这一步通常要调一次模型；模型失败就退回计划原文。计划页上往往是「确认并开始」连着两次请求：先确认锁定，再激活写首条消息，按钮会显示「正在进入…」。对话页再拉一次会话数据，所以体感上会等几秒，不是路由慢，而是首问要在服务端生成并持久化。

高频追问：能不能优化成秒进对话页？

追问回答：可以，方向有几种：激活时先用计划原文占位展示，后台再替换口语化版本；或者在用户确认计划时就预生成首问；或者确认和激活合并成一个接口减少往返。当前实现优先保证「进对话页时库里已有完整首条消息、状态已是进行中」，避免页面上有字但后端还算没开始。我如果继续迭代，会先加耗时观测，看激活到底慢在扣库还是开场口语化，再决定值不值得做预生成。

#### 11.
面试计划里到底存什么？每个主题的追问是不是都提前写死在计划里？

计划存的是一场 45 分钟的考察蓝图，不是逐字稿。整场有主题列表和时长、轮数等边界；每个主题里有名称、考察目标、期望信号、评分参考、一条开场问、追问策略提示等。用户在预览页通常只看到主题名、是否必考、大概时长，看不到完整开场问，避免提前背题。追问不是把第二句、第三句问话都写好，而是给方向和信号，正式聊的时候根据你当场回答动态决定下一句。所以是「带开场问的主题计划 + 现场动态追问」，不是早期那种固定几道题、每题固定追一次。

高频追问：那计划里的 max_rounds 是不是严格执行的？

追问回答：计划里每个主题有 max_rounds 字段，主要表达「这个方向预期聊几轮」，校验时也会限制在合理范围。但运行时强制切题、结束，用的是代码里的全局边界，比如单主题最多几轮回答、全场最多 12 轮、45 分钟倒计时等，不是运行时逐条读每个主题的 max_rounds。计划负责「考什么、怎么判」，边界模块负责「什么时候必须停」，两层分工不同，面试里我会讲清楚，避免说成「计划里写几轮就绝对几轮」。

#### 12.
正式面试时，怎么决定继续追问还是换下一个考察方向？

不是早期那种「每题固定追问一次就切」。我会看当前主题计划里还缺哪些信号、工作记忆里已经有哪些原话证据、这个主题聊了几轮、整场还剩多少时间和总轮数。模型负责软判断，但会先输出结构化决策，比如继续追哪个点、为什么，再单独生成对用户说的话。硬规则如超时、超轮数，在决策前就由代码强制处理，模型碰不到。

高频追问：模型要是决策错了怎么办？

追问回答：分两层兜底。硬边界错了理论上不该发生，因为切题和结束是代码管的；软判断偏了，还有规则降级，可以从缺口列表里选下一个该追的信号，用模板拼一句追问。用户体感可能是追问没那么聪明，但面试不会卡死。我们 CI 里还有专门测「模型全线失败时图还能跑完」的用例，我改过降级逻辑后都会跑这套，避免改坏。

#### 13.
为什么要把「决策」和「说出话术」拆开？

因为我需要知道系统「想干什么」，而不只是「最后说了什么」。合成一次调用时，日志里只有一句面试官的话，出问题了只能猜。拆开后，决策层留下 action 和 reason，我可以断言、可以复盘；话术层单独优化语气，甚至换一套更口语的 Prompt。有一次 Act 的 LLM 超时，Decide 的结果还在，模板顶上一句，用户仍能继续答，这就是拆分带来的工程收益。

高频追问：这和早期「一个 Prompt 出下一句」本质差别是什么？

追问回答：早期等于把推理和表达塞进黑盒，看起来能聊，实际上不可审计。现在是先结构化决策、再生成自然语言，和真实团队里「先定议程再组织措辞」类似。对产品来说，用户觉得追问更连贯；对开发来说，我能分清是决策错了还是话术错了，调优路径清楚很多。这也是后来能加证据、加边界的前提，不然所有问题都会糊在一个 Prompt 里。

#### 14.
整场 45 分钟、最多多少轮，这些规则交给模型管吗？

我不交给模型。45 分钟、单主题最多几轮、整场最多 12 轮回答、重复追问上限，这些都是代码在决策前检查的。模型适合回答「这个点还值不值得追」，不适合回答「第 12 轮必须停」，后者必须精确、可测。我把这类规则放在 boundaries 模块里，单测可以直接构造「已经 12 轮」的状态，断言一定结束，不依赖模型脾气。

高频追问：LLM 调用失败呢，面试就停了吗？

追问回答：不会停，每一环都留了兜底：

- 出计划：模型生成失败 → 用模板拼一份能用的面试计划

- 决定下一步：模型决策失败 → 用规则看「还缺什么信号」，该追问还是该换题

- 组织话术：模型写话失败 → 用固定模板拼一句能听的话

- 开场第一题：实在不行 → 直接用计划里写好的原题

所以不是「模型一挂，用户就白等」，而是「模型挂了，系统换套路把流程走完」。测试里还会故意用一个一调用就报错的假模型，跑完整场面试，检查有没有回复、状态有没有正常更新。

#### 15.
聊天越来越长，上下文会不会爆？怎么记「之前说了什么」？

会爆，所以不能每次把全场聊天记录都塞给模型。我的做法是几层配合：当前考察方向保留完整对话；已经聊完的方向压成短摘要；每轮再从回答里抽结构化证据，记候选人原话和对应哪个考察点，供下一步追问和最终评分。只靠消息列表，token 撑不住，也很难稳定回答「这个信号到底考到了没有」，因为模型每次都要重新读长文本做判断。

高频追问：摘要和结构化记录有什么区别？

追问回答：摘要是切题时生成的文字纪要，给后面轮次当背景，让人知道「前面项目题聊过什么」；结构化记录是工作记忆里的证据和缺口列表，给代码算「还缺什么」、给报告引哪句话。摘要不要替代结构化记录，我在设计里刻意分开：一个偏可读，一个偏可算、可评。合并成一种格式，要么评分不可追溯，要么 Prompt 里全是不可控的自然语言。

#### 16.
用户每答一轮，背后大概要调几次模型？为什么出计划可以校验重试三次，对话里失败一次就降级？

正常一轮回答，图里典型是三次模型相关步骤：从回答里抽证据、决策下一步动作、生成追问话术；如果边界判定必须直接换题或结束，会跳过决策和话术，走代码分支。所以用户觉得「回一句要等很久」，往往不是因为只调了一次，而是串行多次。出计划发生在开聊前，用户本来就在等，计划 JSON 又大又复杂，校验不过可以带错误信息最多重试三次，仍失败还有模板计划。对话是实时的，每步再重试三轮，延迟会成倍上去，而且决策输出相对简单，有规则和模板能兜底，所以对话里模型失败通常一次就降级，保证「聊得下去」优先于「等模型再猜两次」。

高频追问：那延迟主要卡在哪一步？

追问回答：在没有打点之前我也只能猜，经验上抽证据、决策、生成话术都会占时间，且是串行的。所以要先上运行时观测，看每步耗时和降级率，再决定是合并 Prompt、并行能并的部分，还是只给「生成话术」单独做流式。我不会为了少等一两秒牺牲边界和证据链，但会优先优化占比最大的那一两步。这也是我后面想先做观测再动架构的原因。

#### 17.
用户连点提交、或者上一句还没生成完又发一条，系统怎么处理？

有两层保护。一层是运行状态里的「回复处理中」标记：开始处理一轮回答时打上，结束或异常时清掉；处理中再提交会返回明确错误，前端也会禁用发送，避免半句话状态下又收新回答。另一层是重复追问拦截：如果决策层想追的内容和上一轮刚追过的完全一样，图会走「重复被拦截」分支，强制换切题或结束路径，避免面试官卡在同一句话上。刷新页面时还有陈旧锁清理逻辑，防止异常中断后锁一直占着。这些和持久化配合，保证状态和消息序列不会乱。

高频追问：如果用户断网了，锁会不会一直占着？

追问回答：会考虑异常场景。锁占着时用户确实不能再发，但我们有陈旧锁 reconciling：如果会话更新时间超过阈值，或者最后一条已经是 assistant 消息，会认为上一轮其实已经结束，自动清锁。这样用户刷新或重进页面通常能继续，不会永远卡在「处理中」。当然根本解决办法还是把每轮处理做短、做稳，并在前端展示「还在想」，减少用户重复点击的冲动。

#### 18.
评估报告的分数是怎么来的？结束后把对话全文给模型打行吗？

我不这么做。全文打分的问题是模型容易先形成整体印象再凑理由，同一对话跑两次分差可能很大，也没法稳定引用原话。我们的路径是：面试过程中就在收集证据，结束时按面试计划里的主题投影成证据桶，再用规则推导三态和分数；模型只负责把报告写得更顺一点，失败就用规则兜底。用户点开某一题，能看到支撑评价的原话，这是产品设计时就定下的要求。

高频追问：用户问「这个分凭什么」，你怎么答？

追问回答：我会让他看报告里这一主题的证据引用和考察点覆盖情况，分数不是凭空给的。每个 评分条目对应计划里的一个主题，不是另起一套「沟通能力」「领导力」那种泛泛维度。如果有主题标成未验证，是因为这场没充分聊到或证据不足，不是直接判「差」。这样用户至少知道争议点在哪，而不是和一个黑盒分数争论。

#### 19.
候选人前后说法不一致，系统会怎么处理？报告分数是模型直接打的吗？

前后不一致会在工作记忆里记成「待核实」风险，不会直接扣大分，也不会在描述里用「撒谎、造假」这类定论词；最多发起一次验证性追问，是否真的矛盾要看后续回答和新提取的证据。评估分数不是模型读完聊天即兴打的：面试过程中积累的结构化证据，结束时按主题投影，再用规则推导每个主题的验证状态和分数；模型只可选地润色报告文案，失败也不影响分数。这样「矛盾」和「打分」两条线分开：前者是风险提示，后者必须能点开原话依据。

高频追问：为什么不让模型一起打分，不是更「智能」吗？

追问回答：全文印象分看起来智能，但稳定性差，而且很难向用户解释「凭什么」。我们的产品是模拟面试练习，用户要的是可重复、可对照计划、能申诉依据的评分。规则加证据的方式，同一输入下边界行为可测，未充分聊到的主题可以标未验证而不是硬给低分。模型润色放在叙事层，提升可读性，不碰分数主路径，这是信任和工程可测之间的取舍。如果以后要做「模型辅助校准」，也应该是建议分，不能 silent 覆盖规则分。

#### 20.
如果某个考察方向时间不够没聊到，会因此扣很多分吗？

不会。我会先给主题一个验证状态：充分验证、部分验证、未验证。未验证的不给确定低分，综合分里也不把它当零分拉平均。因为没聊到可能是时间不够、节奏快、或者计划里五个方向只深入了三个，这不等于候选人不会。我在报告里会写清楚「本场未充分验证」，同时给练习建议，而不是简单打一个差分糊弄过去。

高频追问：综合分怎么算才公平？

追问回答：我只拿有有效分数的主题做平均，再换算成百分制。比如计划五个主题，深入聊了三个且都有证据，就用这三个算，不会因为另外两个未验证就把总分红拉下来。这和早期「聊多少算多少、印象分打到底」很不一样。用户反馈里，这条规则减少了很多「明明答得还行分却很低」的误解。

#### 21.
用户贴了 JD，系统怎么用？评估里怎么体现？

JD 是用户粘贴原文进配置，生成计划时会参考，并在和 JD 相关的主题上打标记。评估阶段我不会把 JD 全文逐条核对，只验证计划里标记为 JD 相关的那些考察点，有没有对话证据支撑。没验证到的写「未验证」，不写「不符合 JD」，因为没聊到不等于不满足。这样既用了 JD，又避免报告变成机械的 JD 逐条打分表。

高频追问：为什么不把 JD 每一段都塞进每次模型调用？

追问回答：因为 JD 往往很长，每个 Agent 都读一遍，Prompt 又噪又贵，还容易和简历、计划信息打架。我的做法是计划阶段对齐一次，后面面试主要消费面试计划，评估只验面试计划里和 JD 挂钩的主题。这是信息和职责的分工，不是懒。用户贴 JD 的核心诉求是「考得更贴合岗位」，在计划层解决比在每个追问 Prompt 里重复更干净。

#### 22.
项目里用 RAG 了吗？用在什么地方？

用了，但我接在 Planning 阶段：从 Milvus Lite 里的岗位知识库检索，把命中内容塞进生成计划时的「岗位知识」上下文。开关是 RAG_ENABLED，索引脚本和知识 markdown 在 backend/knowledge 下。检索失败或关掉 RAG，计划照样能生成，走简历加模板降级。

高频追问：为什么不是全流程都上 RAG？

追问回答：面试计划输入相对固定，检索岗位 JD、技能、常见题，收益直观；追问要看当前这一轮回答和工作记忆缺口，评估要看已落库的证据，在这两个阶段硬塞检索，召回什么、何时召回都很难定义，还容易引入噪声。我现在的判断是：计划质量先靠 RAG 抬一档，对话和评分靠计划和证据机制保证，等以后有明确场景再扩，而不是一上来全流程 RAG。

#### 23.
接多家模型 API 时怎么设计的？

我封装了一层 LLM 工厂，业务只调「按 JSON schema 生成」或「生成文本」，不关心底层是 OpenAI、Anthropic 还是火山。配置在 .env 里切 Provider 和 Key。早期有过 mock，后来产品要求必须走真实模型，失败就走规则或模板降级；测试里用故意失败的客户端测降级，不用 mock 假装智能。这样开发、测试、演示的语义都清楚：效果看真模型，可靠性看降级。

高频追问：模型返回的 JSON 经常不规范怎么办？

追问回答：大模型返回的 JSON 经常不规范，我不指望它一次就对。Planning 生成计划后会走 validator，检查主题数量、必考维度、摘要是否泄露完整开场题；不过就把错误写回 Prompt，最多重试 3 次，3 次仍失败就用模板计划。Interview 里 Decide、Act 一般是调用一次，输出经 normalize 校验；解析失败或格式不对不再循环重试，直接降级到规则决策或模板话术，避免脏 JSON 写进数据库。原则是：模型可以偶尔出错，系统边界不能跟着乱——该合法入库的必须合法，主流程必须能继续。

#### 24.
用户等 AI 回复很久，体验上怎么处理？

我会用 SSE 把回复分块推给前端，用户提交后先看到「思考中」占位，不会对着空白屏干等。当前实现是后端先把一整句生成完，再按块推送，属于模拟流式，开发成本可控。因为一轮背后往往多次模型调用——抽证据、决策、生成话术——真 token 级流式要动编排，我先把决策链做对，再用分块 SSE 改善体感。

高频追问：为什么用 SSE 而不是 WebSocket？

追问回答：我们的交互模式是「用户答一句、服务端推面试官一句」，主要是单向文本流，SSE 够用。WebSocket 还要管连接保活、重连、心跳，对这个项目来说是额外复杂度，收益不明显。如果以后要做双向实时打断、或者面试官和用户同时在线协作，我会再考虑 WebSocket；当前阶段 SSE 加 HTTP 更简单，也更好排查。

#### 25.
为什么这类 AI 项目要特别重视日志？

因为问题经常不是抛异常，而是「返回 200 但结果离谱」。可能出在简历抽取、JSON 解析、RAG 没命中、状态没更新、写库失败任意一环。我给请求加 trace_id，Planning、图节点、模型调用都串起来。日志我会记决策 action、命中条数、降级是否触发，但简历全文、用户回答会截断或脱敏，开发环境可以看细一点，生产要克制。

高频追问：和普通 CRUD 项目日志有什么不一样？

追问回答：CRUD 大多看 error stack 就够了；AI 项目大量是 success path 上的质量问题和随机性，所以关键输入输出、决策中间态必须可见。我排查过一次「追问总是重复」，就是靠 decide 的 reason 和 memory 缺口日志定位的，光看 HTTP 200 完全没用。这也是我坚持决策层结构化的原因之一：不仅为了测，也为了查。

#### 26.
为什么要做统一错误返回，而不是到处抛字符串？

前端要区分额度不足、计划已锁定、重复提交、模型超时等不同情况，展示不同提示，有的还能重试。我定了 code、message、trace_id 的统一结构，后端抛错时都走这一套。排查时我可以按 error code 聚合，不用在一堆 detail 字符串里搜。联调时前端同学也知道契约稳定，不用每次后端改一句文案就要跟着猜含义。

高频追问：对用户展示和内部日志会一样吗？

追问回答：不一样。用户看到的是友好短句，加上 trace_id 方便反馈；内部日志可以带更多上下文，比如哪一步降级、哪条校验失败，但敏感字段必须脱敏。我遇到过用户把 trace 贴回来，我能直接在日志里定位到那场会话的完整链路，这种体验靠统一错误模型才做得到。

#### 27.
简历解析为什么先抽纯文本？为什么既要结构化字段又要全文？

因为 PDF、DOCX 后面不管是规则还是 LLM，吃的都是文本，二进制没法直接进 Prompt。结构化字段给页面展示和 Planning 用，比如技能、项目、亮点；全文 resume_text 是兜底，结构化抽偏了还能参考原文。解析失败我会降级到规则抽取，保证用户至少能进下一步，不会在第一个上传页就卡死。

高频追问：结构化结果和原文冲突怎么办？

追问回答：我把它当成「摘要」和「依据」的关系，不假设结构化永远对。冲突时 Planning 和评估更信原文片段，结构化主要用于展示和快速引用。实践里 LLM 抽错年限或漏项目的例子有过，有全文兜底，用户还能继续练，不会被错误字段带沟里去。这也是我坚持两个都落库的原因。

#### 28.
会话状态多吗？怎么区分「还没正式开始」和「正在面试」？

会话状态区分计划生成中、计划待确认、已锁定、正式对话中、评估中等。前端根据状态决定进配置页、计划页、Live 页还是报告页，列表里也不会把「还没点确认」显示成「面试进行中」。刷新页面能从 SQLite 恢复消息和 工作状态，我测过计划确认后刷新，仍回到正确页面，不会丢上下文。

高频追问：计划确认之后还能改吗？

追问回答：同一场不能再重新生成。我已经把执行和评分绑在锁定的那版计划上，允许修改会破坏问评一致。用户想换方向，应该新开一场或走我们提供的练习建议跳转。这是我刻意做的强约束，前期有同学觉得「不够灵活」，但从产品可信度上值得。

#### 29.
有没有做跨多次练习的能力？比如记住哪块一直弱？

在做。多次练习后会把每场评估里的缺口信号聚合，评估页有「和上一场对比」和练习建议，根据历史推荐重点方向，后端 API 有了，配置页 UI 还在完善。我坚持历史不能偷偷进当场对话和当场打分，只能在用户看得见的地方提示，比如报告对比、推荐勾选，否则练习者会觉得「这场明明答好了怎么还按老印象判」。

高频追问：为什么不能让系统「记得上次答得差」就在这次判低？

追问回答：因为本场评估必须只反映本场表现，这是模拟面试产品的公正底线。历史信息的价值是帮用户知道该多练什么，不是替面试官做预设立场。我可以聚合历史薄弱点建议在下次计划里加重某方向，但那是用户采纳之后的事，不是系统暗箱降分或少问，这条边界我在设计文档和代码里都卡死了。

#### 30.
重点练习方向是怎么来的？用户必须选吗？

不必须。配置页我会根据校招还是社招、岗位是前端还是后端，给一组推荐标签，比如项目深挖、系统设计，用户可勾选几个写进聚焦主题，面试计划会偏重这些方向。不选也能生成，系统按简历和岗位默认组织。跨场次的历史薄弱点是另一条来源，需要用户明确采纳才影响计划，未采纳等于没有历史。

⛳

高频追问：推荐方向是模型实时想的还是规则给的？

追问回答：配置页推荐目前是前端规则组合，不是每回现场让 LLM 想，保证选项稳定可控。历史薄弱点来自跨场聚合，也是确定性逻辑，比如同一薄弱点多场缺失才进推荐。我不做无限开放的自由文本重点，因为噪声太大，面试计划难以稳定响应。以后可以在规则推荐之上再加模型润色，但入口我倾向于结构化。

#### 31.
数据为什么先用 SQLite？什么时候考虑换库？

SQLite 文件库部署简单，适合当前练习型、单机、并发不高的阶段。会话、消息、计划版本、评估结果、工作流状态我都落库，刷新能恢复。如果以后并发写入争用明显、要做复杂报表或热备，我会迁 Postgres，但那是看到容量信号之后的事，不是 MVP 阶段就上大库。小规模试用，SQLite 足够我把精力放在 Agent 上。

高频追问：刷新页面会话能恢复靠的是什么？

追问回答：对话在 messages 表，进度在 workflow_state，都在库里，否则刷新就全丢。我专门测过计划确认后进对话页、聊几轮刷新，消息和当前主题还在，这对模拟面试产品是关键体验，也是持久化必须做到位的部分。

#### 32.
这个项目怎么测？AI 效果不是很难自动化吗？

效果确实难全自动，但结构和边界必须能测。

测试我会分层做：

- 出计划：主题数量、必考维度、摘要不能泄露完整开场题等校验是否生效

- 面试边界：时间到了、轮数到了，是否强制换题或结束

- 决策输出：模型返回的下一步动作是否在允许范围内（追问、换题、结束等）

- 工作记忆：每轮提取的证据是否正确合并进本场进度

- 降级：模型调用失败时，是否还能给出下一句回复、流程是否继续

Prompt 改完我会跑回归，至少保证流程不会静悄悄断掉。至于追问自然不自然、分数准不准，可以人工抽检；

高频追问：你写过最有价值的测试是哪类？

追问回答：我优先测降级和边界这类「挂了也不能崩」的场景，而不是纠结某次 Prompt 吐出的字面话术。

例如：全场答满 12 轮必须结束；决策层调模型失败时，下一步动作仍在允许范围内，页面上仍有一句面试官回复；计划生成校验连失败 3 次，也要退回模板计划，不能让用户卡在空白页。

这类测试保的是主流程不断、规则不被带偏。每次改面试流程图或相关逻辑，我都会跑这套，心里才有底。

#### 33.
流式输出是真流式还是模拟的？为什么这样选？

目前是生成完整回复再分块 SSE 推送，对用户仍有逐字出来的感觉，实现简单。真 token 流式要处理一轮里多次模型调用的顺序和中断，前端也要区分思考、决策、话术不同阶段，复杂度高一档。我当时的优先级是先把 ODA、证据、边界跑对，再用分块流式补体验，而不是反过来为了「看起来流」牺牲决策链正确性。

高频追问：以后要上真流式，难点在哪？

追问回答：难点在编排，不只在「能不能流式输出」。一轮用户回答背后，往往要依次做：抽证据 → 决策下一步 → 生成话术。要定清楚：从哪一步开始推给前端、等待时怎么显示「还在想」、有内容后怎么显示「开始说」；用户中途刷新或断网，怎么从库里恢复，而不是从头聊。还要和防重复提交、「正在生成回复」锁配合——上一句还没生成完，不能又收一轮新回答，否则会出现半句话、状态错乱。我的做法是先加耗时观测，看用户实际卡在哪一步，再决定值不值得给「生成话术」单独做流式；不会为了炫技把整个链路都改成逐字吐 token。

#### 34.
如果继续做这个产品，下一步优先做什么？

我会先做运行时观测：每轮里出计划、抽证据、做决策、生成话术各花多少时间、用了多少 token、降级触发了几次——没有这些数据，优化就是瞎改。再补产品缺口：跨场次练前推荐的配置页界面、把岗位知识库检索覆盖到更多岗位。然后才谈性能：比如一轮里多次调模型能不能并行或合并，缩短用户等待。不会为了炫技全盘改成真·逐字流式，也不会用户量还没起来就急着上 Postgres——这些等有明确流量信号再说。功能上也不会盲目加。计划锁定后的问评一致、证据链可解释，是用户信任的底座，这两块先稳住，再谈新能力。

高频追问：资源只够做一件事，选什么？

追问回答：

如果只能选一块先做，我会选观测 + 计划质量，两个一起推。

没有数据，你不知道慢是模型本身慢，还是流程里某一步多余；没有好计划，后面追问再聪明、报告再漂亮也救不了——用户第一眼就觉得「这场不像我要练的」。

用户感受的顺序大致是：

1. 考得像不像——主题、岗位、简历、岗位描述（JD）是否对路

2. 聊起来顺不顺——等多久、会不会断

3. 报告信不信——分数有没有依据

所以我会同时做两件事：把岗位知识库检索和出计划的提示词打磨好，让计划更贴岗位、更对齐 JD；把链路追踪和每步耗时打全，后面优化才有靶子。

#### 35.
做这个项目过程中，最满意的一个技术决策是什么？有没有想重来的？

我最满意的两件事是绑在一起的：

第一，用户确认后的面试计划就是唯一数据源——问什么、评什么，都按这份锁定的计划来，不会出现「问的是 A、评的是 B」。

第二，打分不看整段聊天记录重新「印象分」，而是看面试过程中攒下来的证据——哪句原话、对应哪个考察点，报告里能展开，分数才讲得清。

一个解决问和评对不上，一个解决分数像黑盒。两件事一起，产品才从「能演示」变成「真能拿来练」。

如果重来，我会改两处：

状态划分更早做清楚——计划阶段、对话阶段、评估阶段分开，别混在一个状态里绕；我中间迭代了好几版才稳，前端也少踩「页面该跳哪、能不能点开始」的坑。

性能观测更早接上——不然不知道用户主要等在哪。后来才看清楚：用户每答一轮，背后往往要调好几次模型，这才是延迟大头，优化才有方向。

高频追问：这个决策怎么向非技术同事解释？

追问回答：我会说：用户先确认「今天考什么」，再开始聊，聊完评分能点开看到「哪句话导致这个评价」，不会出现「问的是项目、评的却是沟通」那种割裂。还有，时间到了一定会停、模型坏了也能做完一场，这是为了让用户敢用、敢练。技术词换成「先对齐、再开练、评有据、有底线」，产品同事和运营都能听懂，也更好卖这个项目的价值。

#### 36.
什么是「工作记忆」？为什么不能只靠聊天记录？

工作记忆是面试过程中专门为「当前这场」维护的一份结构化笔记：每个考察方向下记了哪些原话证据、还缺哪些期望信号、有没有待核实的矛盾点。聊天记录是给人看的流水账，越来越长；工作记忆是给系统「算缺口、做决策、写报告」用的。如果只堆消息，模型每次都要重读全文，又慢又容易漏；有了工作记忆，追问知道还缺什么，报告也能稳定引用「哪句话支撑这个评价」。

高频追问：和短期记忆里的「摘要」是一回事吗？

追问回答：不是。摘要是某个主题聊完后压成的一段文字纪要，方便后面轮次知道背景；工作记忆里的证据是带出处、带主题归属的原话片段和缺口列表，偏可计算、可评分。我刻意分开：一个让人读得懂，一个让机器算得准。混成一种格式，要么评分追溯不了，要么 Prompt 里全是不可控的自然语言。

#### 37.
每轮回答里的「证据提取」在干什么？为什么重要？

用户每答一轮，系统会先从这段话里抽出和当前考察方向相关的原话片段，标成支持、风险或待核实，写进工作记忆。后面 Decide 看「还缺什么信号」、报告看「凭什么给这个状态」，都依赖这一步。没有证据提取，追问只能凭模型印象瞎追，报告也只能靠读完聊天即兴打分，和用户要的「能点开看依据」对不上。

高频追问：提取错了怎么办？

追问回答：单轮提取偏了，后面还有机会在后续回答里补证据；如果模型提取失败，有规则降级，至少保留原话片段和主题归属，不让这一轮流空。评估时未验证的主题不会硬给低分。设计上接受「单轮不完美」，但要求「全程可追溯、可修正」，而不是一次猜错就定终身。

#### 38.
你说的 ODA 是什么？三个步骤分别解决什么问题？

ODA 是「观察 Observation - 决策 Decide - 执行 Action」的 Agent 循环范式：Observe 观察当前状态——这轮用户说了什么、时间和轮数是否触线；Decide 决策下一步——继续追、换主题还是结束，并说明理由；Act 生成用户听得懂的面试官话术。拆开的好处是：出问题时能分清是「判断错了」还是「话说得不好」，日志里也能看到 action 和 reason，而不是只有一句面试官回复的黑盒。

高频追问：为什么不合成一步让模型直接说下一句？

追问回答：一步合成看起来省事，但不可审计。真实面试里面试官也是先判断「这个点够不够、要不要换题」，再组织语言。我们产品要长期迭代追问策略和边界，拆开之后可以单独调决策 Prompt、单独调话术 Prompt，甚至决策用规则、话术用模型。有一次话术生成超时，决策结果还在，模板顶上一句，用户仍能继续答——这就是拆分的工程价值。

#### 39.
从生成计划到出报告，三个环节怎么串起来？

可以想成一条流水线：Planning Agent 根据简历、岗位和配置产出考察计划，用户确认后锁定；Interview Agent 只认这份锁定计划，在对话里按主题追问、换题、收尾，同时往工作记忆里填证据；用户结束后，Evaluation Agent 按同一份计划把证据投影成各主题的验证状态和分数，再润色成报告。关键约束是「一份计划贯穿始终」——问什么、评什么，都来自用户确认过的那版，不会出现问项目和评沟通各说各话。

高频追问：中间哪一环最容易「跑偏」？

追问回答：对话环节。计划是批量的、可校验的；评估消费的是已落库证据；对话是实时、多轮、受模型随机性影响最大的。所以我在对话里加了硬边界、结构化决策、证据台账和降级，把跑偏限制在「追问不够聪明」，而不是「整场失控」。排查时也是先看对话轮的 decide 日志和 memory 缺口，而不是先怀疑计划或报告算法。

#### 40.
用户预览计划时，为什么只能看到方向摘要，看不到完整面试题？

这是刻意的防泄题设计。预览页告诉用户「今天大概考哪些方向、哪些必考」，足够他判断要不要换一版计划；具体开场怎么问、怎么追问、评分细则，属于面试官执行层，确认开始后才逐步展现。否则用户会对着预览背答案，练习价值就没了。技术上完整题目只在服务端内部计划里，下发给前端的只有候选人可见摘要字段。

高频追问：那用户会不会觉得「黑盒」？

追问回答：会有这种感觉，所以我们在摘要里给足信息：主题名、是否必考、和简历/JD 的关联提示、版本和剩余换版次数。用户知道「考什么」，只是不知道「逐字怎么问」，这和真实面试里候选人知道岗位考察面、不知道考官下一句一模一样。真不满意方向，可以在确认前换策略重生成，而不是偷看原题。

#### 41.
开场白为什么要口语化？直接用计划里的原题不行吗？

计划里的开场问是「意图锚点」，保证考的是这个方向；点「开始面试」时，会尽量改写成更像真人面试官口吻的一句，降低机读感。模型失败就退回计划原文，保证一定能开聊。口语化是体验层，不是换题——意图不能变，否则后面证据和评分都对不上。

高频追问：这会不会增加用户等待时间？

追问回答：会，多一次模型调用，激活接口比纯读库慢几秒。当前取舍是「进对话页时库里已有完整首条消息」，避免页面上有字但后端还算没开始。如果要优化，可以先用计划原文占位、后台再替换，或把口语化前移到确认计划时预生成——但我会先看耗时打点，再决定值不值得做。

#### 42.
校招和社招的面试计划，考察重点有什么不同？

校招更偏基础是否扎实、项目或实习经历是否说得清、遇到问题怎么分析、学习成长潜力；社招更偏真实项目贡献、技术深度、方案或系统设计、以及故障排查、工程落地或业务理解里至少一块。Planning 校验时会检查计划是否覆盖这些最低考察面，避免生成「只有八股、没有项目」或「只有项目、没有深度」的偏科计划。

高频追问：用户选错类型会怎样？

追问回答：计划可能和真实场景不匹配，比如社招岗却生成偏刷题的基础计划。我们在配置页用校招/社招开关和岗位标签引导，Planning Prompt 也会带入类型；如果用户填了 JD，还能拉回来一些岗位特异性。最佳做法仍是用户配对类型，系统做校验兜底，而不是事后硬改对话。

#### 43.
模型服务挂了，用户还能完成一场面试吗？你们怎么保证？

能。主路径用真实模型，但每条链路都有降级：计划生成失败有岗位模板；对话里决策失败有规则选动作，话术失败有模板句；报告叙事失败有规则文案，分数仍走证据和规则。测试里用「一调用就失败」的假客户端跑完整流程，断言仍然能返回下一句话、状态合法更新。产品承诺是「模型不稳定时练习还能做完」，而不是静默假装智能。

高频追问：降级时用户体验差很多吧？

追问回答：追问可能没那么犀利，话术可能模板感强一些，但流程完整、边界仍在、报告仍有依据。对用户来说，「能练完且有反馈」比「等模型恢复」更重要。我们会打日志标 degraded，方便事后看降级率；如果某段时间降级占比过高，说明该修模型接入而不是忽视。

#### 44.
「问和评一致」具体怎么做到？

核心是用户确认后锁定一份计划，记下这一版的 ID；之后对话只读这份计划里的主题和期望信号，不允许中途换考察清单；评估也只按这份计划的主题投影证据和打分。报告里每一项能力对应计划里的一个考察方向，不是另起一套泛泛维度。想改计划只能确认前换版，且有次数限制——执行和评分绑死后，问评就不会漂移。

高频追问：对话里口语化、改写会不会破坏一致？

追问回答：口语化只动表达方式，不动考察意图。证据提取和决策仍挂在计划里的主题和信号上；报告评的也是「这个主题下证据是否支撑期望信号」。如果为了好听把题改成另一个方向，校验和记忆归属会出问题，所以我们在 Act 层约束「意图不变」，Decide 层约束「动作只能围绕当前主题缺口」。

#### 45.
报告里的「已验证 / 部分验证 / 未验证」对用户意味着什么？

已验证：这个方向聊透了，有足够的原话证据支撑判断；部分验证：聊到了一些，但信号不完整；未验证：这场没有充分聊到，或证据不足。未验证不会给确定低分，也不会写成「不符合」，避免「时间不够没考到」被当成「能力不行」。用户看报告时能分清「我真的弱」还是「这场没展开」。

高频追问：部分验证和未验证差在哪？

追问回答：部分验证说明至少有过有效对话和证据，只是达不到「充分验证」的门槛，报告里会给有限结论和引用；未验证通常是几乎没聊或只有一句带过，系统选择不强行评判。这个区分减少了「聊了两句就给很差」或「完全没聊却给中间分」两种误解，也让练习建议更准——部分验证补细节，未验证建议下一场多留时间给这个方向。

#### 46.
JD 在用户配置里到底起什么作用？

JD 是用户粘贴的岗位描述原文，主要在生成计划时用：帮助对齐岗位关键词、在相关考察主题上打「和 JD 有关」的标记。评估阶段不逐条拿 JD 原文核对，只验证计划里 JD 相关主题有没有对话证据。没聊到写「未验证」，不写「不符合 JD」——没考到不等于不满足。

高频追问：为什么不把 JD 塞进每一轮追问？

追问回答：JD 往往很长，每轮都塞会噪声大、成本高，还容易和简历、计划信息冲突。岗位对齐应在计划层做一次，对话层消费「已对齐的计划」，评估层验「计划里和岗位相关的点」。用户的核心诉求是「考得贴岗位」，在计划层解决比在每个追问里重复更干净。

#### 47.
「和上一场对比」怎么做的？历史记录会影响当场打分吗？

多场练习后，系统会把各场报告里的薄弱信号聚合起来，在评估页展示和上一场的对比；练前也可能根据历史推荐重点方向，用户在配置页采纳后才会影响新计划。当场打分只看当场工作记忆和证据，历史不会偷偷进对话 Prompt 或拉低分数——否则用户会觉得「明明这次答好了还按老印象判」。

高频追问：历史推荐是模型想的还是规则算的？

追问回答：跨场聚合是确定性逻辑，比如同一薄弱信号多场出现才进推荐；配置页的标签推荐也是规则组合，保证选项稳定。我不做无限制的开放式「你弱在哪」文本，噪声太大，计划难以稳定响应。历史的价值是帮用户决定「下一场多练什么」，不是替当场面试官做预设立场。

#### 48.
登录和权限大概怎么做的？为什么面试数据要按用户隔离？

用户注册登录后拿到 token，后续请求带在请求头里，后端解析出是谁，再查简历、会话、额度。每场面试、每份简历都挂在用户 ID 下，A 用户不能看 B 的数据。这不只是安全要求，也是产品逻辑：额度、历史对比、推荐方向都是 per-user 的，隔离错了整个商业和体验模型都崩。

高频追问：token 过期了会怎样？

追问回答：接口返回未授权，前端清本地 token 并跳登录。面试进行到一半如果过期，刷新后需要重新登录，会话数据仍在库里，用 session_id 能恢复——只要还是本人。实现上我用的是常见 JWT 方案，重点是过期处理和前端 401 统一跳转，避免半登录态下乱调接口。

#### 49.
前端几个核心页面怎么配合？刷新会丢进度吗？

典型路径：配置页 → 计划预览页 → 正式对话页 → 评估页，中间还有会话列表。前端根据会话当前阶段决定跳转，不会「计划还没确认就进对话」。数据存在后端，刷新后重新拉会话和消息列表，计划确认后聊了几轮再刷新，对话和当前主题仍在——这对模拟面试很关键，不能只靠浏览器内存。

高频追问：列表页状态和详情不一致怎么办？

追问回答：以详情接口为准。列表为了展示会做一点纠偏，比如长时间卡在进行中可能标成待处理，但点进去看 status 和最后一条消息最准。前端我也会在关键操作后 refetch 详情，减少列表缓存旧状态。用户侧感知就是「点进去是对的」，列表偶尔滞后可以接受，详情不能错。

#### 50.
面试官老重复同一个点，系统怎么防？

两层：一是决策层有重复追问拦截，如果本轮想追的内容和上一轮刚追过的完全一样，会强制换切题或结束路径；二是用户连点发送有「回复处理中」锁，避免半句话状态下又收新回答导致状态乱。再配合单主题追问次数上限，从产品和代码两侧减少「卡死在一个问法上」。

高频追问：用户故意敷衍重复回答呢？

追问回答：证据层会识别低信息量或重复，Decide 可能判定信号仍缺失而换角度追，或达到轮数上限后切题。不会无限陪聊同一空答案，因为整场有总轮数和时长。报告里证据不足会反映为部分验证或未验证，而不是因为用户重复同一句就给极低分——除非能提取出明确负面证据。

#### 51.
岗位知识库的文档怎么组织？怎么建索引？

知识放在 backend/knowledge/roles/ 下，按岗位用 markdown 写，用二级标题切章节，脚本扫目录建向量索引。配置里打开知识库开关后，生成计划时会按目标岗位检索相关段落，塞进计划上下文。索引和对话模型配置是独立的：换了嵌入模型要删库重建，否则维度对不上。

高频追问：检索不到内容常见原因？

追问回答：三类最多：岗位名和文件名映射不上；文档加了但没重新跑索引；本地嵌入是词面匹配，简历/JD 措辞和知识库差太多命不中。排查时看日志有没有「检索无命中」，再看 Chunks 是否为 0。开发期用本地嵌入省 Key，上线前可以换更强的嵌入并重建索引。

#### 52.
为什么向量库用 Milvus Lite，而不是一上来用云服务？

当前阶段是单机、练习型产品，Milvus Lite 文件库部署简单，不需要单独起向量服务，和 SQLite 放在一起就能跑通 RAG 闭环。等并发、数据量和运维要求上来，再迁托管或集群版不迟。我优先把「计划能吃到岗位知识」这条链路跑通，而不是过早为基础设施付复杂度。

高频追问：和直接把 JD 塞进 Prompt 比，收益在哪？

追问回答：JD 是一份；岗位知识库可以沉淀多份 markdown、多岗位、可版本迭代，检索只拿相关片段，比每次全量塞 Prompt 更省、更稳。收益在计划质量——考得更贴岗位；不是让每轮对话都去搜库，那样噪声和时序都难控。

#### 53.
Prompt 出问题你怎么排查和迭代？

我从不只看最终一句输出，而是看该步的输入摘要、结构化输出、校验错误和是否触发降级。改 Prompt 后会跑回归：计划校验、边界切题、降级路径、关键 JSON schema。效果抽检用固定简历和 JD 做人工对比，但「流程不能断、不能泄题、不能越界」必须自动化。Prompt 是活文档，和代码一起版本化，而不是散落在聊天记录里。

高频追问：你怎么判断该改 Prompt 还是改代码？

追问回答：硬规则类：轮数、时长、次数、泄题，一定改代码，不能赌 Prompt 自觉。软质量类：追问是否贴切、话术是否自然，先改 Prompt，并看结构化决策 reason 是否已经把方向判对。如果 reason 对但话术差，只动 Act；reason 就偏了，动 Decide 或证据。这个分工省很多无效调 Prompt 时间。

#### 54.
做这个项目，你个人觉得最大的技术难点是什么？

是把「模型不确定」包进「流程确定」：每一轮都要在证据、决策、话术、边界、持久化之间保持一致，还要在模型失败时优雅降级，不能用户答到一半卡死。难的不是调一次 Chat，而是多场会话、刷新恢复、问评一致、可解释评分同时成立。状态设计和日志可追溯投入了大量时间，后期排查重复追问、激活慢，都靠这些底子。

高频追问：如果只能留一条经验给后来者？

追问回答：先钉死「用户确认的计划」和「证据驱动的评分」，再往上堆智能。没有这两个锚点，加 RAG、加记忆、加流式，都会变成更花哨的黑盒。面试里我能讲很多技术名词，但这两条是产品为什么成立、为什么敢让用户反复练的根。
